# Агент ревью требований для финтех‑проектов

Агент помогает аналитику и QA-инженеру решить, по каким требованиям уже можно готовить приёмку и что сначала нужно согласовать с владельцем продукта. На вход подаётся ТЗ в Markdown, PDF с текстовым слоем или DOCX. На выходе — отчёт на русском языке с цитатами, приоритетами, уточняющими вопросами и сценариями проверки. Проект подготовлен для BCC-HUB × MNU FinTech Hackathon.

### Как один вопрос меняет приёмку

Клиент совершил покупку в январе. Полный возврат в феврале уменьшает январские расходы на всю сумму. Но что должно произойти при **частичном** возврате? Агент предлагает взять другую январскую покупку на 4 000 ₸ и в феврале вернуть 1 500 ₸. Если правило распространяется на частичный возврат, январский итог должен уменьшиться на 1 500 ₸. При исключении частичных возвратов из этого правила январский итог остаётся прежним. Ответ владельца даёт QA проверяемый результат для одной и той же операции. [Правило о возвратах](docs/requirements.md?plain=1#L38) · [Вопрос, цитата и тест Z-008](reports/review14/review.md#z-008)

## Как устроен агент

1. **Чтение источника.** Парсер привязывает фрагменты к разделам, строкам Markdown, страницам PDF или элементам DOCX. Исходные ID требований сохраняются.
2. **Проверка требований и их связей.** Модель выделяет проверяемые утверждения. Затем рассматривает весь документ и сопоставляет, например, бизнес-правило, описание API и пример ответа.
3. **Проверка замечаний.** Отдельный запрос к той же модели перепроверяет каждое основание. Для открытого вопроса агент описывает, что уже известно, какое решение требуется и как ответ изменит ожидаемый результат теста.
4. **Сборка отчёта.** Python проверяет структуру ответа, существование ID и дословность цитат. Отчёт связывает каждое замечание с источником. В паспорте сохраняются версия кода, модель, время и хеши входа и результата. [Парсер](requirements_validator/source.py) · [Порядок вызовов](requirements_validator/engine.py) · [Вычитка вопросов](requirements_validator/question_proof.py) · [Сборка отчёта](requirements_validator/report.py)

**Что происходит при ошибке.** Агент может запросить у модели исправление, если вывод не подтверждён цитатой. При исчерпании попыток CLI сообщает причину и завершает запуск с ошибкой. В серии из 24 заданий для 23 хватило одного полного запуска. Для одного потребовался повтор с начала. Сохранены оба журнала и отчёт успешной попытки. [Разбор отказа и повтора](reports/README.md#reliability)

## Запуск на своём документе

Понадобятся **Python 3.10 или новее**, **Git**, **Codex CLI** и учётная запись с доступом к `gpt-6.2-sol`. На сохранённом прогоне использовался Codex CLI `0.171.0-alpha.13`. Склонируйте репозиторий с историей или распакуйте архив команды и откройте терминал в каталоге с этим README. [Установка Codex CLI](https://developers.openai.com/codex/cli/)

**1. Подключите модель.** Выполните `codex login` и затем `codex login status`. Для входа с API-ключом OpenAI создайте ключ в своём аккаунте и передайте его через стандартный ввод команды `codex login --with-api-key`. Секрет хранится средствами Codex CLI. Эта версия агента работает только с `gpt-6.2-sol` через Codex CLI. Файл `.env` для этого запуска необязателен. [Ключи OpenAI](https://platform.openai.com/api-keys) · [Пример настроек](.env.example)

**2. Установите зависимости и запустите проверку.** Ниже приведены команды для банковского примера. Чтобы проверить своё ТЗ, замените путь после `--input`. Путь после `--output` задаёт имя нового отчёта.

**Windows, PowerShell**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m requirements_validator --input docs/requirements.md --output .tmp/review.md
```

**Linux и macOS**

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m requirements_validator --input docs/requirements.md --output .tmp/review.md
```

**3. Откройте результат.** В `.tmp/review.md` сначала идут вывод о готовности и блокирующие вопросы. Каждая карточка ведёт к цитате и приёмочному сценарию. В `.tmp/review/run-meta.json` находятся параметры именно вашего запуска. Формулировки и число карточек при повторном обращении к модели могут меняться. Если повторный ответ модели не проходит проверку, CLI сообщает причину. История такого запуска видна в терминале. [Пример журнала](checks/review14/cli/markdown-attempt-1.txt)

При подготовке истории для публикации команда сверила дерево пакета `requirements_validator` и файл зависимостей `requirements.txt` для каждой версии из 600 паспортов. Git-идентификаторы этих объектов совпали в исходной и публичной версиях. [Таблица соответствия версий](checks/historical-revisions.json) · [Паспорт банковского запуска](reports/review14/review/run-meta.json)


## Проверка качества и границы результата

- **Повторяемость.** На семи размеченных документах агент обнаружил все 15 заложенных дефектов в каждом из трёх проходов. В каждом проходе 15 из 26 карточек совпали с эталоном по категории и цитатам (57,7 %). В отдельной вычитке модельный рецензент установил, что 23 из 33 остальных карточек за три прохода уточняют вход или ожидаемый результат теста. В это число входят повторения между проходами. [Метрики и метод подсчёта](reports/review14/evaluation.md) · [Разбор всех 33 карточек](reports/review14/additional-findings.md)
- **Техническая проверка.** Все 238 автоматических тестов прошли на каждой из трёх версий CPython под Windows — 3.10, 3.12 и 3.15. Независимая от модели программа проверила паспорта 600 сохранённых запусков, текст и адреса 19 493 цитат за историю разработки. [Проверенные версии Python](checks/review14/python-versions.md) · [Протокол проверки цитат](checks/review14/citations.json)
- **Практические границы.** Для сканов PDF нужен предварительный OCR. Объём входа ограничен контекстом модели. Бизнес-решения принимает владелец требований. Время банковского прогона измерено автоматически. Независимого ручного замера работы аналитика у команды нет.

Сохранённый банковский отчёт и тесты можно проверить локально без обращения к модели. После установки зависимостей выполните следующие команды интерпретатором виртуального окружения. В PowerShell используйте `.\.venv\Scripts\python.exe` вместо `python`.

```sh
python -m scripts.verify_report reports/review14/review.md docs/requirements.md
python -m unittest discover -q
```

Для сверки всех исторических отчётов установите в то же окружение `python-docx==1.2.0` и выполните `python -m scripts.verify_release`. [Проверка установки в чистом окружении](checks/review14/reproduction.txt)
