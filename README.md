# Агент статического ревью требований


CLI читает техническое задание и помогает аналитику или QA-инженеру подготовить обсуждение до разработки. Из каждого замечания можно перейти к исходной строке или странице, увидеть затронутые требования и определить, какой тест зависит от ответа автора. Основной результат — самодостаточный Markdown-файл на русском.

### Дополнительные сценарии, сверенные с исходником

- Для чужой и отсутствующей карты явно задан 404. Агент спрашивает, в каком ещё случае применим 403. Для запроса без тела он сопоставил пометку `Content-Type` с примером передачи параметров в query. [Вопрос о 403](reports/final.md#z-017) · [Заголовок запроса](reports/final.md#r-m0147-01) · [Тело запроса](reports/final.md#r-m0148-01)
- При выключении уведомлений агент предлагает проверить переключатель и отправку push. Остаётся отдельный вопрос для QA: продолжается ли накопление расходов, пока уведомления выключены? [Проверка `enabled`](reports/final.md#z-005)
- Для возврата отчёт прослеживает связь с исходной покупкой и её месяцем. Для приёмки полезен ещё один сценарий: отправить push, сделать возврат, снова достичь того же порога без изменения настройки и проверить месячное ограничение в одну отправку. [Возврат](reports/final.md#r-m0038-03) · [Месячный максимум](reports/final.md#r-m0039-03)
- Сумма покупки хранится в тиынах, порог — в целых тенге. Агент отдельно спрашивает про единицу в сообщении push. При проверке сравнения с порогом стоит взять сумму на один тиын ниже порога, затем добавить один тиын. Этот пограничный тест добавлен при сверке отчёта. [Единицы хранения](docs/requirements.md#L49) · [Вопрос о сумме для push](reports/final.md#z-004)
- В оригинале прямо указано, что версия, дата и отметки чек-листа не заполнены. По этим полям нельзя установить статус согласования. [Пояснение к шаблону](docs/requirements.md#L68) · [Блок согласующих](docs/requirements.md#L86)

## Запуск

Требуются Python 3.10+ и Git. Откройте терминал в корне репозитория и создайте виртуальное окружение.

**Windows, PowerShell**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Если Windows запускает установленный Python 3 командой `python`, окружение можно создать через `python -m venv .venv`.

**Linux и macOS**

```sh
python3 -m venv .venv
. .venv/bin/activate
```

Установите зависимости и проверьте, что агент запускается:

```sh
python -m pip install -r requirements.txt
python -m requirements_validator --help
```

### Доступ к модели

**Codex CLI.** Сохранённый отчёт получен через CLI `0.171.0-alpha.13` с моделью `gpt-6.2-sol`. Для воспроизведения установите эту версию для своей ОС и добавьте исполняемый файл `codex` в `PATH`. Понадобится аккаунт с доступом к выбранной модели. [Проверенный выпуск Codex CLI](https://github.com/openai/codex/releases/tag/rust-v0.171.0-alpha.13) · [Инструкция по установке](https://developers.openai.com/codex/cli/)

```sh
codex --version
codex login
codex login status
```

В корне репозитория создайте файл `.env` в UTF-8 со следующими двумя строками:

```dotenv
LLM_PROVIDER=codex
LLM_MODEL=gpt-6.2-sol
```

**Gemini API.** Адаптер проверен автономными тестами. Полный прогон с реальным ключом Google AI Studio пока не проверен, доступность модели и достаточность квоты зависят от проекта Google. Создайте ключ в AI Studio и скопируйте `.env.example` в `.env` командой `Copy-Item .env.example .env` в PowerShell или `cp .env.example .env` в Linux/macOS. В полученном файле заполните `GEMINI_API_KEY`, оставьте `LLM_PROVIDER=gemini` и укажите доступную вашему проекту модель в `LLM_MODEL`. Агент проверит поддержку `generateContent` и отправит короткий контрольный запрос. Переменные среды имеют приоритет над `.env`. [Пример настроек](.env.example) · [Ключ Google AI Studio](https://aistudio.google.com/docs/api-key) · [Каталог моделей](https://aistudio.google.com/docs/models)

### Проверка документа

После настройки одного из провайдеров команда для Markdown одинакова на всех трёх ОС:

```sh
python -m requirements_validator --input docs/requirements.md --output reports/final.md
```

## Как проходит проверка

1. Читатель вычисляет SHA-256 исходных байтов и строит индекс фрагментов с заголовками разделов. Для Markdown сохраняются строки файла, для PDF — страница и строки текстового слоя. Строка таблицы сохраняет контекст столбцов, а пример кода передаётся целиком.
2. Модель выделяет независимо проверяемые утверждения и даёт каждому локальную оценку. Она также классифицирует блоки, содержащие контекст, шаблоны и метаданные. Код требует решения по каждому входному блоку, проверяет буквальное вхождение каждой цитаты и назначает утверждениям ID с адресом исходного блока.
3. В отдельном запросе модель получает все блоки и реестр утверждений. Она сравнивает правила, спецификации, интерфейсы и примеры, подтверждает или снимает локальные гипотезы. Для доказанной неоднозначности нужны две трактовки, исходные цитаты и разные последствия.
4. Ещё один независимый запрос к той же модели проверяет каждое предложенное замечание по полному исходнику. Рецензент получает доказательства и решает, сохранить ли замечание, снять его или превратить в открытый вопрос. Он заново определяет серьёзность и устанавливает, блокирует ли вопрос конкретный приёмочный тест.
5. Код валидирует структуру JSON, ссылки на ID, цитаты, полноту оценок и решений по замечаниям. Повторно запрашиваются проблемные блоки или точечные правки ошибочных записей. Таблицы, счётчики и вопросы строятся по проверенному реестру. Рабочий файл заменяется атомарно после успешной проверки всего результата.

Для наблюдаемого значения агент прослеживает, кто его получает и какой фрагмент спецификации объясняет его источник или вычисление. Для интерфейсной операции он сопоставляет заявленный способ вызова с ожидаемым эффектом. Если документ описывает HTTP, доступен справочник двух свойств методов — безопасности и идемпотентности. В карточке замечания ссылка на правило протокола даётся отдельно от дословных цитат ТЗ. [RFC 9110, раздел 9.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)

Методические ориентиры заданы организаторами — ISO/IEC/IEEE 29148:2018, пп. 5.2.5–5.2.6, и IEEE 830-1998, п. 4.3. [Задание организаторов](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/main/README.md)

## Ограничения

- На вход подаются Markdown в UTF-8 или PDF с текстовым слоем. Скану требуется OCR. В сложной многоколоночной вёрстке порядок текста зависит от кодирования PDF.
- Для сквозной проверки весь исходник и извлечённые утверждения должны поместиться в контекст выбранной модели. Большой документ или исчерпание лимита могут остановить запуск. Уже сохранённый отчёт при этом сохраняется.
- Проверка цитаты устанавливает её присутствие в источнике. Смысловую связь, серьёзность и готовность к приёмке оценивает модель, а решение по бизнес-правилу принимает автор ТЗ. Повторный запуск может выделить другое число атомарных утверждений.
- Критичным считается непроверяемое, противоречивое или неполное требование, из-за которого нельзя принять существенный обязательный сценарий. Например, для одних и тех же условий заданы взаимоисключающие исходы либо ожидаемый результат отсутствует.
- Провайдер получает текст задания. При работе с внутренними спецификациями используйте разрешённый для них аккаунт и модель. В репозиторий попадают пример настроек и публичные материалы хакатона. Реальные ключи хранятся в локальном окружении.
