# Агент статического ревью требований

Аналитик получает список дефектов, вопросы владельцу требований и приёмочные сценарии. У каждого замечания есть ссылка на исходный текст. Агент читает Markdown, PDF с текстовым слоем и DOCX. Все модельные прогоны выполнены на **`gpt-6.2-sol` через Codex CLI**.


## Что показал запуск на ТЗ организаторов

Версия `5669ac8` проверила документ за 11 мин 12 с. В отчёте 127 утверждений, 5 нарушений по оценке модели и 17 вопросов к автору. Число проверенных по исходнику цитат — 182. [Отчёт](reports/finish4/review.md) · [Паспорт запуска](reports/finish4/review/run-meta.json)

В банковских отчётах для Markdown, PDF и Word исчез вопрос о длине `cardId` в байтах. Во всех трёх агент сначала выясняет, входит ли срок получения push клиентом в приёмку. Отдельно он спрашивает, какое наблюдаемое событие у отправителя устанавливает признак отправки. Тест проверяет признак до и после этого события.

[Исходное банковское ТЗ](docs/requirements.md) · [Вопросы и приёмочные сценарии](checks/finish4/handoff.md) · [Сопоставление Markdown, Word и PDF](checks/finish4/formats.md)

При вычитке 15 из 17 вопросов можно передать владельцу требований дословно. Для двух других, о возврате денег и о прежней настройке в теле ответа, предложены более узкие формулировки. [Разбор всех 17 вопросов](checks/finish4/queue-review.md)

## Как агент проверяет требования

Парсер даёт каждому фрагменту адрес в исходном файле. В первом проходе модель выделяет утверждения, во втором сопоставляет их по всему документу. Затем отдельный запрос к той же модели перепроверяет основания замечаний, приоритеты и вопросы. Перед записью Python проверяет структуру ответа, буквальные цитаты, ID и связи. В паспорте остаются версия кода, хеши исходника и отчёта, вызовы модели и время.

- Числовое правило и соседний пример пересчитываются в общей единице. Цитата должна подтверждать заявленное исключение. При сравнении ожидаемых выходов сохраняются регистр букв в литералах, знак и оператор.
- Для явной внутренней ссылки агент сверяет именованный ID с индексом всего документа. Если цель отсутствует, он предлагает восстановить адрес. Отдельный вопрос о поведении системы требует отдельного основания.
- Рецензент указывает, что источник уже установил и какие два результата одного теста зависят от ответа автора. Для неоднозначности нужны текстовые основания обеих трактовок. Разные последствия сохраняются даже при совпадении цитаты и названия темы.
- Неопределённое значение термина, отсутствующий результат действия и отсутствие меры проверки различаются при классификации. Отложенный приёмочный сценарий проверяется по другим разделам документа.

Если при одном и том же распознанном входе обязательное действие может закончиться двумя разными состояниями, рецензент ищет в документе требуемый результат. Для вопроса о байтах и символах требуется пример или правило, которое допускает такой идентификатор. В сценариях доставки рецензент отдельно проверяет, какое событие может наблюдать отправитель и что обещано получателю. [Проверка конечного состояния](requirements_validator/transition_result.py) · [Проверка вопросов](requirements_validator/question_scope.py)

## Результат на фиксированном корпусе

В каждом проходе семь документов и 15 заранее внесённых дефектов. По прежним прогонам этого корпуса команда разбирала причины ошибок. При запуске модель видит только исходное ТЗ. Для зачёта должны совпасть категория и все эталонные фрагменты. В знаменатель строгой точности входят все карточки агента, включая дополнительные вопросы.

| Проход | Найдено из 15, до → после | Совпало среди всех карточек, до → после | Вопросы автору, до → после |
|---|---:|---:|---:|
| 1 | 15 → 15 | 15/24 → 15/26 | 21 → 23 |
| 2 | 14 → 15 | 14/27 → 15/25 | 24 → 23 |
| 3 | 14 → 15 | 14/26 → 15/29 | 23 → 26 |

Во всех трёх проходах незаданное аварийное положение клапана отнесено к категории «Полнота». В тесте на вход подают уже распознанное некорректное показание и проверяют конечное положение клапана.

На восьми ранее проверявшихся документах агент нашёл все 8 внесённых дефектов. Четыре согласованных документа получили по 0 вопросов. На отдельной паре обнаружены все 3 дефекта. На её согласованной копии появился один лишний вопрос о точности наблюдения событий.

## Запуск на своём документе

Понадобятся Python 3.10+, Git и Codex CLI в `PATH`. В проверенном запуске использовался Codex CLI `0.171.0-alpha.13`. Из корня проекта выполните `codex login` под аккаунтом с доступом к `gpt-6.2-sol`, затем `codex login status`. CLI хранит данные авторизации отдельно от проекта. Для входа по ключу OpenAI принимает его через стандартный ввод команды `codex login --with-api-key`. [Установка Codex CLI](https://developers.openai.com/codex/cli/)

**Windows, PowerShell**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m requirements_validator --input docs/requirements.md --output .tmp/review.md
```

**Linux и macOS**

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m requirements_validator --input docs/requirements.md --output .tmp/review.md
```

Для другого документа замените путь после `--input`. Откройте `.tmp/review.md`. Паспорт этого запуска сохранится в `.tmp/review/run-meta.json`. Модель выбирается автоматически. Файл `.env` необязателен. Параметр `CODEX_EXTRACT_WORKERS` позволяет выбирать между одним и двумя потоками выделения требований. [Пример настроек](.env.example)

Если CLI пишет «Повторный ответ модели не прошёл проверку», автоматическая попытка исправления исчерпана. Повторите ту же команду. Ранее сохранённый отчёт останется доступен. [Журнал запусков](checks/finish4/attempts.md)
