# Агент статического ревью требований

Аналитик загружает ТЗ и получает список решений для согласования. Для каждого вопроса указано, какой сценарий QA проверит после ответа. Агент читает Markdown, текстовые PDF и DOCX. Все модельные прогоны в репозитории выполнены через Codex CLI на **`gpt-6.2-sol`**.


## Что обнаружено в исходном ТЗ

Версия `bf920eb` завершила анализ за **10 мин 54 с**. Проверено утверждений — 138, нарушений по оценке агента — 4, критичных — 2. Автору адресовано вопросов — 17, блокируют приёмку — 2. [ТЗ организаторов](docs/requirements.md) · [Паспорт, токены и длительность](reports/final/review/run-meta.json)

- После первого push автору нужно решить, позволяет ли смена порога отправить второй push по той же карте в том же месяце. Один ответ даёт тест на одно уведомление, другой — на два. [Ф-3 и Ф-4](docs/requirements.md#L39-L40) · [Две ветви решения](reports/final/review.md#z-009)
- Для покупки в 23:58 и проведения в 00:03 по Алматы не указан часовой пояс покупки. Чтобы зафиксировать месяц ожидаемого начисления, QA нужны обе полные временные метки и их последовательность. [Пограничный пример](docs/requirements.md#L64) · [Вопрос автору](reports/final/review.md#z-007)


Для быстрой проверки результата достаточно Python. Из корня проекта команда ниже заново читает оригинал, сверяет цитаты и выводит число проверенных утверждений и замечаний. Доступ к модели для неё не требуется.

```sh
python -m scripts.verify_report reports/final/review.md docs/requirements.md
```

## Запуск на своём документе

Понадобятся Python 3.10+, Git и Codex CLI в `PATH`. В проверенном запуске использовался Codex CLI `0.171.0-alpha.13`. Из корня проекта выполните `codex login` под аккаунтом с доступом к `gpt-6.2-sol`, затем `codex login status`. CLI хранит данные авторизации отдельно от проекта. Для входа по ключу OpenAI принимает его через стандартный ввод команды `codex login --with-api-key`. [Установка Codex CLI](https://developers.openai.com/codex/cli/)

**Windows, PowerShell**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m requirements_validator --input docs/requirements.md --output .tmp/review.md
```

**Linux и macOS**

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m requirements_validator --input docs/requirements.md --output .tmp/review.md
```

Для другого документа замените путь после `--input`. Откройте `.tmp/review.md`. Паспорт этого запуска сохранится в `.tmp/review/run-meta.json`. Модель выбирается автоматически. Файл `.env` необязателен. Параметр `CODEX_EXTRACT_WORKERS` позволяет выбирать между одним и двумя потоками выделения требований. [Пример настроек](.env.example)

Если CLI пишет «Повторный ответ модели не прошёл проверку», автоматическая попытка исправления исчерпана. Повторите ту же команду. Ранее сохранённый отчёт останется доступен. [Журнал запусков](checks/final/attempts.md)

## Как агент обосновывает решение

1. Python сохраняет хэш исходных байтов и адресует фрагменты по строкам Markdown, страницам PDF, абзацам и таблицам Word.
2. Модель выделяет утверждения, затем сопоставляет их по всему документу. Код проверяет дословность цитат. Для снятия локального сомнения нужны ссылки на проверенные утверждения.
3. Отдельный запрос к той же модели пересматривает основания и условия. Цитату, которой рецензент обосновал исключение, Python сверяет с источником. Отсутствие правила в выбранном фрагменте само по себе не подтверждает исключение. Вывод о смысле цитаты остаётся предметом рецензии.
4. Отчёт сначала показывает блокирующие вопросы, затем решения по нарушениям и прочие уточнения. Роли взяты из реквизитов связанных разделов, а ссылки ведут к исходному тексту. Если адресат не указан, вопрос остаётся у автора ТЗ. [Код анализа](requirements_validator/engine.py) · [Сборка отчёта](requirements_validator/report.py)

### Повторная проверка без ключа

Из активного виртуального окружения запустите команды ниже. Для `verify_release` нужна история Git из комплекта или полного клона. Библиотека `python-docx` используется для независимого чтения Word.

```sh
python -m unittest discover -v
python -m pip install python-docx==1.2.0
python -m scripts.verify_release
python -m scripts.evaluate --import-dir reports/final/benchmark-runs --repeat 3 --output .tmp/evaluation.md
```

Полные запуски выполнены в Windows. Для сканов PDF требуется предварительное распознавание. Длинный документ может превысить контекст модели. Время CLI замерено от запуска до записи результата. Команда не измеряла экономию человеко-часов. Цитату и её адрес проверяет код, итоговый выбор бизнес-правила остаётся за владельцем требования.
