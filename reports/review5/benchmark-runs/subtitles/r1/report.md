## Проверка набора в целом

Требования к BOM, шкале времени и обработке реплики из приёмочного примера задают несовместимые исходы. Для оценки лёгкости экспорта нужна измеримая мера. Ссылка T-40 требует редакторского исправления. Сообщение для пустой дорожки задано в T-6.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 требует записать экспортированный файл без BOM, а T-2 требует BOM в первых трёх байтах того же файла. Проверка формата не может удовлетворить обоим правилам.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с допустимой репликой в файл длиной не менее трёх байтов.

**Последствие.** Для одного файла предписаны несовместимые результаты проверки первых трёх байтов.

**Общее условие.** Приёмка проверяет первые три байта файла, записанного при экспорте дорожки по T-1. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат должна ожидать приёмка, наличие или отсутствие BOM?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** Первые три байта не образуют BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Принимать файл UTF-8, если первые три байта образуют BOM.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта образуют BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Экспортировать одну и ту же дорожку и сравнить первые три байта файла с EF BB BF.

### Z-002 · Масштаб временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт для одного поля миллисекунды и соответствие числа 1000 одной минуте. Приёмка экспорта не может однозначно проверить время реплики.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** В поле временной метки экспортированного файла записано 1000.

**Последствие.** Один и тот же файл задаёт разные времена реплики в зависимости от применённого правила.

**Общее условие.** В поле временной метки, для которого T-3 объявляет миллисекунды, записано число 1000. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой момент должно обозначать значение 1000, одну секунду или одну минуту?

1. **Вариант 1.** Читать числовые значения полей временных меток в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Значение 1000 соответствует одной секунде.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Трактовать значение 1000 в поле временной метки как одну минуту и согласовать с этим объявленную единицу.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Значение 1000 соответствует одной минуте.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Прочитать значение 1000 из поля результата экспорта и сверить, какой момент оно должно обозначать.

### Z-003 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** Реплика из примера T-8 превышает лимит T-7. Конфликт блокирует приёмку проверки превышения лимита.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Попытаться экспортировать реплику из приёмочного примера, текст которой состоит из 81 кодовой точки Unicode.

**Последствие.** Отклонение реплики выполняет T-7 и проваливает пример T-8. Принятие даёт обратный результат.

**Общее условие.** Проверяется реплика из примера T-8 с текстом длиной 81 кодовая точка Unicode. Этот текст превышает порог T-7. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат должен ожидать тест T-8, принятие или отклонение реплики?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Запустить экспорт с репликой из примера T-8 и проверить результат её обработки.

<a id="z-004"></a>

### Z-004 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт ощущался лёгким для каждого пользователя, но не задаёт наблюдаемой меры успеха. Это мешает оценить удобство при успешно выполненном экспорте.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователи успешно экспортируют дорожку, но оценивают усилие по-разному.

**Последствие.** Оценщики могут вынести разные решения о выполнении T-4 на одних данных.

**Уже установлено.** Пользователь экспортирует открытую дорожку в локальный файл. T-4 требует, чтобы экспорт ощущался лёгким для каждого пользователя. Основания — [R-M0009-01](#r-m0009-01), [R-M0003-02](#r-m0003-02).

**Открытое решение.** Выбрать измеримый критерий лёгкости экспорта для каждого пользователя.

**Что различит проверка.** По одному критерию наблюдаемый результат каждого участника соответствует порогу и испытание проходит. / По другому критерию те же наблюдения дают результат за порогом хотя бы для одного участника и испытание проваливается.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому наблюдаемому критерию, порогу и охвату пользователей принимать T-4?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователи успешно экспортируют дорожку, но оценивают усилие по-разному.».

**Черновик приёмочного теста.** Провести экспорт с согласованным охватом пользователей и сравнить измеренный результат с выбранным порогом.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта. Сначала нужно согласовать формат файла и результат проверки лимита.

1. Согласовать наличие BOM и шкалу временных меток. Привести описание формата и приёмку в соответствие с этими решениями. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать лимит длины текста и ожидаемый результат для реплики из приёмочного примера. ([Z-003](#z-003))
3. Задать измеримый критерий лёгкости экспорта и порядок его проверки. ([Z-004](#z-004))
4. Исправить ссылку T-40 или включить текст сообщения в исходное правило. ([Z-005](#z-005))
