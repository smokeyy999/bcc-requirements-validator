Требования расходятся по BOM, масштабу временных меток и исходу для реплики из 81 кодовой точки. Для лёгкости экспорта нужен измеримый критерий. Ссылка T-40 требует редакторского исправления.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · Наличие BOM в файле

**Дефект · Противоречивость · Критичная.** T-1 исключает BOM, а T-2 требует его в том же файле. Файл, записанный по T-1, провалит обязательную проверку формата.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с обычным текстом без начального U+FEFF.

**Последствие.** Один и тот же файл нельзя принять одновременно по обоим пунктам.

**Общее условие.** Приёмка файла UTF-8, полученного при успешном экспорте непустой дорожки. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Файл в этом сценарии должен начинаться с EF BB BF или записываться без BOM?

1. **Вариант 1.** Записывать дорожку в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** При приёмке требовать BOM UTF-8 в первых трёх байтах.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Файл начинается с EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Экспортировать дорожку и проверить первые три байта по выбранному правилу.

### Z-002 · Масштаб временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт миллисекунды и соответствие 1000 одной минуте для того же поля. Из-за несовместимого масштаба нельзя принять точность временных меток.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать реплику с временной отметкой в одну минуту.

**Последствие.** Одна минута представляется разными числами в одном и том же поле.

**Общее условие.** В экспортируемом поле временной метки требуется представить одну минуту. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое представление одной минуты принять: 60000 по заявленной единице или 1000 по заданному соответствию?

1. **Вариант 1.** Число в каждом поле временной метки выражает время в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** В поле записано 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Число 1000 в поле временной метки представляет одну минуту.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** В поле записано 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать реплику с отметкой в одну минуту и сверить число в соответствующем поле.

### Z-004 · Приёмка реплики из 81 кодовой точки

**Дефект · Противоречивость · Критичная.** T-7 требует отклонить реплику из приёмочного примера, а T-8 требует её принять. Обязательная проверка ограничения даёт взаимоисключающие исходы.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Подать на экспорт реплику из приёмочного примера с текстом длиной 81 кодовая точка Unicode.

**Последствие.** Приёмочный пример требует принять реплику, которую общее правило требует отклонить.

**Общее условие.** Экспорт реплики из приёмочного примера с текстом длиной 81 кодовая точка Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплика из приёмочного примера должна быть отклонена или принята?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Выполнить экспорт из приёмочного примера и проверить, принята ли реплика.

### Z-003 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 обещает лёгкость экспорта для каждого пользователя. Без измеримого критерия нельзя оценить выполнение этого свойства, хотя сам экспорт проверяется отдельно.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователи выполняют экспорт одной открытой дорожки и по-разному оценивают затраченные усилия.

**Последствие.** По наблюдениям нельзя вынести однозначный вердикт о выполнении T-4.

**Уже установлено.** Проверяется лёгкость локального экспорта одной открытой дорожки для каждого пользователя. Основания — [R-M0009-01](#r-m0009-01), [R-M0003-01](#r-m0003-01).

**Открытое решение.** Какой измеримый критерий определяет, что экспорт ощущается лёгким для каждого пользователя?

**Что различит проверка.** При допустимой оценке усилий до 2 баллов из 5 для каждого пользователя результат проходит, если максимальная оценка равна 2. / При допустимой оценке усилий до 1 балла из 5 для каждого пользователя те же наблюдения не проходят.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой наблюдаемый показатель и порог определяют успех и как подтвердить заявленный охват пользователей?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователи выполняют экспорт одной открытой дорожки и по-разному оценивают затраченные усилия.».

**Черновик приёмочного теста.** Провести экспорт по согласованной процедуре и сравнить наблюдения с утверждённым критерием и порогом.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке. Сначала нужно согласовать формат файла и ожидаемые исходы обязательных проверок.

1. Согласовать наличие BOM, числовое представление временных меток и исход экспорта реплики из приёмочного примера. Привести требования и проверки в соответствие. ([Z-001](#z-001), [Z-002](#z-002), [Z-004](#z-004))
2. Задать показатель, порог и способ подтвердить, что критерий лёгкости выполнен для каждого пользователя. ([Z-003](#z-003))
3. Исправить внутреннюю ссылку T-40. Сообщение для пустой дорожки уже задано в T-6. ([Z-005](#z-005))
