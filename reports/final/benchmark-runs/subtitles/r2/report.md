## Проверка набора в целом

ТЗ задаёт несовместимые результаты для BOM, значения временной метки 1000 и реплики из приёмочного примера. Состояние файла после отклонения длинной реплики требует уточнения. У обещанной лёгкости экспорта отсутствует критерий приёмки, а ссылка на сообщение пустой дорожки ошибочна.

Открытых предполагаемых пробелов — 1. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

<a id="critical"></a>

## Критичные дефекты

- [Z-002](#z-002) · T-1 требует записать файл без BOM, а T-2 требует BOM в первых трёх байтах того же файла. Успешный экспорт нельзя принять по обоим правилам.
- [Z-003](#z-003) · T-3 объявляет миллисекунды для каждого поля временной метки, поэтому 1000 в таком поле соответствует одной секунде. Для того же значения T-3 прямо задаёт одну минуту. Корректность экспортированного времени нельзя проверить по обоим правилам.
- [Z-005](#z-005) · T-7 требует отклонить реплику из 81 кодовой точки, поскольку 81 превышает 80. T-8 принимает эту реплику в приёмочном примере. Для обязательной проверки ограничения заданы взаимоисключающие результаты.

### Z-002 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 требует записать файл без BOM, а T-2 требует BOM в первых трёх байтах того же файла. Успешный экспорт нельзя принять по обоим правилам.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Успешно экспортировать непустую дорожку в локальный файл.

**Последствие.** Для одного файла требования задают несовместимые признаки начала файла.

**Общее условие.** Проверяется начало файла, полученного при экспорте дорожки. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл принимать: с начальным BOM или без него?

1. **Вариант 1.** Записывать UTF-8 без начального BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать UTF-8 с BOM в первых трёх байтах.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла — EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Экспортировать дорожку, прочитать первые три байта файла и проверить наличие EF BB BF по выбранному правилу.

### Z-003 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 объявляет миллисекунды для каждого поля временной метки, поэтому 1000 в таком поле соответствует одной секунде. Для того же значения T-3 прямо задаёт одну минуту. Корректность экспортированного времени нельзя проверить по обоим правилам.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Интерпретировать экспортированное поле временной метки со значением 1000.

**Последствие.** Одна и та же запись задаёт либо одну секунду, либо одну минуту.

**Общее условие.** В поле временной метки с объявленной единицей «миллисекунды» записано 1000. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое время должно означать значение 1000: одну секунду или одну минуту?

1. **Вариант 1.** Числа в полях временных меток выражены в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Значение 1000 означает одну секунду.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Значение 1000 в поле временной метки означает одну минуту.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Значение 1000 означает одну минуту.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Прочитать поле со значением 1000 по правилам формата и сверить полученное время с выбранным исходом.

### Z-005 · Реплика из приёмочного примера

**Дефект · Противоречивость · Критичная.** T-7 требует отклонить реплику из 81 кодовой точки, поскольку 81 превышает 80. T-8 принимает эту реплику в приёмочном примере. Для обязательной проверки ограничения заданы взаимоисключающие результаты.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Проверить реплику из T-8 длиной 81 кодовую точку Unicode.

**Последствие.** Приёмка одной реплики требует противоположных решений.

**Общее условие.** Проверяется реплика из приёмочного примера T-8 длиной 81 кодовая точка Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплику из T-8 следует принять или отклонить?

1. **Вариант 1.** Отклонять реплики с текстом длиннее 80 кодовых точек Unicode, включая реплику из приёмочного примера.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать указанную в примере реплику длиной 81 кодовую точку Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Подать реплику из примера на экспорт и проверить исход для этой реплики.

**Последствие.** По тексту нельзя определить, выполнено ли обязательное требование к удобству.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому наблюдаемому результату и в каких условиях следует принимать выполнение T-4?

**Черновик приёмочного теста.** Выполнить экспорт в согласованных условиях и оценить результат по заданному критерию.

### R-M0003-01 · За один экспорт выгружается одна открытая дорожка.

## Готовность и порядок исправлений

ТЗ пока не готово к разработке и приёмке. Сначала нужно согласовать формат начала файла, шкалу временных меток и результат проверки реплики из T-8.

1. Согласовать правило для BOM и шкалу временных меток с ожидаемыми результатами проверки файла. ([Z-002](#z-002), [Z-003](#z-003))
2. Согласовать ограничение длины с результатом приёмочного примера для 81 кодовой точки. ([Z-005](#z-005))
3. Определить состояние файла после отклонения длинной реплики в непустой дорожке. ([Z-001](#z-001))
4. Задать наблюдаемый критерий и условия проверки лёгкости экспорта. ([Z-004](#z-004))
5. Исправить ссылку на источник сообщения для пустой дорожки по T-6. ([Z-006](#z-006))
