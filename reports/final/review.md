## Проверка набора в целом

Критичны два сценария. После смены порога правила расходятся в том, будет ли второй push за месяц. Операция сохранения запрашивает изменение настройки через безопасный HTTP-метод. Для остальных сценариев нужно уточнить сквозной срок получения push, отдельные условия приёмки и обмен данными между компонентами.

Открытых предполагаемых пробелов — 15. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-009](#z-009) · Ф-3 запрещает второй push на карту за месяц. Ф-4 требует push при достижении повышенного порога независимо от истории предыдущей настройки. Оба правила охватывают то же достижение, поэтому принять сценарий смены порога по одному ожидаемому результату нельзя.
- [Z-011](#z-011) · Часть B прямо задаёт GET и замену настройки по запросу клиента. Пример использует тот же метод. По RFC 9110 § 9.2.1 GET — безопасный метод. Запрошенная замена ресурса выходит за его семантику, поэтому обязательное сохранение нельзя принять по этому HTTP-контракту.

### Z-009 · Месячный лимит push после смены порога

**Дефект · Противоречивость · Критичная.** Ф-3 запрещает второй push на карту за месяц. Ф-4 требует push при достижении повышенного порога независимо от истории предыдущей настройки. [R-M0126-01](#r-m0126-01) · Уведомление о расходах по карте / Часть B. REST API / Особые правила · [строка 126](../../docs/requirements.md#L126)

> Изменение порога сохраняет накопленные расходы.  

**Сценарий.** Уведомление включено. По карте уже получен push в этом календарном месяце. Порог повышают выше накопленных расходов, затем покупка в том же месяце доводит расходы до нового порога.

**Последствие.** Клиент получит один или два push за месяц в зависимости от выбранного правила.

**Общее условие.** По карте уже получен push в текущем календарном месяце. Порог повышен выше накопленной суммы и достигнут покупкой в том же месяце. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При достижении нового порога в этом сценарии отправлять второй push или подавлять его?

1. **Вариант 1.** Максимум один такой push на карту за календарный месяц, включая достижения после смены порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если расходы ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Клиент получает второй push в том же месяце.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** Получить первый push, повысить порог и достичь его покупкой в том же месяце. Проверить наличие второй отправки и второго push.

### R-M0144-06 · Входной \`enabled\` задаёт признак включения уведомления.

Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [строка 144](../../docs/requirements.md#L144)

> \| 0 или 1 \| Признак включения \|  

**Связано с нарушением в спецификации.** Строка приёмки задаёт итог и один push, но не фиксирует состояние переключателя и квоты. Выключенное начальное состояние задано. Таблицы допускают 0 и 1, а пример подтверждает возврат сохранённого кода как строки. Связь каждого кода с отправкой push не указана.

## Готовность и порядок исправлений

ТЗ не готово к полной разработке и приёмке. Сначала требуется согласовать поведение после смены порога и HTTP-контракт сохранения. Остальные вопросы можно закрывать параллельно с разработкой независимых частей.

1. Согласовать приоритет правил после смены порога и выбрать HTTP-метод для обязательного сохранения настройки. ([Z-009](#z-009), [Z-011](#z-011))
2. Задать сквозной срок, связь кодов с состоянием уведомления, правила учёта квоты и признака отправки, часовой пояс покупки и предусловия примера с одним push. ([Z-001](#z-001), [Z-004](#z-004), [Z-006](#z-006), [Z-007](#z-007), [Z-015](#z-015))
3. Установить чтение порога и переключателя, источник месячной суммы на экране, смысл и единицу суммы для push и источник последних цифр карты. ([Z-002](#z-002), [Z-003](#z-003), [Z-008](#z-008), [Z-010](#z-010))
4. Уточнить состав ответов при ошибках, границы проверки параметров, классификацию неуспешных ответов и участие Prod в приёмке. ([Z-005](#z-005), [Z-013](#z-013), [Z-016](#z-016), [Z-018](#z-018), [Z-021](#z-021), [Z-022](#z-022))
5. Уточнить отображение тиынов и перенести пример ответа под заголовок 404. ([Z-014](#z-014), [Z-023](#z-023))
