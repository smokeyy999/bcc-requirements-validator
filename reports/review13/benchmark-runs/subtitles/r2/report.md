## Проверка набора в целом

Требования задают несовместимые результаты для BOM, минутной отметки и реплики из приёмочного примера. Для лёгкости экспорта нужна измеримая мера. Ссылка на T-40 требует редакторской правки, а текст сообщения для пустой дорожки уже задан в T-6.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в экспортированном файле

**Дефект · Противоречивость · Критичная.** T-1 предписывает записать файл без BOM, а T-2 требует BOM в начале этого же файла. Успешный экспорт нельзя принять по обоим правилам.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с допустимой репликой и прочитать первые три байта файла.

**Последствие.** Один файл не может одновременно выполнить оба требования к BOM.

**Общее условие.** Проверяются первые три байта файла, полученного при экспорте открытой дорожки. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку, с BOM или без BOM?

1. **Вариант 1.** Записывать дорожку в UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Требовать UTF-8 BOM в первых трёх байтах файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла равны EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Экспортировать одну и ту же непустую дорожку и проверить начало файла по выбранному правилу.

### Z-002 · Масштаб отметок времени

**Дефект · Противоречивость · Критичная.** Обе части T-3 относятся к одному полю. Для одной минуты заявленная единица даёт 60000, а заданное соответствие даёт 1000. Приёмка числового представления времени заблокирована.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать реплику с отметкой в одну минуту и прочитать числовое значение этого поля.

**Последствие.** Потребитель, читающий поле в заявленных миллисекундах, воспринимает значение 1000 как одну секунду.

**Общее условие.** Проверяется числовое значение поля отметки в одну минуту. T-3 объявляет миллисекунды для каждого поля отметки времени. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое значение для отметки в одну минуту должна принять проверка, 60000 или 1000?

1. **Вариант 1.** Выражать каждую отметку времени в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Отметка в одну минуту записана числом 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Использовать шкалу, в которой значение 1000 представляет одну минуту.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Отметка в одну минуту записана числом 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать отметку в одну минуту и сравнить число в соответствующем поле с выбранным результатом.

<a id="z-004"></a>

### Z-004 · Длина реплики в приёмочном примере

**Дефект · Противоречивость · Критичная.** Текст реплики из T-8 содержит 81 кодовую точку Unicode и превышает предел T-7. Одну и ту же реплику требуется отклонить и принять, поэтому приёмочный пример нельзя выполнить по обоим правилам.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Подать на экспорт реплику из приёмочного примера T-8 с текстом длиной 81 кодовую точку Unicode.

**Последствие.** Экспортёр, применяющий лимит T-7, отклоняет реплику, которую приёмочный пример требует принять.

**Общее условие.** На экспорт подаётся реплика из приёмочного примера с текстом длиной 81 кодовую точку Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплику из T-8 длиной 81 кодовую точку следует отклонить или принять?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из приёмочного примера длиной 81 кодовую точку Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Повторить приёмочный пример с репликой из 81 кодовой точки и проверить выбранный исход.

<a id="z-003"></a>

### Z-003 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 обещает лёгкость экспорта для каждого пользователя, но не задаёт измеримого критерия. Это мешает проверить заявленное свойство отдельно от результата экспорта.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователи выполняют один и тот же экспорт и по-разному оценивают его лёгкость.

**Последствие.** По результатам проверки нельзя вынести однозначное решение о выполнении T-4.

**Уже установлено.** Свойство относится к опыту экспорта каждого пользователя. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Какой измеримый критерий подтверждает лёгкость экспорта для каждого пользователя?

**Что различит проверка.** Если по согласованному критерию наблюдаемый результат каждого проверяемого пользователя достаточен, проверка T-4 проходит. / Если тот же результат хотя бы одного пользователя ниже согласованного порога, проверка T-4 не проходит.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой наблюдаемый результат подтвердит лёгкость экспорта и как проверка должна установить охват всех пользователей?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователи выполняют один и тот же экспорт и по-разному оценивают его лёгкость.».

**Черновик приёмочного теста.** Провести экспорт по согласованным условиям и оценить результат по установленному критерию и охвату.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке по текущим формулировкам. Для трёх обязательных сценариев нужно согласовать ожидаемый результат.

1. Согласовать наличие BOM и числовое представление отметок времени, затем привести проверки формата в соответствие с выбранными правилами. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать предел длины текста с ожидаемым исходом для реплики из 81 кодовой точки Unicode. ([Z-004](#z-004))
3. Задать измеримый критерий лёгкости экспорта и способ проверки охвата пользователей. ([Z-003](#z-003))
4. Исправить ссылку на T-40 редакторской правкой. ([Z-005](#z-005))
