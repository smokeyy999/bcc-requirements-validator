Открытых предполагаемых пробелов — 1. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

<a id="z-001"></a>

### Z-001 · Наличие BOM в файле экспорта

**Дефект · Противоречивость · Критичная.** T-1 требует записать файл без BOM, а T-2 требует BOM в начале того же файла. Приёмка формата экспортированного файла невозможна без выбора.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку без символа U+FEFF в данных.

**Последствие.** Для одного файла спецификация и приёмочный тест требуют противоположных результатов.

**Общее условие.** Проверяются первые три байта успешно экспортированного файла. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку, с BOM или без BOM?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет UTF-8 BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать UTF-8 BOM в первые три байта файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла образуют UTF-8 BOM.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Выполнить экспорт и сравнить первые три байта с EF BB BF.

<a id="z-004"></a>

### Z-004 · Приёмочный пример превышает лимит длины

**Дефект · Противоречивость · Существенная.** T-7 требует отклонить реплику длиннее 80 кодовых точек, а T-8 принимает реплику из 81. Нельзя определить ожидаемый исход явно заданного приёмочного примера.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Экспортировать дорожку с репликой из приёмочного примера, текст которой содержит 81 кодовую точку Unicode.

**Последствие.** Один и тот же пример имеет несовместимые ожидаемые исходы.

**Общее условие.** Проверяется реплика из приёмочного примера T-8 с текстом из 81 кодовой точки Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплика из приёмочного примера должна быть отклонена по общему правилу или принята?

1. **Вариант 1.** Отклонять реплики длиннее 80 кодовых точек Unicode, включая реплику из примера.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в приёмочном примере и явно согласовать этот случай с общим лимитом.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Выполнить экспорт с репликой из T-8 и проверить, принята она или отклонена.

<a id="z-003"></a>

### Z-003 · Критерий лёгкости экспорта

**Предполагаемый пробел · Проверяемость · Существенная.** T-4 прямо обещает лёгкость экспорта для каждого пользователя. В документе отсутствует критерий проверки этого свойства. Файловый результат проверяется отдельно.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователь успешно экспортирует дорожку, но считает процедуру трудной.

**Последствие.** По документу нельзя решить, выполнено ли T-4 в этом случае.

<a id="z-005"></a>

### Z-005 · Ссылка на отсутствующий T-40

**Дефект · Трассируемость · Низкая.** T-5 ссылается на отсутствующий T-40. Точный текст сообщения для того же случая задан в T-6, поэтому замена ссылки сохраняет ожидаемый результат.

Затронутые утверждения — [R-M0010-01](#r-m0010-01), [R-M0011-01](#r-m0011-01).

[R-M0010-01](#r-m0010-01) · Subtitle track export / Format · [строка 10](../../../../../benchmark/subtitles/requirements.md#L10)

> For an empty track, display the exact message listed in T-40  

[R-M0011-01](#r-m0011-01) · Subtitle track export / Format · [строка 11](../../../../../benchmark/subtitles/requirements.md#L11)

> The message for an empty track is “Add at least one cue”.  

**Сценарий.** При подготовке теста пустой дорожки перейти по ссылке на T-40.

**Последствие.** По ссылке нельзя найти ожидаемую строку, хотя она доступна в T-6.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

Проект правки по [R-M0010-01](#r-m0010-01), [R-M0011-01](#r-m0011-01) — В правиле экспорта пустой дорожки заменить нерабочую ссылку ссылкой на пункт с точным текстом сообщения.

**Черновик приёмочного теста.** Открыть исправленные пункты [R-M0010-01](#r-m0010-01), [R-M0011-01](#r-m0011-01) и проверить выполнение предложенной правки «В правиле экспорта пустой дорожки заменить нерабочую ссылку ссылкой на пункт с точным текстом сообщения.».

## Готовность и порядок исправлений

К полной приёмке ТЗ не готово. До реализации формата файла и проверки длины реплик нужно согласовать ожидаемые исходы для BOM и примера T-8.

1. Согласовать наличие BOM и привести правило записи и приёмочный тест к одному исходу. (Z-001)
2. Согласовать лимит длины и ожидаемый исход для реплики из T-8. (Z-004)
3. Задать наблюдаемый критерий и способ проверки лёгкости экспорта. (Z-003)
4. Исправить в T-5 ссылку на пункт с точным текстом сообщения. (Z-005)
