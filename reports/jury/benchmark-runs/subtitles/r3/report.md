### Z-001 · BOM в файле экспорта

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM в экспортированном файле, а T-2 требует его в первых трёх байтах того же файла. Результат успешного экспорта нельзя принять по обоим правилам.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Успешно экспортировать непустую дорожку, удовлетворяющую лимиту длины.

**Последствие.** Реализация формата T-1 провалит проверку T-2.

**Общее условие.** Проверяются первые три байта файла, записанного при успешном экспорте дорожки. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку, с BOM или без него?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла отсутствует BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать BOM UTF-8 в первые три байта файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла образуют BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Проверить первые три байта файла на наличие BOM UTF-8.

### Z-004 · Длина субтитра в приёмочном примере

**Дефект · Противоречивость · Существенная.** Текст из примера T-8 содержит 81 кодовую точку Unicode и подпадает под лимит T-7. Принятие прямо задано примером, а исключение из общего правила не установлено.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Экспортировать дорожку с субтитром из приёмочного примера, текст которого содержит 81 кодовую точку Unicode.

**Последствие.** Соблюдение лимита приводит к отклонению субтитра, который по примеру должен быть принят.

**Общее условие.** Проверяется субтитр из приёмочного примера с текстом длиной 81 кодовая точка Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Следует отклонить субтитр из примера по общему лимиту или принять его как исключение?

1. **Вариант 1.** Отклонять субтитр с текстом длиннее 80 кодовых точек Unicode, включая приёмочный пример.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Субтитр из примера отклонён.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Применять лимит в 80 кодовых точек Unicode с исключением для субтитра из 81 кодовой точки в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Субтитр из примера принят.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Подать субтитр из приёмочного примера и проверить, принят ли он.

### Z-002 · В T-3 миллисекунды относятся к числу, записанному в поле, или к длительности после его преобразования?

**Предполагаемый пробел · Полнота · Существенная.** T-3 прямо сопоставляет 1000 с одной минутой. Одна секунда получается только при условии, что объявленная единица относится непосредственно к записанному числу. Смена объявленной единицы также не следует из T-3.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds;  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать отметку в одну минуту и проверить объявленную единицу и записанное значение по согласованному правилу их связи.

**Что нужно уточнить.** Неясно, относится ли объявление миллисекунд к записанному числу или к длительности после преобразования.

**Как ответ изменит приёмку.** Если единица относится к записанному числу, 1000 миллисекунд расходятся с заданной минутой. Если единица относится к длительности после преобразования, значению 1000 соответствуют 60 000 миллисекунд.

### Z-005 · Ссылка на отсутствующий T-40

**Дефект · Трассируемость · Низкая.** T-5 ссылается на отсутствующий T-40. T-6 задаёт точное сообщение для пустой дорожки, поэтому результат проверяем, а ссылка требует исправления.

Затронутые утверждения — [R-M0010-01](#r-m0010-01), [R-M0011-01](#r-m0011-01).

[R-M0010-01](#r-m0010-01) · Subtitle track export / Format · [строка 10](../../../../../benchmark/subtitles/requirements.md#L10)

> For an empty track, display the exact message listed in T-40  

[R-M0011-01](#r-m0011-01) · Subtitle track export / Format · [строка 11](../../../../../benchmark/subtitles/requirements.md#L11)

> The message for an empty track is “Add at least one cue”.  

**Сценарий.** При подготовке теста экспорта пустой дорожки проверяющий ищет сообщение по ссылке из T-5.

**Последствие.** Проверяющий не может перейти к указанному пункту, но может определить ожидаемый текст по T-6.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

Проект правки по [R-M0010-01](#r-m0010-01), [R-M0011-01](#r-m0011-01) — Направить ссылку на пункт, который задаёт точный текст сообщения для пустой дорожки.

**Черновик приёмочного теста.** Открыть исправленные пункты [R-M0010-01](#r-m0010-01), [R-M0011-01](#r-m0011-01) и проверить выполнение предложенной правки «Направить ссылку на пункт, который задаёт точный текст сообщения для пустой дорожки.».

## Готовность и порядок исправлений

ТЗ не готово к разработке. Сначала нужно согласовать требования к BOM и ожидаемый исход приёмочного примера.

1. Согласовать правило записи BOM с приёмочным тестом. (Z-001)
2. Согласовать исход приёмочного примера с правилом ограничения длины. (Z-004)
3. Уточнить, к какой величине относится объявленная единица временной отметки. (Z-002)
4. Задать наблюдаемый критерий приёмки лёгкости экспорта. (Z-003)
5. Исправить ссылку на требование с точным текстом сообщения. (Z-005)
