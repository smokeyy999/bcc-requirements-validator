## Проверка набора в целом

Нельзя однозначно принять загрузку сохранённых настроек, учёт покупки на границе месяца и уведомление после смены порога. Контракт сохранения задаёт разные HTTP-коды для отклонения суммы. Состав ответа при отклонении и детали передачи push требуют уточнения.

Открытых предполагаемых пробелов — 7. Неоднозначностей — 1. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Вопросы и рекомендации имеют отдельные счётчики.

## Вопросы к автору ТЗ

**В какой зоне указано 23:58 в критерии и какой месяц должен получить покупку, если обе метки заданы по Алматы?**

Блокирует приёмку · [Z-004](#z-004). Зависимый сценарий — Явно задать обе метки по Алматы и проверить, что на 4 000 ₸ вырос только согласованный счётчик, а возврат уменьшил тот же итог.

**Смена порога разрешает второй push в том же месяце или месячный максимум действует и после смены?**

Блокирует приёмку · [Z-008](#z-008). Зависимый сценарий — Проверить, остаётся ли число push равным одному или увеличивается до двух в указанном сценарии.

**Какой HTTP-код возвращается для целой суммы вне диапазона при остальных корректных параметрах?**

Блокирует приёмку · [Z-009](#z-009). Зависимый сценарий — Передать 999 и 1 000 001 ₸, проверить согласованный HTTP-код и предписанный для отклонённой суммы результат ERROR.

**Какой запрос читает порог и переключатель и что он возвращает для карты с настройкой и карты без неё?**

Блокирует приёмку · [Z-002](#z-002). Зависимый сценарий — Открыть экран для обеих карт, проверить согласованные ответы и убедиться, что чтение не изменило настройки.

**Входит ли время получения push клиентом в критерии приёмки? Если входит, каков предельный интервал и от какого события его измерять?**

Требует уточнения · [Z-001](#z-001). Зависимый сценарий — При достижении порога зафиксировать время передачи и получения push. Проверить минутный срок передачи и, если установлен предел получения, проверить его от согласованного события.

**Если позднее проведение по согласованному правилу доводит до порога расходы прошлого месяца, какой результат по push ожидается при этом достижении и при последующем достижении порога текущего месяца?**

Требует уточнения · [Z-005](#z-005). Зависимый сценарий — После согласования месяца учёта воспроизвести оба достижения, если покупка может увеличить итог прошлого месяца, и проверить ожидаемое число push.

**Какой результат ожидается при повторном достижении того же порога в том же месяце, если первый push передан на отправку, но не доставлен? Какое событие учитывается в месячном лимите?**

Требует уточнения · [Z-006](#z-006). Зависимый сценарий — Смоделировать недоставку первого push, возврат и повторное достижение порога. Проверить признак отправки и наличие второй передачи по согласованному правилу.

**Какой показатель и в какой единице должен получить сервис push при пересечении порога?**

Требует уточнения · [Z-007](#z-007). Зависимый сценарий — Провести покупку, при которой сумма операции, месячный итог и порог различаются. Сверить значение и единицу поля в запросе с согласованным контрактом.

**Какие поля обязательны в теле ответа при отклонении суммы? Должен ли ответ содержать прежний порог и состояние переключателя?**

Требует уточнения · [Z-010](#z-010). Зависимый сценарий — При сохранённых 50 000 ₸ и включённых уведомлениях отправить 999 ₸ с выключенным переключателем. Проверить согласованное тело ответа и сохранение прежней настройки.

**Применяется ли HTTP 403 к этому методу? Если да, при каком условии?**

Требует уточнения · [Z-013](#z-013). Зависимый сценарий — Если для метода предусмотрен HTTP 403, воспроизвести согласованное условие и проверить код ответа.

### R-M0163-01 · Неверно заполненные параметры дают HTTP 400.

Уведомление о расходах по карте / Часть B. REST API / Статусы · [строка 163](../docs/requirements.md#L163)

> \*\*400.\*\* Ответ в случае, если параметры запроса заполнены неверно.  

**Выявлено нарушение.** Для cardId указан строковый идентификатор карты клиента размером 1–64. Строковый тип сам по себе не обещает существования допустимого идентификатора из 64 многобайтовых символов. Для заявленного сценария сравнение исходов не обосновано. Для query-параметра enabled одновременно заданы «1 знак» и «0 или 1». Запись 01 нарушает ограничение размера, поэтому применим HTTP 400 для неверного параметра. Целочисленный тип не даёт основания игнорировать размер.

Связанные замечания — [Z-009](#z-009).

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ не готово к передаче в разработку в полном объёме. Для приёмки нужны контракт чтения и однозначные результаты по месяцу учёта, повторному push после смены порога и HTTP-коду при отклонении суммы.

1. Согласовать исходы на границе месяца и после смены порога. Описать запрос и ответ для чтения сохранённой настройки. (Z-004, Z-008, Z-002)
2. Согласовать HTTP-код и обязательные поля ответа при отклонении суммы, затем сверить примеры с контрактом. (Z-009, Z-010)
3. Уточнить показатель и единицу суммы для push, расходование лимита при недоставке и критерий своевременности получения. После выбора даты учёта определить применимость лимита к позднему проведению. (Z-007, Z-006, Z-001, Z-005)
4. Уточнить, при каком условии метод возвращает HTTP 403. (Z-013)
