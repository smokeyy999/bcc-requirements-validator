## Проверка набора в целом

Требования дают несовместимые результаты для BOM, минутной метки и реплики из 81 кодовой точки. Удобство экспорта не имеет критерия проверки. Ссылка на T-40 требует редакторского исправления. Сообщение «Add at least one cue» и сохранение состояния назначения уже заданы в T-6 и T-5.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · Наличие BOM в файле экспорта

**Дефект · Противоречивость · Критичная.** T-1 требует записать файл без BOM, а T-2 требует BOM в начале того же файла. Файл успешного экспорта не может пройти обе проверки.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку в локальный файл и проверить начало файла.

**Последствие.** Один и тот же файл нельзя принять по обоим требованиям.

**Общее условие.** Проверяются первые три байта файла, записанного при успешном экспорте дорожки. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку — с UTF-8 BOM или без него?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Считать файл прошедшим проверку BOM, если его первые три байта образуют UTF-8 BOM.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла равны EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Экспортировать дорожку, проверить начальные байты файла и применить выбранное правило.

### Z-002 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт миллисекунды для каждого поля временной метки. Для одной минуты это 60000, тогда как тот же пункт предписывает 1000. Однозначно принять экспорт временных меток невозможно.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute  

**Сценарий.** Экспортировать реплику с временной меткой ровно в одну минуту.

**Последствие.** Реализация и приёмочный тест могут ожидать разные числа в одном поле.

**Общее условие.** В одном поле экспорта записывается временная метка в одну минуту. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое значение должно пройти приёмку для минутной метки — 60000 или 1000?

1. **Вариант 1.** Числовое значение каждого поля временной метки выражается в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** В поле записано 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Числовое значение 1000 в поле временной метки обозначает одну минуту.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute».

   **Ожидаемый результат.** В поле записано 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать одну и ту же минутную метку и сравнить число в поле с выбранным значением.

<a id="z-003"></a>

### Z-003 · Критерий удобства экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как лёгкий каждым пользователем. Успешная запись файла подтверждает работу экспорта, а для оценки усилий отсутствует критерий успеха.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Проверяющий наблюдает успешный экспорт и оценивает, потребовал ли он усилий от пользователя.

**Последствие.** При одинаковых наблюдениях проверяющие могут вынести разные решения о выполнении T-4.

**Уже установлено.** Экспорт записывает открытую дорожку в локальный файл и должен восприниматься как лёгкий каждым пользователем. Основания — [R-M0009-01](#r-m0009-01), [R-M0003-02](#r-m0003-02).

**Открытое решение.** Какой критерий оценки усилий определяет успех для каждого пользователя?

**Что различит проверка.** Экспорт проходит проверку T-4, если зафиксированная оценка усилий каждого участника допустима по выбранному критерию. / Тот же экспорт не проходит проверку T-4, если по другому критерию хотя бы одна из тех же оценок недопустима.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой наблюдаемый результат и какое условие успеха подтверждают выполнение T-4?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Проверяющий наблюдает успешный экспорт и оценивает, потребовал ли он усилий от пользователя.».

**Черновик приёмочного теста.** Выполнить экспорт в согласованных условиях и оценить наблюдаемый результат по заданному критерию.

<a id="z-004"></a>

### Z-004 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** T-7 требует отклонить реплику с текстом длиннее 80 кодовых точек Unicode, а T-8 требует принять пример с 81 кодовой точкой. Для этой приёмочной проверки ожидаемый исход противоречив.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Экспортировать реплику из T-8, текст которой содержит 81 кодовую точку Unicode.

**Последствие.** Отклонение по T-7 приводит к провалу примера T-8, а принятие примера нарушает T-7.

**Общее условие.** На экспорт подаётся реплика из приёмочного примера с текстом длиной 81 кодовую точку Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход должен пройти приёмку для реплики из T-8 — принятие или отклонение?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Подать реплику из T-8 длиной 81 кодовую точку Unicode и проверить выбранный исход.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта по спорным правилам. Сначала нужно согласовать формат файла, шкалу меток и исход приёмочного примера, затем определить критерий удобства и исправить ссылку.

1. Согласовать наличие BOM и числовую шкалу временных меток с приёмочными проверками. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать предел длины с ожидаемым исходом для реплики из 81 кодовой точки Unicode. ([Z-004](#z-004))
3. Задать наблюдаемый критерий оценки усилий пользователя при экспорте. ([Z-003](#z-003))
4. Исправить внутреннюю ссылку на T-40. ([Z-005](#z-005))
