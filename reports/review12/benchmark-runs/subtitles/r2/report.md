Правила экспорта и приёмки расходятся по BOM, значению временной метки 1000 и допустимой длине реплики. Для лёгкости экспорта нужен наблюдаемый критерий. Ссылка T-40 требует редакторского исправления. Сообщение для пустой дорожки уже задано в T-6.

Открытых предполагаемых пробелов — 1. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в экспортируемом файле

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM в экспортируемом файле, а T-2 требует BOM в его первых трёх байтах. Один файл не может выполнить оба требования.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с короткой репликой и проверить начало локального файла.

**Последствие.** Файл, соответствующий T-1, провалит приёмочную проверку T-2. Добавление BOM нарушит T-1.

**Общее условие.** Приёмочный тест проверяет первые три байта файла успешного экспорта. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку — с UTF-8 BOM или без него?

1. **Вариант 1.** Записывать экспорт в UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет UTF-8 BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать экспорт в UTF-8 с BOM в первых трёх байтах.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла — EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Экспортировать одну и ту же непустую дорожку и проверить первые три байта файла на EF BB BF.

### Z-002 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт миллисекунды для каждого поля временной метки и одновременно приравнивает 1000 к минуте. Смысл экспортируемой метки 1000 при приёмке расходится на 59 секунд.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Проверить поле экспортированной временной метки со значением 1000 относительно одного и того же начала отсчёта.

**Последствие.** Одна и та же метка указывает на моменты, различающиеся на 59 секунд.

**Общее условие.** В экспортированном поле временной метки указано значение 1000. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой момент должно обозначать значение 1000 при приёмке — одну секунду или одну минуту от начала отсчёта?

1. **Вариант 1.** Интерпретировать каждое поле временной метки в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Значение 1000 указывает на одну секунду от начала отсчёта.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Сохранить соответствие значения 1000 одной минуте и согласовать с ним обозначение шкалы.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Значение 1000 указывает на одну минуту от начала отсчёта.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Сопоставить значение 1000 в экспортированном поле с ожидаемым моментом относительно того же начала отсчёта.

### Z-004 · Лимит длины реплики

**Дефект · Противоречивость · Критичная.** T-7 требует отклонить текст длиннее 80 кодовых точек Unicode, а T-8 требует принять реплику из 81 кодовой точки. Для приёмочного примера действуют взаимоисключающие исходы.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Проверить при экспорте реплику приёмочного примера с текстом длиной 81 кодовая точка Unicode.

**Последствие.** Соблюдение лимита даёт отказ на входе, который приёмочный пример требует принять.

**Общее условие.** При экспорте проверяется реплика приёмочного примера с текстом из 81 кодовой точки Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплику из 81 кодовой точки в приёмочном примере нужно отклонить или принять?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из 81 кодовой точки отклоняется.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в указанном приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из 81 кодовой точки принимается.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Подать реплику приёмочного примера с текстом из 81 кодовой точки Unicode и зафиксировать принятие или отказ.

### Z-003 · Критерий лёгкости экспорта

**Предполагаемый пробел · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как лёгкий каждым пользователем. Успешная запись файла проверяема, а для оценки пользовательского опыта в ТЗ отсутствует наблюдаемый критерий.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователь успешно экспортирует открытую дорожку в локальный файл. Проверяющий оценивает выполнение T-4.

**Последствие.** Даже при успешном экспорте проверяющие могут вынести разные решения по T-4.

**Уже установлено.** Экспорт сохраняет открытую дорожку в локальный файл. T-4 распространяет требование лёгкости на каждого пользователя. Основания — [R-M0009-01](#r-m0009-01), [R-M0003-02](#r-m0003-02).

**Открытое решение.** Определить наблюдаемый критерий, по которому результаты пользовательской проверки подтверждают выполнение T-4.

**Что различит проверка.** Зафиксированные результаты успешного экспорта удовлетворяют согласованному критерию лёгкости, и T-4 проходит приёмку. / Те же результаты успешного экспорта не удовлетворяют критерию лёгкости, и T-4 не проходит приёмку.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ пока не готово к разработке и приёмке экспорта. Сначала нужно согласовать обязательные исходы проверок файла, временной метки и реплики приёмочного примера.

1. Согласовать наличие BOM в экспортируемом файле и значение временной метки 1000. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать предел длины текста с ожидаемым исходом для реплики из 81 кодовой точки Unicode. ([Z-004](#z-004))
3. Задать наблюдаемый критерий лёгкости экспорта для пользовательской приёмки. ([Z-003](#z-003))
4. Исправить ссылку T-40 редакторской правкой. ([Z-005](#z-005))
