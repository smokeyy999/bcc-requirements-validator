Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. ### Z-009 · Второй push после смены порога

**Дефект · Противоречивость · Критичная.** Ф-3 ограничивает число push по карте. Ф-4 предписывает push при следующем достижении независимо от истории прежней настройки. При уже полученном push эти исходы взаимоисключающие.

[R-M0126-01](#r-m0126-01) · Уведомление о расходах по карте / Часть B. REST API / Особые правила · [строка 126](../../docs/requirements.md#L126)

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** Для включённого уведомления по карте уже получен push. В том же календарном месяце владелец повышает порог выше накопленной суммы и следующая покупка доводит расходы до нового порога.

**Последствие.** За месяц получится один либо два push по той же карте.

**Общее условие.** Включённое уведомление уже сработало по карте. В том же календарном месяце порог повышен выше сохранённой суммы, затем расходы достигают нового порога. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-01](#r-m0040-01) «При изменении порога накопленная сумма сохраняется.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При следующем достижении нового порога в этом месяце отправлять второй push или подавлять его?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после изменения порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если сохранённая сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая уже отправленный по ней push.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Клиент получает второй push за тот же месяц.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** Получить первый push, повысить порог, подтвердить сохранение суммы и провести покупку до нового порога. Проверить число уведомлений за месяц.

### Z-018 · Если у карт бывают многобайтные идентификаторы, в какой единице действует ограничение \`cardId\` от 1 до 64?

**Предполагаемый пробел · Полнота · Низкая.** Размер \`cardId\` задан без единицы. Тест с 64 кириллическими символами различает способы подсчёта только при поддержке таких идентификаторов.

Затронутые утверждения — [R-M0142-02](#r-m0142-02), [R-M0142-04](#r-m0142-04).

[R-M0142-02](#r-m0142-02) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [строка 142](../../docs/requirements.md#L142)

> \| \`cardId\` \| string \| 1–64 \|  

[R-M0142-04](#r-m0142-04) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [строка 142](../../docs/requirements.md#L142)

> \| \`cardId\` \| string \| 1–64 \| Да \| Карта клиента \| Идентификатор карты \| \`card\_id\` \|  

**Сценарий.** При подтверждённой поддержке такого ID взять существующую карту владельца с идентификатором из 64 кириллических символов. При остальных корректных параметрах проверить прохождение ограничения длины либо HTTP 400 за её нарушение.

**Что нужно уточнить.** Допускает ли формат существующих \`cardId\` идентификатор, который содержит 64 кириллических символа и занимает более 64 байтов в UTF-8.

**Как ответ изменит приёмку.** Если такой ID допустим, подсчёт символов пропускает его, а подсчёт байтов отклоняет. Если такой ID невозможен, этот тест неприменим.

**Уже установлено.** Для строкового идентификатора карты клиента указан размер 1–64. Неверные параметры дают 400. Поддержка кириллицы не установлена. Основания — [R-M0142-04](#r-m0142-04), [R-M0142-02](#r-m0142-02), [R-M0163-01](#r-m0163-01).

**Открытое решение.** Единица измерения длины при подтверждённой поддержке многобайтного ID.

**Что различит проверка.** Идентификатор из 64 символов проходит проверку длины. / Тот же идентификатор отклоняется с HTTP 400 из-за превышения 64 байтов.

## Готовность и порядок исправлений

ТЗ не готово к полной приёмке. Сценарий смены порога после первого push заблокирован до согласования ожидаемого результата. Для интеграции сначала нужно согласовать операции чтения и сохранения.

1. Согласовать число push после достижения нового порога в том же месяце. ([Z-009](#z-009))
2. Назначить HTTP-метод сохранения, допускающий замену настройки, и описать загрузку текущего порога и переключателя. ([Z-011](#z-011), [Z-003](#z-003))
