## Проверка набора в целом

Два противоречия блокируют приёмку существенных сценариев. Ф-3 и Ф-4 дают разное число push после повышения порога в том же месяце. Описанный GET требует заменить настройку вопреки семантике HTTP. Согласованность примера на стыке месяцев зависит от часового пояса отметки совершения покупки. Для интеграционных тестов нужны контракты чтения, источники данных и ответы на отклонённые запросы.

Открытых предполагаемых пробелов — 14. Неоднозначностей — 1. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-009](#z-009) · При расходах 50 000 ₸ после первого push повышение порога до 60 000 ₸ сохраняет итог. Покупка на 10 000 ₸ достигает нового порога в том же месяце. Ф-3 ограничивает карту одним push, а Ф-4 требует второй независимо от истории предыдущей настройки.

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** При включённых уведомлениях карта получила push на 50 000 ₸. В том же месяце клиент поднял порог до 60 000 ₸ при расходах 50 000 ₸ и провёл покупку на 10 000 ₸.

**Последствие.** Тест второй покупки имеет два несовместимых ожидаемых числа уведомлений.

**Общее условие.** Та же карта в том же календарном месяце уже получила push. Накопленная сумма после смены ниже нового порога, и следующая покупка достигает его. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.», [R-M0040-01](#r-m0040-01) «При изменении порога накопленная сумма сохраняется.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При втором достижении в этом месяце подавить push или отправить его?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, включая смену порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет. За месяц получен один push.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении 60 000 ₸ приходит второй push за месяц.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** После первого push повысить порог выше накопленной суммы, достичь нового порога и посчитать push.

**Уже установлено.** Признак хранится, а передача на отправку ограничена минутой. Получение клиентом описано отдельно. Основания — [R-M0049-06](#r-m0049-06), [R-M0039-02](#r-m0039-02), [R-M0039-03](#r-m0039-03), [R-M0046-01](#r-m0046-01).

**Открытое решение.** Событие, после которого хранимый признак показывает отправку.

**Что различит проверка.** Сразу после передачи на отправку признак установлен. / После передачи признак ещё не установлен и меняется при подтверждении отправки.

### Z-018 · Какой отдельный отказ доступа для этого метода, если он предусмотрен, должен возвращать 403?

**Предполагаемый пробел · Полнота · Низкая.** Слова «Для чужой карты возвращается 404» задают конкретный исход проверки принадлежности, совпадающий с исходом для отсутствующей карты. Для общего правила 403 остаётся вопрос о другом применимом запрете.

Затронутые утверждения — [R-M0175-01](#r-m0175-01), [R-M0189-02](#r-m0189-02).

[R-M0175-01](#r-m0175-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 200. Successful — Created · [строка 175](../../docs/requirements.md#L175)

> \*\*403.\*\* Ответ в случае, если на указанный ресурс доступ запрещен.  

[R-M0189-02](#r-m0189-02) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 403. Unsuccessful — Forbidden · [строка 189](../../docs/requirements.md#L189)

> Для чужой карты возвращается 404, как и для отсутствующей карты.  

**Сценарий.** Проверить одинаковый 404 для чужой и отсутствующей карты. Если для метода указан отдельный запрет, воспроизвести его и проверить 403.

**Что нужно уточнить.** Есть ли для метода отдельное условие запрета доступа после исключения случаев чужой и отсутствующей карты.

**Как ответ изменит приёмку.** При наличии отдельного запрета появляется самостоятельный сценарий 403. Без такого запрета проверяются два заданных исхода 404.

**Уже установлено.** Чужая и отсутствующая карты дают 404, отсутствие нужной авторизации даёт 401. Основания — [R-M0175-01](#r-m0175-01), [R-M0189-01](#r-m0189-01), [R-M0118-01](#r-m0118-01), [R-M0174-01](#r-m0174-01).

**Открытое решение.** Применимость 403 к отдельному запрету в этом методе.

**Что различит проверка.** Есть самостоятельный воспроизводимый запрос с 403. Для чужой и отсутствующей карты получен 404. / Самостоятельного сценария 403 для метода нет. Для чужой и отсутствующей карты получен 404.

### Z-019 · Как проверять предел 64 для cardId из 64 символов, занимающих более 64 байт, если такие идентификаторы выпускаются для карт?

**Предполагаемый пробел · Полнота · Низкая.** Для строкового cardId задан размер 1–64 без единицы. Разница между символами и байтами влияет на приёмку только при наличии поддерживаемых идентификаторов, для которых эти длины различаются.

[R-M0142-06](#r-m0142-06) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [строка 142](../../docs/requirements.md#L142)

> \| \`cardId\` \| string \| 1–64 \| Да \| Карта клиента \| Идентификатор карты \| \`card\_id\` \|  

[R-M0163-01](#r-m0163-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы · [строка 163](../../docs/requirements.md#L163)

> \*\*400.\*\* Ответ в случае, если параметры запроса заполнены неверно.  

**Сценарий.** Установить применимость многобайтного cardId к картам. Если доступна собственная карта с таким идентификатором, передать его с остальными допустимыми параметрами и проверить согласованный исход проверки длины.

**Что нужно уточнить.** Встречаются ли в поддерживаемых cardId идентификаторы из 64 символов, занимающих более 64 байт.

**Уже установлено.** cardId является строкой с пределом 64. Ни единица длины, ни применимость многобайтного случая не заданы. Основания — [R-M0142-06](#r-m0142-06), [R-M0142-02](#r-m0142-02), [R-M0163-01](#r-m0163-01).

**Открытое решение.** Единица проверки предела для поддерживаемого многобайтного cardId.

**Что различит проверка.** Идентификатор собственной карты из 64 символов проходит проверку длины. / Тот же идентификатор отклоняется с HTTP 400 из-за длины более 64 байт.

Уведомление о расходах по карте / Часть B. REST API / Статусы / 200. Successful — Created · [строки 170–172](../../docs/requirements.md#L170)

> "message":"Проверьте сумму"  

**Связано с вопросом к автору.** 999 ₸ вне диапазона, поэтому общее правило поддерживает 400. В разделе 200 есть пример с ERROR и сообщением о сумме, но его вход не указан. Для отклонённой суммы прежнее состояние и ERROR обязательны при любом согласованном статусе.

Связанные замечания — [Z-012](#z-012).

## Готовность и порядок исправлений

ТЗ пока не готово к разработке и приёмке затронутых сценариев. Сначала нужно согласовать поведение при повторном достижении порога и HTTP-операцию записи. Затем можно зафиксировать входы и ожидаемые результаты интеграционных тестов.

1. Согласовать число push при достижении нового порога после первого push месяца и выбрать совместимую с HTTP операцию обязательного сохранения. ([Z-009](#z-009), [Z-011](#z-011))
2. Указать часовой пояс времени совершения и сверить ожидаемый счётчик с Ф-2 после перевода времени в Алматы. ([Z-008](#z-008))
3. Уточнить загрузку обоих значений настройки, коды и проверку переключателя, HTTP-ответ при отклонении суммы и представление прежнего состояния. ([Z-001](#z-001), [Z-006](#z-006), [Z-012](#z-012), [Z-013](#z-013), [Z-020](#z-020))
4. Установить источники месячного итога, переключателя, трёх связей в учёте и последних цифр карты. Определить величину и единицу суммы для push. ([Z-002](#z-002), [Z-005](#z-005), [Z-007](#z-007), [Z-010](#z-010), [Z-003](#z-003))
5. Уточнить оценку срока получения push, момент установки признака отправки, применимость 403 и проверку длины cardId. Перенести пример 404 под соответствующий заголовок. ([Z-014](#z-014), [Z-015](#z-015), [Z-018](#z-018), [Z-019](#z-019), [Z-022](#z-022))
