## Проверка набора в целом

ТЗ задаёт экспорт открытой дорожки и поведение при пустой дорожке. Требования к BOM, шкале временных меток и реплике из 81 кодовой точки расходятся. Для оценки простоты экспорта нужен измеримый критерий, а ссылка на текст сообщения требует исправления.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM, а T-2 требует его в начале того же файла. Для обычного непустого экспорта единый ожидаемый результат невозможен.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку, содержимое которой в файле не начинается с U+FEFF.

**Последствие.** Реализация без BOM провалит приёмку, а добавление BOM нарушит формат записи.

**Общее условие.** Проверяются первые три байта экспортированного файла с непустым содержимым без начального U+FEFF. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат считать правильным при приёмке: файл с BOM или без него?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла не образуют BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Требовать UTF-8 BOM в первых трёх байтах файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла равны EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Экспортировать указанную дорожку и сравнить первые три байта с EF BB BF.

### Z-002 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 объявляет миллисекунды для самого поля и задаёт для его числового значения другое соответствие. Однозначного эталона приёмки временной метки нет.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать временную метку, установленную ровно на одну минуту от начала дорожки.

**Последствие.** Для метки нельзя задать единый числовой эталон приёмки.

**Общее условие.** В одном экспортируемом поле требуется представить временную метку в одну минуту. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое значение должно пройти приёмку для метки в одну минуту: 60000 или 1000?

1. **Вариант 1.** Выражать числовое значение каждой временной метки в объявленных миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** В поле записано 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Представлять одну минуту числовым значением 1000.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** В поле записано 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать дорожку с указанной меткой и сравнить числовое поле с выбранным эталоном.

### Z-003 · Критерий простоты экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как простой каждым пользователем, но не задаёт способ измерения и критерий успеха.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователь выполняет экспорт открытой дорожки в локальный файл и оценивает затраченные усилия.

**Последствие.** По наблюдениям нельзя однозначно подтвердить выполнение требования.

**Уже установлено.** Оценивается восприятие каждым пользователем экспорта одной открытой дорожки в локальный файл. Основания — [R-M0009-01](#r-m0009-01), [R-M0003-01](#r-m0003-01).

**Открытое решение.** Какой наблюдаемый критерий определяет успех для каждого пользователя?

**Что различит проверка.** При согласованной шкале простоты минимальная оценка 4 из 5 среди участников проходит при пороге 4 для каждого. / Те же оценки не проходят при пороге 5 для каждого.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какие наблюдаемые условия и порог определяют успешную проверку простоты экспорта?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователь выполняет экспорт открытой дорожки в локальный файл и оценивает затраченные усилия.».

**Черновик приёмочного теста.** Провести экспорт по согласованному сценарию и сравнить наблюдения с заданным порогом.

### Z-004 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** Общий лимит T-7 охватывает реплику из T-8. Пример требует принятия той же реплики без явно заданного исключения из лимита.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Проверить реплику из приёмочного примера, текст которой содержит 81 кодовую точку Unicode.

**Последствие.** Проверка лимита и приёмочный пример требуют взаимоисключающих результатов для одной реплики.

**Общее условие.** Воспроизводится приёмочный пример с репликой, текст которой содержит 81 кодовую точку Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход должен пройти приёмку для реплики из примера: отклонение или принятие?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из приёмочного примера с текстом из 81 кодовой точки Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Воспроизвести приёмочный пример и проверить решение по реплике.

## Готовность и порядок исправлений

ТЗ не готово к разработке с однозначной приёмкой. Сначала нужно согласовать формат файла и исход приёмочного примера для лимита реплики.

1. Согласовать наличие BOM и привести числовую шкалу временных меток в соответствие с объявленной единицей. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать решение по реплике из 81 кодовой точки между правилом и приёмочным примером. ([Z-004](#z-004))
3. Задать наблюдаемый критерий простоты экспорта и порог успеха. ([Z-003](#z-003))
4. Исправить в T-5 ссылку на T-6. ([Z-005](#z-005))
