## Проверка набора в целом

Ф-3 и Ф-4 дают разные результаты второго достижения порога в одном месяце. Обязательная запись настройки конфликтует с семантикой GET. Согласованность пограничного примера зависит от даты совершения покупки по Алматы. Для интеграционной приёмки остаются открыты составы ответов, источники значений и границы проверки push.

Открытых предполагаемых пробелов — 12. Неоднозначностей — 1. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-008](#z-008) · Ф-3 ограничивает число push за месяц по карте. Ф-4 требует push при следующем достижении повышенного порога независимо от истории прежней настройки. Приёмка второго достижения даёт взаимоисключающие результаты.
- [Z-012](#z-012) · Часть B объявляет GET и требует по этому вызову заменить настройку. По RFC 9110 § 9.2.1 GET безопасен. Здесь клиент запрашивает изменение ресурса, поэтому обязательную запись нельзя принять по объявленному HTTP-контракту.

### Z-008 · Повторный push после смены порога

**Дефект · Противоречивость · Критичная.** Ф-3 ограничивает число push за месяц по карте. Ф-4 требует push при следующем достижении повышенного порога независимо от истории прежней настройки. Приёмка второго достижения даёт взаимоисключающие результаты.

Затронутые утверждения — [R-M0039-03](#r-m0039-03), [R-M0040-01](#r-m0040-01), [R-M0040-02](#r-m0040-02).

[R-M0039-03](#r-m0039-03) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [строка 39](../../docs/requirements.md#L39)

> На карту приходится максимум один такой push за календарный месяц.  

[R-M0040-02](#r-m0040-02) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [строка 40](../../docs/requirements.md#L40)

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

[R-M0040-01](#r-m0040-01) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [строка 40](../../docs/requirements.md#L40)

> При изменении порога накопленная сумма сохраняется.  

**Сценарий.** Уведомления включены. Карта уже получила push при расходах 50 000 ₸. В том же календарном месяце клиент повышает порог до 60 000 ₸, затем проводится покупка на 10 000 ₸.

**Последствие.** Приёмка не может установить, должен ли клиент получить второй push.

**Общее условие.** Та же карта уже получила push в этом календарном месяце. После повышения порога сохранённая сумма ниже нового порога и затем достигает его в том же месяце. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-01](#r-m0040-01) «При изменении порога накопленная сумма сохраняется.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Должен ли прийти второй push при достижении повышенного порога в том же месяце?

1. **Вариант 1.** На карту приходится максимум один push о достижении порога за календарный месяц, в том числе после изменения порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** После второй покупки нового push нет. За месяц остаётся один push.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если при изменении порога накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** После второй покупки приходит push. За месяц их два.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** После первого push повысить порог, провести покупку до нового порога и проверить число push за месяц.

> 2. Повторное сохранение заменяет действующую настройку.  

**Внешнее основание.** Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. Побочные действия сервера, которых клиент не запрашивал, сами по себе допустимы. [RFC 9110 § 9.2.1 · Safe Methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)

**Сценарий.** У владельца активной KZT-карты сохранён порог 40 000 ₸. Клиент отправляет по объявленному маршруту допустимый GET с порогом 50 000 ₸.

**Последствие.** По логике ТЗ порог становится 50 000 ₸. При безопасной операции клиент своим запросом не должен инициировать эту замену.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

Проверяемое поведение — У владельца активной KZT-карты сохранён порог 40 000 ₸. Клиент отправляет по объявленному маршруту допустимый GET с порогом 50 000 ₸.

## Готовность и порядок исправлений

ТЗ требует согласования до начала разработки записи настроек и обработки повторного достижения порога. Основные правила расчёта расходов проверяемы. Для сквозной приёмки нужно уточнить контракты чтения, передачи push и ответов API.

1. Согласовать месячный лимит push после смены порога и выбрать HTTP-операцию обязательной записи. ([Z-008](#z-008), [Z-012](#z-012))
2. Привязать момент покупки в примере ко времени Алматы, сопоставить коды переключателя состояниям и определить величину и единицу суммы для push. ([Z-006](#z-006), [Z-005](#z-005), [Z-007](#z-007))
3. Указать контракт чтения для приложения и источники трёх значений у их потребителей, месячного итога, последних четырёх цифр карты и порога для сервиса расходов. ([Z-002](#z-002), [Z-003](#z-003), [Z-010](#z-010), [Z-011](#z-011))
4. Определить границу приёмки цели у клиента и событие фиксации признака отправки на стороне отправителя. ([Z-001](#z-001), [Z-009](#z-009))
5. Привязать примеры ошибок к входам, согласовать тела ответов для отклонённой и отсутствующей суммы и установить достижимый сценарий 403. ([Z-013](#z-013), [Z-015](#z-015), [Z-016](#z-016), [Z-020](#z-020))
6. Перенести правило, метку и тело 404 в подраздел 404. ([Z-021](#z-021))
