Требования к BOM и шкале временных меток расходятся в обязательных сценариях. Для смешанной дорожки требуется определить состояние файла, для приёмочного примера уточнить длину текста реплики, для лёгкости экспорта задать измеримый критерий. Открытых предполагаемых пробелов — 2. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

**Какой файл должна принять проверка начала файла, с BOM или без него?**

Блокирует приёмку · [Z-003](#z-003). Зависимый сценарий — Экспортировать ту же метку, сравнить записанное число с выбранным значением и сверить обозначение единицы с выбранной шкалой.

### Выбрать исправление для выявленного нарушения

Требует уточнения · [Z-001](#z-001). Зависимый сценарий — Подготовить файл с известным содержимым. Экспортировать в него смешанную дорожку, проверить отклонение длинной реплики и сверить содержимое файла с согласованным результатом.

**Сколько кодовых точек Unicode в тексте реплики из приёмочного примера T-8?**

Требует уточнения · [Z-004](#z-004). Зависимый сценарий — Подсчитать кодовые точки Unicode в тексте реплики из T-8. При длине до 80 включительно проверить приём реплики. При большей длине зафиксировать расхождение между требуемым отклонением и приёмом в примере.

### Z-002 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 требует записать экспортированный файл без BOM, а T-2 требует BOM в начале этого файла. Экспорт нельзя принять по обоим пунктам.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с короткой допустимой репликой и проверить начало файла.

**Последствие.** Для одного файла спецификация требует отсутствия BOM, а приёмка требует его наличия.

**Общее условие.** Проверяются первые байты файла, записанного при экспорте непустой дорожки с допустимой репликой. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должна принять проверка начала файла, с BOM или без него?

1. **Вариант 1.** Записывать UTF-8 без BOM и принимать файл без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** Файл не начинается с EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать UTF-8 с BOM и требовать его в первых трёх байтах.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Файл начинается с EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** После экспорта проверить первые три байта на EF BB BF согласно выбранному правилу.

### Z-003 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** Для поля с объявленной единицей в миллисекундах одна минута равна 60 000. T-3 для той же длительности задаёт 1000. Приёмка временной метки не может соблюсти оба условия.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать дорожку с временной меткой в одну минуту и прочитать соответствующее числовое поле.

**Последствие.** Реализации, следующие разным частям T-3, запишут разные числа для одной метки.

**Общее условие.** Экспортируется временная метка в одну минуту. Проверяется число в поле, для которого T-3 объявляет миллисекунды. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое число должна ожидать приёмка для метки в одну минуту, 60 000 или 1000?

1. **Вариант 1.** Число в каждом поле означает количество миллисекунд.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Поле содержит 60 000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Использовать шкалу, в которой 1000 означает одну минуту, и согласовать с ней обозначение единицы.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Поле содержит 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать ту же метку, сравнить записанное число с выбранным значением и сверить обозначение единицы с выбранной шкалой.

### Z-005 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как лёгкий каждым пользователем. Без измеримого критерия одинаковые оценки пользователей могут привести к разным итогам проверки.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Дать участникам одну задачу экспорта, измерить восприятие лёгкости по согласованной методике и проверить критерий для каждого участника.

**Последствие.** Проверяющие могут вынести разные итоги при одинаковых наблюдениях.

**Уже установлено.** Свойство заявлено для каждого пользователя. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Определить измеримый критерий восприятия лёгкости экспорта.

**Что различит проверка.** При оценке 4 из 5 у каждого участника и пороге 4 свойство принято. / При тех же оценках и пороге 5 свойство не принято.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому измеримому критерию определить, что экспорт воспринимается как лёгкий каждым пользователем?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Дать участникам одну задачу экспорта, измерить восприятие лёгкости по согласованной методике и проверить критерий для каждого участника.».

**Черновик приёмочного теста.** Дать участникам одну задачу экспорта, измерить восприятие лёгкости по согласованной методике и проверить критерий для каждого участника.

### Z-001 · Каким должно быть содержимое существующего файла после попытки экспорта дорожки с допустимой репликой и репликой, текст которой превышает 80 кодовых точек Unicode?

**Предполагаемый пробел · Полнота · Существенная.** T-7 требует отклонить длинную реплику. T-5 сохраняет файл при пустой дорожке. Состояние файла после экспорта смешанной дорожки не определено.

Затронутые утверждения — [R-M0003-01](#r-m0003-01), [R-M0014-01](#r-m0014-01).

[R-M0003-01](#r-m0003-01) · Subtitle track export · [строка 3](../../../../../benchmark/subtitles/requirements.md#L3)

> exports one open track to a local file  

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

**Сценарий.** Подготовить файл с известным содержимым. Экспортировать в него смешанную дорожку, проверить отклонение длинной реплики и сверить содержимое файла с согласованным результатом.

**Последствие.** T-7 требует отклонить длинную реплику. T-5 сохраняет файл при пустой дорожке. Состояние файла после экспорта смешанной дорожки не определено.

**Уже установлено.** Экспорт направлен в локальный файл, длинная реплика отклоняется. Сохранение файла явно задано для пустой дорожки. Основания — [R-M0003-01](#r-m0003-01), [R-M0014-01](#r-m0014-01), [R-M0010-02](#r-m0010-02).

**Открытое решение.** Определить состояние существующего файла после отклонения длинной реплики в смешанной дорожке.

**Что различит проверка.** Исходное содержимое файла сохраняется. / Файл содержит экспорт только допустимой реплики.

### Z-004 · Сколько кодовых точек Unicode в тексте реплики из приёмочного примера T-8?

**Предполагаемый пробел · Полнота · Существенная.** T-7 ограничивает длину текста, а T-8 указывает 81 кодовую точку для реплики. Для сопоставления правил нужна длина текста в самом примере.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Подсчитать кодовые точки Unicode в тексте реплики из T-8. При длине до 80 включительно проверить приём реплики. При большей длине зафиксировать расхождение между требуемым отклонением и приёмом в примере.

**Что нужно уточнить.** Неизвестно, превышает ли длина текста реплики из T-8 80 кодовых точек Unicode.

**Как ответ изменит приёмку.** При длине текста свыше 80 правила требуют разных исходов. При длине до 80 включительно приём совместим с лимитом.

**Уже установлено.** Пример требует принять реплику. Лимит требует отклонить реплику, если её текст длиннее 80 кодовых точек Unicode. Основания — [R-M0015-01](#r-m0015-01), [R-M0014-01](#r-m0014-01).

**Открытое решение.** Установить длину текста реплики в приёмочном примере.

**Что различит проверка.** Текст содержит до 80 кодовых точек включительно, ожидаемый приём согласуется с лимитом. / Текст содержит свыше 80 кодовых точек, ожидаемый приём расходится с обязательным отклонением.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке формата экспорта до согласования BOM и шкалы временных меток.

1. Согласовать наличие BOM и привести числовую шкалу временных меток в соответствие с обозначением единицы. ([Z-002](#z-002), [Z-003](#z-003))
2. Определить состояние файла для смешанной дорожки и проверить длину текста в примере T-8. Если она превышает лимит, согласовать ожидаемый исход примера с правилом. ([Z-001](#z-001), [Z-004](#z-004))
3. Задать измеримый критерий лёгкости экспорта для каждого пользователя. ([Z-005](#z-005))
4. Исправить внутреннюю ссылку T-40. ([Z-006](#z-006))
