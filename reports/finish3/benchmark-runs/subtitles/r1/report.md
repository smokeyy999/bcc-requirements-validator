## Проверка набора в целом

Условия приёмки расходятся по BOM, числу для минутной метки и исходу для реплики из 81 кодовой точки Unicode. Для лёгкости экспорта нужна измеримая мера. Ссылка T-40 требует редакторского исправления. Текст сообщения для пустой дорожки уже указан в T-6.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · Наличие BOM в файле

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM, а T-2 требует его в первых трёх байтах того же файла. Ни один файл не удовлетворяет обоим условиям приёмки экспорта.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с допустимой репликой в локальный файл.

**Последствие.** Для одного файла заданы несовместимые условия приёмки.

**Общее условие.** Проверяются первые три байта локального файла, полученного при успешном экспорте открытой дорожки. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Принимать файл с BOM или без BOM?

1. **Вариант 1.** Записывать дорожку в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** Файл начинается без BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Требовать UTF-8 BOM в первых трёх байтах экспортированного файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла образуют UTF-8 BOM.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Экспортировать одну и ту же дорожку и проверить первые три байта файла по выбранному правилу.

### Z-002 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 объявляет миллисекунды для каждого поля и задаёт число 1000 для одной минуты. В миллисекундах минута равна 60000, поэтому корректность экспортированной метки принять невозможно.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds;  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать дорожку с временной меткой в одну минуту и прочитать соответствующее числовое поле файла.

**Последствие.** Одна и та же метка должна получить два разных числа.

**Общее условие.** Проверяется числовое поле экспортированной метки в одну минуту. Объявление миллисекунд распространяется на каждое поле. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds;», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое значение принимать для минутной метки, 60000 или 1000?

1. **Вариант 1.** Выражать числовые значения временных меток в объявленных миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds;».

   **Ожидаемый результат.** Для минутной метки записано 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Кодировать минутную метку числом 1000 и согласовать объявленную единицу поля с этой шкалой.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Для минутной метки записано 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать минутную метку и сравнить число в файле с выбранным значением.

### Z-003 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует лёгкости экспорта для каждого пользователя, но не задаёт измеримого признака успеха. Проверить запись файла можно независимо от оценки удобства.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Два пользователя выполняют один и тот же экспорт и по-разному оценивают его лёгкость.

**Последствие.** По результатам наблюдения нельзя установить выполнение T-4.

**Уже установлено.** Лёгкость должна оцениваться для каждого пользователя, выполняющего экспорт. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Какой измеримый критерий устанавливает, что экспорт дался пользователю легко?

**Что различит проверка.** При пороге 4 из 5 результаты 4 и 5 проходят проверку для обоих пользователей. / При пороге 5 из 5 те же результаты не проходят проверку для пользователя с оценкой 4.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому измеримому критерию и на какой группе пользователей принимать требование T-4?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Два пользователя выполняют один и тот же экспорт и по-разному оценивают его лёгкость.».

**Черновик приёмочного теста.** Провести экспорт в согласованной группе и оценить результат по выбранному критерию.

### Z-004 · Приёмка реплики из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** Текст реплики из T-8 на одну кодовую точку превышает порог T-7. Общее правило требует отклонить реплику, а приёмочный пример требует принять её.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Подать на экспорт реплику из приёмочного примера с текстом длиной 81 кодовая точка Unicode.

**Последствие.** Одна и та же реплика должна быть одновременно принята и отклонена.

**Общее условие.** На экспорт подаётся реплика из приёмочного примера с текстом длиной 81 кодовая точка Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплику из приёмочного примера следует принять или отклонить?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из приёмочного примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из приёмочного примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Запустить экспорт с репликой из примера и проверить исход для этой реплики по выбранному правилу.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта по единому набору требований. Сначала нужно согласовать формат файла, шкалу меток и исход приёмочного примера.

1. Согласовать правило о BOM и привести объявленную единицу временных меток в соответствие с числовой шкалой. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать порог длины текста с ожидаемым исходом для реплики из приёмочного примера. ([Z-004](#z-004))
3. Задать измеримый критерий лёгкости экспорта и способ его проверки для пользователей. ([Z-003](#z-003))
4. Редакторски исправить ссылку T-40 и проверить её разрешимость. ([Z-005](#z-005))
