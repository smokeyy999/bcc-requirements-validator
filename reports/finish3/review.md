> При изменении порога накопленная сумма сохраняется.  

[R-M0126-01](#r-m0126-01) · Уведомление о расходах по карте / Часть B. REST API / Особые правила · [строка 126](../../docs/requirements.md#L126)

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** По карте с включённым уведомлением уже был push в текущем месяце. Владелец повышает порог выше накопленных расходов, затем проведённая покупка доводит расходы до нового порога в том же месяце.

**Последствие.** Ф-3 допускает всего один push, а Ф-4 требует второй.

**Общее условие.** По карте уже был push в этом месяце. Сохранённая сумма ниже нового порога, который достигается в том же месяце. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** После достижения нового порога в этом сценарии ожидается второй push или сохраняется максимум один за месяц?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, включая достижение изменённого порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет. За месяц по карте остаётся один push.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая отправку в том же месяце.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Приходит второй push по карте за тот же месяц.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** Зафиксировать первый push, повысить порог без сброса суммы, провести покупку до нового порога и проверить число push за этот месяц.

> 2. Повторное сохранение заменяет действующую настройку.  

**Внешнее основание.** Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. Побочные действия сервера, которых клиент не запрашивал, сами по себе допустимы. [RFC 9110 § 9.2.1 · Safe Methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)

**Сценарий.** Владелец активной карты KZT вызывает объявленный GET с допустимым порогом, отличным от сохранённого.

**Последствие.** По логике ТЗ сохранённый порог изменяется. Повторное сохранение с другим порогом снова меняет состояние.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

## Готовность и порядок исправлений

Документ частично готов к разработке. Сценарии учёта проведённых покупок, исключения переводов и передачи push в течение минуты можно проверять по источнику. Для полной приёмки нужны согласованные правила отправки, сохранения и отказа в доступе, а также ответы по оставшимся интеграционным сценариям.

1. Согласовать число push после смены порога и привести метод сохранения в соответствие с семантикой HTTP. ([Z-008](#z-008), [Z-010](#z-010))
2. Установить единый статус для запроса к чужой карте и согласовать его с общим правилом отказа в доступе. ([Z-011](#z-011))
3. Установить дату совершения покупки по Алматы, указать исходные запросы обоих примеров ошибок и определить представление прежней настройки при отклонении суммы. ([Z-006](#z-006), [Z-013](#z-013), [Z-015](#z-015))
4. Определить чтение порога и переключателя, источники месячной суммы, состояния уведомления и цифр карты, а также величину и единицу суммы для push. ([Z-003](#z-003), [Z-002](#z-002), [Z-005](#z-005), [Z-009](#z-009), [Z-007](#z-007))
5. Определить, входит ли срок получения push клиентом в приёмку, и отдельно указать событие фиксации признака отправки. ([Z-001](#z-001), [Z-004](#z-004))
6. Уточнить, возвращает ли метод 201 и при каком условии. ([Z-014](#z-014))
