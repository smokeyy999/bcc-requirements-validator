## Проверка набора в целом

Требования к BOM, шкале временных меток и субтитру из 81 кодовой точки задают несовместимые исходы. Для удобства экспорта нужен проверяемый критерий. Ссылка T-40 требует редакторского исправления. Сообщение для пустой дорожки уже задано в T-6.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в экспортируемом файле

**Дефект · Противоречивость · Критичная.** Для одного экспортированного файла T-1 исключает BOM, а T-2 требует его в первых трёх байтах. Принять экспорт по обоим пунктам невозможно.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с коротким ASCII-текстом и проверить начало файла.

**Последствие.** Один файл не может одновременно удовлетворить требованиям к записи и к приёмке.

**Общее условие.** Проверяются первые три байта UTF-8-файла, полученного при экспорте непустой дорожки с коротким ASCII-текстом. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат принять для этого файла: отсутствие BOM или BOM в первых трёх байтах?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать файл в UTF-8 с BOM в первых трёх байтах.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла равны EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Выгрузить дорожку и сравнить первые три байта файла с EF BB BF.

### Z-002 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт миллисекунды для каждого поля и соответствие одной минуты числу 1000. Для метки через минуту от начала отсчёта того же поля единица требует 60000. Одновременно принять оба значения невозможно.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать метку, отстоящую ровно на одну минуту от начала отсчёта своего поля.

**Последствие.** Чтение числа 1000 в объявленных миллисекундах даст одну секунду вместо одной минуты.

**Общее условие.** Проверяется числовое значение временной метки через одну минуту от начала отсчёта поля, для которого объявлены миллисекунды. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое значение должна содержать метка для одной минуты от начала отсчёта: 60000 или 1000?

1. **Вариант 1.** Записывать числовые значения временных меток в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Поле для одной минуты содержит 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** В числовом представлении временной метки одна минута соответствует 1000.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Поле для одной минуты содержит 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать метку на расстоянии одной минуты от начала отсчёта и сверить число в поле с выбранным представлением.

<a id="z-004"></a>

### Z-004 · Приём субтитра из 81 кодовой точки

**Дефект · Противоречивость · Критичная.** Текст субтитра в приёмочном примере превышает предел T-7. T-7 требует отклонения, а T-8 требует приёма. Проверку ограничения длины нельзя принять по обоим пунктам.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Выполнить приёмочный пример с субтитром, текст которого содержит 81 кодовую точку Unicode.

**Последствие.** Общее правило и приёмочный пример дают противоположные оценки одного результата проверки субтитра.

**Общее условие.** Проверяется субтитр из приёмочного примера, текст которого содержит 81 кодовую точку Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат должен дать приёмочный пример: отклонение или приём субтитра?

1. **Вариант 1.** Отклонять субтитр, если его текст превышает 80 кодовых точек Unicode, в том числе в приёмочном примере.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Субтитр отклонён.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** В приёмочном примере принимать субтитр с текстом из 81 кодовой точки Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Субтитр принят.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Предъявить субтитр из приёмочного примера и проверить, принят ли он.

<a id="z-003"></a>

### Z-003 · Критерий удобства экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как лёгкий каждым пользователем. При разных оценках успешного экспорта ТЗ не задаёт меры и порога для воспроизводимого вердикта.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Два пользователя успешно экспортируют одинаковую дорожку и по-разному оценивают требуемые усилия.

**Последствие.** Проверяющий не может вынести воспроизводимый вердикт по T-4.

**Уже установлено.** Экспорт должен восприниматься как лёгкий каждым пользователем. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Какой наблюдаемый критерий считать достаточным для подтверждения лёгкости экспорта у каждого участника проверки?

**Что различит проверка.** Согласованный критерий выполнен у обоих пользователей, проверка T-4 пройдена. / Согласованный критерий нарушен хотя бы у одного из тех же пользователей, проверка T-4 не пройдена.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** На каких пользователях, по какой наблюдаемой мере и с каким порогом следует проверять удобство экспорта?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Два пользователя успешно экспортируют одинаковую дорожку и по-разному оценивают требуемые усилия.».

**Черновик приёмочного теста.** Провести экспорт с указанными пользователями, измерить согласованный показатель и применить порог.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта до согласования формата файла, шкалы временных меток и результата проверки длины субтитра.

1. Установить единый исход для BOM, согласовать единицу временных меток с числовым соответствием и привести приёмочный пример в соответствие с правилом длины. ([Z-001](#z-001), [Z-002](#z-002), [Z-004](#z-004))
2. Задать наблюдаемую меру и порог для проверки удобства экспорта у каждого участника. ([Z-003](#z-003))
3. Исправить ссылку T-40 редакторски, опираясь на уже заданное сообщение для пустой дорожки. ([Z-005](#z-005))
