## Проверка набора в целом

Для BOM, минутной метки и реплики из 81 кодовой точки заданы несовместимые результаты. У требования к лёгкости экспорта отсутствует измеримый критерий. Ссылка T-40 требует редакторского исправления. Сообщение для пустой дорожки уже задано в T-6, а T-5 требует оставить назначение без изменений.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-001](#z-001) · T-1 запрещает BOM в экспортируемом файле, а T-2 требует его в первых трёх байтах того же файла. Принять формат экспорта по обоим критериям невозможно.
- [Z-002](#z-002) · T-3 задаёт миллисекунды для каждого поля временной метки и одновременно сопоставляет значение 1000 одной минуте. Для минутной метки в одном поле получаются два ожидаемых значения, поэтому её запись нельзя принять однозначно.
- [Z-004](#z-004) · Текст реплики из приёмочного примера превышает предел T-7. Правило требует отклонить её, а T-8 требует принятия, поэтому проверку ограничения по этому примеру нельзя принять однозначно.

### Z-001 · BOM в экспортируемом файле

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM в экспортируемом файле, а T-2 требует его в первых трёх байтах того же файла. Принять формат экспорта по обоим критериям невозможно.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспорт непустой дорожки с одной короткой репликой в новый локальный файл.

**Последствие.** У реализации и приёмочного теста несовместимые критерии для начала одного файла.

**Общее условие.** Правило записи и приёмочная проверка применяются к одному экспортированному файлу UTF-8. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат должна принять проверка начала файла: наличие или отсутствие BOM UTF-8?

1. **Вариант 1.** Экспорт записывает UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Приёмка требует BOM UTF-8 в первых трёх байтах.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла — EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Экспортировать дорожку из сценария и проверить первые три байта файла.

### Z-002 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт миллисекунды для каждого поля временной метки и одновременно сопоставляет значение 1000 одной минуте. Для минутной метки в одном поле получаются два ожидаемых значения, поэтому её запись нельзя принять однозначно.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** Экспорт реплики с временной меткой в одну минуту.

**Последствие.** В поле для одной и той же метки ожидаются разные числа.

**Общее условие.** В одном поле экспортируемой временной метки записывается значение для одной минуты. Обе части T-3 относятся к этому полю. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое число должна принять проверка метки в одну минуту: 60000 или 1000?

1. **Вариант 1.** Число в каждом поле временной метки выражает время в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** В поле записано 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Числовое значение 1000 в поле временной метки представляет одну минуту.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** В поле записано 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать реплику из сценария и сравнить число в поле с выбранным значением.

### Z-004 · Приёмка реплики из 81 кодовой точки

**Дефект · Противоречивость · Критичная.** Текст реплики из приёмочного примера превышает предел T-7. Правило требует отклонить её, а T-8 требует принятия, поэтому проверку ограничения по этому примеру нельзя принять однозначно.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Проверить при экспорте реплику из приёмочного примера с текстом длиной 81 кодовая точка Unicode.

**Последствие.** Отклонение, требуемое общим правилом, приводит к провалу приёмочного примера.

**Общее условие.** При экспорте проверяется реплика из приёмочного примера с текстом длиной 81 кодовая точка Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** В приёмочном примере реплику с текстом из 81 кодовой точки следует отклонить или принять?

1. **Вариант 1.** Отклонять реплику при длине текста свыше 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Unicode в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Выполнить экспорт с репликой из примера и проверить, принята она или отклонена.

<a id="z-003"></a>

### Z-003 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт казался лёгким каждому пользователю. Без наблюдаемого критерия разные оценки участников не дают воспроизводимого вердикта по этому свойству.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователи выполняют экспорт одной открытой дорожки и по-разному оценивают его лёгкость.

**Последствие.** По результатам проверки нельзя вынести воспроизводимый вердикт по T-4.

**Уже установлено.** Критерий лёгкости экспорта должен выполняться для каждого пользователя. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Какой наблюдаемый критерий считать достаточным для подтверждения лёгкости экспорта у каждого пользователя?

**Что различит проверка.** По одним и тем же наблюдениям каждый участник выполняет согласованный критерий, и T-4 проходит проверку. / При другом допустимом пороге те же наблюдения показывают, что хотя бы один участник не выполняет критерий, и T-4 не проходит проверку.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой наблюдаемый результат подтвердит лёгкость экспорта и как при проверке учесть требование о каждом пользователе?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователи выполняют экспорт одной открытой дорожки и по-разному оценивают его лёгкость.».

**Черновик приёмочного теста.** Провести экспорт в согласованных условиях и сопоставить наблюдаемый результат с заданным критерием.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта до согласования трёх обязательных результатов. Для приёмки лёгкости экспорта нужен измеримый критерий.

1. Согласовать наличие BOM, числовое значение минутной метки и исход для реплики из 81 кодовой точки. Синхронизировать требования и приёмочные проверки. ([Z-001](#z-001), [Z-002](#z-002), [Z-004](#z-004))
2. Задать воспроизводимый критерий лёгкости экспорта с учётом требования к каждому пользователю. ([Z-003](#z-003))
3. Исправить внутреннюю ссылку T-40 и проверить переход к действительному пункту. ([Z-005](#z-005))
