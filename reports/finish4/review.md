## Проверка набора в целом

Два обязательных сценария имеют несовместимые требования. Повторное достижение после смены порога одновременно требует и исключает второй push за месяц, а сохранение через GET требует запрошенной замены состояния. Пограничный пример учёта и пример HTTP 200 с ERROR требуют восстановления исходных условий. Для приёмки интеграций также нужны контракт чтения, источники значений и правила для оставшихся наблюдаемых результатов.

Открытых предполагаемых пробелов — 13. Неоднозначностей — 2. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. ### Z-011 · Второй push после смены порога

**Дефект · Противоречивость · Критичная.** После первого push повышение порога сохраняет расходы. При следующем достижении в том же месяце Ф-3 ограничивает результат одним push, а Ф-4 требует push «независимо от истории предыдущей настройки». Приёмка этого сценария невозможна.

Затронутые утверждения — [R-M0039-03](#r-m0039-03), [R-M0040-01](#r-m0040-01), [R-M0040-02](#r-m0040-02).

> На карту приходится максимум один такой push за календарный месяц.  

[R-M0040-02](#r-m0040-02) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [строка 40](../../docs/requirements.md#L40)

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

[R-M0040-01](#r-m0040-01) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [строка 40](../../docs/requirements.md#L40)

> При изменении порога накопленная сумма сохраняется.  

**Сценарий.** Клиент уже получил push по карте. В том же месяце он повышает порог выше текущих расходов, оставляет уведомление включённым и покупкой достигает нового порога.

**Последствие.** По Ф-3 за месяц остаётся один push. По Ф-4 клиент получает второй.

**Общее условие.** Для той же карты в том же календарном месяце после первого push порог изменён. Сохранённые расходы ниже нового порога, который затем достигнут при включённом уведомлении. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.», [R-M0040-01](#r-m0040-01) «При изменении порога накопленная сумма сохраняется.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход принять в этом сценарии — один push за месяц или второй push при достижении нового порога?

1. **Вариант 1.** После первого push действует предел в один push на карту за календарный месяц, в том числе после смены порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** При достижении нового порога второго push нет.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если расходы ниже нового порога, его следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении нового порога клиент получает второй push.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** После первого push повысить порог и провести покупку до его достижения. Посчитать полученные push по карте за тот же месяц.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке в полном объёме. Сначала нужно согласовать исход повторного достижения порога и метод сохранения. Остальные вопросы следует закрыть для соответствующих интеграционных и приёмочных сценариев.

1. Согласовать число push при повторном достижении в том же месяце и совместимый с HTTP метод сохранения. ([Z-011](#z-011), [Z-013](#z-013))
2. Восстановить момент совершения покупки и запрос примера HTTP 200 с ERROR. Отдельно определить смысл успеха для состава ответа 200. ([Z-007](#z-007), [Z-014](#z-014), [Z-017](#z-017))
3. Описать чтение настроек, источники признака включения, месячного итога и последних цифр карты, а также величину и единицу суммы в push. ([Z-002](#z-002), [Z-003](#z-003), [Z-004](#z-004), [Z-010](#z-010), [Z-012](#z-012))
4. Определить месяц ограничения push при позднем проведении и величину уменьшения месячного итога при возврате. ([Z-008](#z-008), [Z-009](#z-009))
5. Установить, входит ли срок получения клиентом в приёмку, и отдельно определить событие фиксации признака отправки. ([Z-001](#z-001), [Z-005](#z-005))
6. Уточнить поля ответов при отказе и условие 403. Поместить пример 404 под соответствующий заголовок. ([Z-015](#z-015), [Z-016](#z-016), [Z-020](#z-020), [Z-023](#z-023))
