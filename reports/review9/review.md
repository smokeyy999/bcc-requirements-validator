## Проверка набора в целом

Правила учёта покупок и полного возврата определяют исходный месяц. Конфликт месячного максимума и повторного достижения после смены порога блокирует приёмку этого сценария. Контракт сохранения нарушает семантику GET. Для сквозной приёмки остаётся определить контракты чтения и передачи данных, состав ответов и границы измерения push.

Открытых предполагаемых пробелов — 27. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-010 · Повторный push после смены порога

**Дефект · Противоречивость · Критичная.** На втором достижении в том же месяце Ф-3 запрещает второй push, а Ф-4 требует его независимо от истории настройки. Ожидаемый результат приёмки смены порога определить нельзя.

2. **Вариант 2.** Если расходы ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

<a id="r-m0037-05"></a>

### R-M0037-05 · Начальное состояние уведомления выключено.

Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [строка 37](../../docs/requirements.md#L37)

> По умолчанию уведомление выключено.  

**Связано с нарушением в спецификации.** В строке приёмки задан переход к порогу, но пропущены предусловия одного push. Для воспроизводимого испытания достаточно явно включить уведомление и задать отсутствие предыдущего push по карте в этом месяце. Чтение через REST API обещано. Описанный вызов предписывает замену и не задаёт контракт чтения. API допускает 0 и 1, но прямо не сопоставляет каждое значение с деловым состоянием. Выключенное состояние по умолчанию не задаёт его код. При отклонении суммы прежнее состояние и ERROR уже обязательны. **Связано с нарушением в спецификации.** Таблица задаёт строковый исход сохранения, а ERROR прямо обязателен при отклонении суммы. Явные коды 401, 403 и 500 помещены под заголовком 200, а правило 404 и его пример находятся под 403. Заголовки можно согласовать с явно указанными кодами.

## Готовность и порядок исправлений

ТЗ требует доработки перед общей приёмкой. Сценарий смены порога заблокирован до согласования результата. Пограничный пример месяца и пример HTTP 200 с ERROR оцениваются после установления их исходных данных.

1. Согласовать число push при повторном достижении после смены порога в том же месяце. ([Z-010](#z-010))
2. Согласовать HTTP-операцию сохранения, контракт чтения, источник идентификатора карты, заголовок и применимые адреса. Уточнить назначение метода в описании. ([Z-013](#z-013), [Z-003](#z-003), [Z-023](#z-023), [Z-024](#z-024), [Z-018](#z-018), [Z-017](#z-017))
3. Подготовить условия точного достижения, установить дату покупки в пограничном примере и согласовать правила частичного возврата и месячного максимума push. ([Z-004](#z-004), [Z-006](#z-006), [Z-008](#z-008), [Z-030](#z-030))
4. Закрепить входы учёта и настроек, значения кодов переключателя, источник итога для приложения и отображаемый период. ([Z-007](#z-007), [Z-025](#z-025), [Z-026](#z-026), [Z-029](#z-029), [Z-002](#z-002), [Z-028](#z-028), [Z-005](#z-005))
5. Определить данные запроса push, адресацию, границу проверки получения и событие записи признака отправки. ([Z-009](#z-009), [Z-012](#z-012), [Z-027](#z-027), [Z-001](#z-001), [Z-011](#z-011))
6. Дополнить контракты тел ответов, установить запрос для примера 200 с ERROR, подтвердить применимость 201 и 403 и привести заголовки в соответствие с кодами.
