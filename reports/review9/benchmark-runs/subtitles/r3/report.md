## Проверка набора в целом

Требования расходятся по BOM, значению временной метки 1000 и исходу проверки реплики из 81 кодовой точки. Для лёгкости экспорта нужен измеримый критерий. Ссылка на T-40 требует редакторской правки. Сообщение для пустой дорожки задано в T-6, а сохранение места назначения задано в T-5.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 требует записать файл без BOM, а T-2 требует BOM в первых трёх байтах того же файла. Результат экспорта нельзя принять по обоим правилам.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку в локальный файл.

**Последствие.** Один файл не может одновременно удовлетворить формату и приёмочному тесту.

**Общее условие.** Запись экспортированной дорожки и проверка первых трёх байтов полученного файла. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход считать правильным при приёмке: BOM отсутствует или занимает первые три байта файла?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла отсутствует BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Первые три байта файла должны составлять UTF-8 BOM.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла образуют BOM.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Выполнить экспорт и проверить первые три байта на UTF-8 BOM.

### Z-002 · Масштаб временной метки

**Дефект · Противоречивость · Критичная.** В объявленных миллисекундах значение 1000 соответствует одной секунде. T-3 приписывает той же записи одну минуту. Проверка временной метки даёт несовместимые результаты.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds;  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** В экспортированном поле временной метки, объявленном в миллисекундах, записано 1000.

**Последствие.** Для одной записи проверяющий получает две разные длительности.

**Общее условие.** В поле временной метки, для которого T-3 объявляет миллисекунды, записано 1000. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds;», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какую длительность должен подтвердить тест для значения 1000: одну секунду или одну минуту?

1. **Вариант 1.** Интерпретировать числовое значение поля в объявленных миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds;».

   **Ожидаемый результат.** Значение 1000 означает одну секунду.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Значение 1000 в поле означает одну минуту.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Значение 1000 означает одну минуту.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Прочитать значение 1000 из поля экспортированного файла и сверить его длительность с выбранным исходом.

### Z-003 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как лёгкий каждым пользователем. В ТЗ отсутствует наблюдаемый критерий прохождения этой проверки.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователи выполняют одинаковые действия экспорта и по-разному оценивают усилия.

**Последствие.** Проверяющие могут вынести разные решения по T-4 при одинаковом поведении редактора.

**Уже установлено.** Требование относится к восприятию экспорта каждым пользователем. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Какой измеримый критерий подтверждает лёгкость экспорта для заявленного охвата пользователей?

**Что различит проверка.** Наблюдения по согласованному сценарию удовлетворяют выбранному критерию, проверка T-4 пройдена. / Те же наблюдения не удовлетворяют другому выбранному критерию, проверка T-4 не пройдена.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой наблюдаемый критерий и какое условие прохождения теста подтверждают выполнение T-4 для заявленного охвата пользователей?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователи выполняют одинаковые действия экспорта и по-разному оценивают усилия.».

**Черновик приёмочного теста.** Выполнить экспорт по согласованному сценарию, измерить выбранный показатель и применить утверждённое условие прохождения.

### Z-004 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** Текст реплики из T-8 содержит 81 кодовую точку Unicode. T-7 требует отклонить эту реплику, а приёмочный пример требует её принять.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Проверить реплику из T-8 с текстом длиной 81 кодовая точка Unicode.

**Последствие.** Приёмочный пример и проверка ограничения требуют противоположных результатов для одной реплики.

**Общее условие.** Проверяется реплика из приёмочного примера T-8 с текстом длиной 81 кодовая точка Unicode. К её тексту применим предел T-7. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход должен проверять пример T-8: принятие или отклонение реплики?

1. **Вариант 1.** Отклонять реплику, если её текст длиннее 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать в приёмочном примере реплику из 81 кодовой точки Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Предъявить указанную в T-8 реплику из 81 кодовой точки Unicode и проверить решение по реплике.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта. Сначала нужно согласовать формат файла, масштаб временных меток и исход приёмочного примера на границе длины.

1. Согласовать наличие BOM и соответствие числовых временных меток объявленной единице. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать предел T-7 и ожидаемый исход для реплики из 81 кодовой точки в T-8. ([Z-004](#z-004))
3. Задать измеримый критерий прохождения проверки T-4 для заявленного охвата пользователей. ([Z-003](#z-003))
4. Исправить ссылку на отсутствующий пункт T-40. ([Z-005](#z-005))
