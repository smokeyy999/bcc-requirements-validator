## Проверка набора в целом

Ф-3 и Ф-4 задают взаимоисключающие результаты повторного достижения порога. API требует изменить настройку через GET. Для проверки уведомления нужны критерий своевременности получения и точное значение суммы в вызове. Интеграционные проверки зависят от уточнения чтения настроек, источников данных и отдельных веток ответа.

Открытых предполагаемых пробелов — 12. Неоднозначностей — 2. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** Уведомления включены. Карта уже получила push в этом месяце. Клиент повышает порог выше накопленной суммы, затем новой покупкой достигает его в том же месяце.

**Последствие.** Нельзя принять поведение при повторном достижении и проверить, как история отправок влияет на новую настройку.

**Общее условие.** Карта уже получила push в календарном месяце. Накопленная сумма ниже нового порога, который затем достигнут в том же месяце. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Что выбрать для второго достижения в этом сценарии: применить месячный максимум или отправить новый push по изменённому порогу?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после изменения порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второе достижение в том же месяце проходит без нового push.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая уже отправленный push в этом месяце.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Клиент получает второй push в том же месяце.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** После первого push сохранить повышенный порог, подтвердить прежний итог, провести покупку до нового порога и посчитать новые push.

### R-M0163-01 · Некорректные параметры запроса приводят к HTTP 400.

Уведомление о расходах по карте / Часть B. REST API / Статусы · [строка 163](../../docs/requirements.md#L163)

> \*\*400.\*\* Ответ в случае, если параметры запроса заполнены неверно.  

**Связано с нарушением в спецификации.** Размер «1 знак» поддерживает проверку исходной записи, а формат integer и набор 0 или 1 поддерживают проверку разобранного числа. Контракт не задаёт представление, к которому относится размер. 999 ₸ выходит за допустимый диапазон, поэтому правило для неверных параметров задаёт 400. У альтернативного примера ERROR под 200 отсутствует вход, который связал бы его с этим запросом.

Связанные замечания — [Z-020](#z-020), [Z-014](#z-014).

## Готовность и порядок исправлений

ТЗ не готово к полной разработке и приёмке сценариев уведомления и сохранения. Сначала нужно согласовать повторную отправку и исправить метод записи. Базовый расчёт расходов и срок передачи push на отправку уже можно проверять по документу.

1. Выбрать ожидаемое число новых push при повторном достижении в том же месяце после смены порога. (Z-011)
2. Согласовать HTTP-метод записи и описать чтение сохранённых порога и переключателя. (Z-013, Z-003)
3. Задать критерий срока получения push, значение и единицу суммы, источник цифр карты и способ получения и интерпретации переключателя. (Z-001, Z-004, Z-007, Z-008, Z-012)
4. Уточнить источник месячного итога для экрана, зону времени совершения в примере и данные для привязки возврата. (Z-002, Z-009, Z-010)
5. Согласовать применимость примера ERROR, состав ответа при отклонении суммы и обработку enabled=01. (Z-014, Z-015, Z-020)
6. Уточнить наличие отдельной ветки 403 и применимость пограничного теста cardId. (Z-017, Z-019)
