## Проверка набора в целом

Требования расходятся по BOM, шкале временных меток и исходу приёмочного примера с 81 кодовой точкой Unicode. Для лёгкости экспорта отсутствует измеримый критерий, а ссылка T-40 требует редакторского исправления.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в экспортируемом файле

**Дефект · Противоречивость · Критичная.** T-1 требует записать UTF-8 без BOM, а T-2 требует BOM в первых трёх байтах того же файла. Успешный экспорт нельзя принять по обоим правилам.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с одной короткой репликой.

**Последствие.** Для одного и того же файла заданы несовместимые результаты проверки первых трёх байтов.

**Общее условие.** Проверяются первые три байта файла, записанного при успешном экспорте дорожки. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку, с BOM в первых трёх байтах или без BOM?

1. **Вариант 1.** Записывать экспортируемую дорожку в UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать BOM UTF-8 в первые три байта экспортируемого файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла образуют BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** После экспорта прочитать первые три байта файла и проверить наличие BOM UTF-8 по выбранному правилу.

### Z-002 · Единица временной метки

**Дефект · Противоречивость · Критичная.** T-3 объявляет миллисекунды для каждого поля и прямо связывает значение 1000 с минутой. Преобразование шкалы не задано, поэтому корректность экспортированных временных меток по обоим правилам подтвердить нельзя.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Прочитать экспортированное поле временной метки с числовым значением 1000.

**Последствие.** Значение 1000 соответствует одной секунде по объявленной единице и одной минуте по явному правилу T-3.

**Общее условие.** Читается экспортированное поле временной метки со значением 1000 и объявленной единицей «миллисекунды». Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое время должно означать значение 1000 при приёмке, одну секунду или одну минуту?

1. **Вариант 1.** Числовые значения во всех полях временных меток выражать в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Метка 1000 означает одну секунду.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Сохранить соответствие значения 1000 одной минуте и согласовать с ним объявление единицы поля.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Метка 1000 означает одну минуту.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Прочитать поле со значением 1000 и проверить, какое время ему соответствует по выбранной шкале.

### Z-003 · Допустимая длина текста реплики

**Дефект · Противоречивость · Существенная.** T-7 требует отклонить текст длиннее 80 кодовых точек Unicode, а T-8 принимает реплику длиной 81 в приёмочном примере. Исключение для примера не задано. Конфликт блокирует проверку ограничения длины.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Выполнить экспорт с репликой из приёмочного примера, текст которой содержит 81 кодовую точку Unicode.

**Последствие.** T-7 требует отклонить реплику, поскольку 81 больше 80, а T-8 требует принять ту же реплику.

**Общее условие.** При экспорте проверяется реплика из приёмочного примера с текстом длиной 81 кодовая точка Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Реплику из приёмочного примера с текстом из 81 кодовой точки Unicode нужно принять или отклонить?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode, включая реплику из приёмочного примера.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика с текстом из 81 кодовой точки Unicode отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из приёмочного примера с текстом из 81 кодовой точки Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика с текстом из 81 кодовой точки Unicode принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Экспортировать дорожку с репликой из примера, подтвердить длину её текста в кодовых точках Unicode и проверить выбранный исход для этой реплики.

### Z-004 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт ощущался лёгким для каждого пользователя, но не задаёт измеримого критерия. Это мешает принять заявленное свойство при успешном экспорте.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователь успешно экспортирует открытую дорожку и оценивает свои усилия.

**Последствие.** По результатам испытания нельзя однозначно решить, выполнено ли требование T-4.

**Уже установлено.** Пользователь экспортирует открытую дорожку в локальный файл. Свойство лёгкости заявлено для каждого пользователя. Основания — [R-M0009-01](#r-m0009-01), [R-M0003-01](#r-m0003-01).

**Открытое решение.** Определить измеримый критерий лёгкости и порог его выполнения для каждого пользователя в заданных условиях.

**Что различит проверка.** В том же испытании наблюдаемый результат каждого участника удовлетворяет принятому критерию, и T-4 проходит приёмку. / В том же испытании тот же результат хотя бы одного участника выходит за допустимый порог по другому критерию, и T-4 не проходит приёмку.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому наблюдаемому критерию, порогу и условиям испытания следует принимать заявленную лёгкость экспорта для пользователей?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователь успешно экспортирует открытую дорожку и оценивает свои усилия.».

**Черновик приёмочного теста.** Выполнить экспорт в согласованных условиях и сопоставить наблюдаемый результат с заданным критерием успеха.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта. Сначала нужно согласовать формат файла и проверить ожидаемый исход примера на границе допустимой длины.

1. Согласовать правило BOM между форматом и приёмкой, затем привести объявленную единицу в соответствие со значением 1000. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать предел длины текста и ожидаемый исход приёмочного примера с 81 кодовой точкой Unicode. ([Z-003](#z-003))
3. Задать измеримый критерий, порог и условия приёмки лёгкости экспорта для каждого пользователя. ([Z-004](#z-004))
4. Исправить внутреннюю ссылку T-40. Сообщение для пустой дорожки задано в T-6. ([Z-005](#z-005))
