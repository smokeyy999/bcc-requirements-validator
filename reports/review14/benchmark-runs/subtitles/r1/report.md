### Z-002 · BOM в экспортированном файле

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM в экспортированном файле, а T-2 требует BOM в начале того же файла. Ни один вариант записи не позволяет принять формат.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Успешно экспортировать непустую дорожку и прочитать первые три байта файла.

**Последствие.** Один файл не может удовлетворить обоим требованиям.

**Общее условие.** Проверяются первые три байта файла успешного экспорта непустой дорожки. Основания — [R-M0006-02](#r-m0006-02) «in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл должен пройти приёмку, с BOM или без BOM?

1. **Вариант 1.** Записывать UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать BOM UTF-8 в первых трёх байтах файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла равны EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Экспортировать дорожку с допустимой репликой и проверить наличие EF BB BF в начале файла по выбранному правилу.

### Z-003 · Шкала временной метки

**Дефект · Противоречивость · Критичная.** Для одного поля T-3 задаёт миллисекунды, но приравнивает 1000 к минуте. При объявленной единице это одна секунда, поэтому формат времени нельзя принять.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** Прочитать значение 1000 в поле временной метки экспортированной реплики.

**Последствие.** Проверяющие получат отсчёты в одну секунду и в одну минуту для одного поля.

**Общее условие.** В экспортированном поле временной метки, объявленном в миллисекундах, записано значение 1000. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой отсчёт должен соответствовать значению 1000 при приёмке, одна секунда или одна минута?

1. **Вариант 1.** Числовые значения временных меток выражать в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Значение 1000 означает одну секунду.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Сохранить соответствие значения 1000 одной минуте и согласовать с ним объявленную единицу.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Значение 1000 означает одну минуту.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Декодировать поле со значением 1000 и проверить отсчёт вместе с объявленной единицей.

### Z-004 · Критерий простоты экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует простоты для каждого пользователя, но не задаёт наблюдаемую меру и порог успеха. Проверить сам факт экспорта это не мешает.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Пользователи выполняют один и тот же успешный экспорт и по-разному оценивают его простоту.

**Последствие.** Текст не позволяет вынести единый приёмочный вердикт.

**Уже установлено.** Простота заявлена для каждого пользователя, поэтому средняя оценка сама по себе не подтверждает требование. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Установить наблюдаемый критерий простоты для каждого пользователя в согласованных условиях экспорта.

**Что различит проверка.** При минимальной индивидуальной оценке 4 из 5 испытание проходит по критерию не ниже 4 у каждого. / При тех же результатах испытание не проходит по критерию 5 у каждого.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому наблюдаемому критерию и в каких условиях принимать требование о простоте экспорта?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Пользователи выполняют один и тот же успешный экспорт и по-разному оценивают его простоту.».

**Черновик приёмочного теста.** Выполнить экспорт в согласованных условиях и сопоставить результат с утверждённым критерием.

### Z-005 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** T-7 требует отклонить реплику из 81 кодовой точки, а T-8 требует принять её в примере. Исключение не задано. Расхождение блокирует приёмку порога, но не определение результата для реплик в пределах лимита.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Экспортировать реплику из приёмочного примера с текстом длиной 81 кодовую точку Unicode.

**Последствие.** Реализация порога отклонит реплику, которую приёмочный пример требует принять.

**Общее условие.** Экспортируется реплика приёмочного примера с текстом длиной 81 кодовую точку Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Должна ли реплика из 81 кодовой точки в приёмочном примере быть отклонена или принята?

1. **Вариант 1.** Отклонять реплику с текстом длиннее 80 кодовых точек Unicode, в том числе в приёмочном примере.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из 81 кодовой точки отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать указанную в приёмочном примере реплику из 81 кодовой точки Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из 81 кодовой точки принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Подать реплику из примера и проверить выбранный исход для этой реплики.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта как единого сценария. Сначала нужно согласовать формат файла, временную шкалу и исход приёмочного примера на границе лимита.

1. Согласовать правило BOM и соответствие числовых меток объявленной единице времени. ([Z-002](#z-002), [Z-003](#z-003))
2. Согласовать порог с ожидаемым исходом примера для 81 кодовой точки Unicode. ([Z-005](#z-005))
3. Определить судьбу файла и допустимой реплики после обязательного отклонения сверхдлинной. ([Z-001](#z-001))
4. Задать условия испытания и наблюдаемый критерий простоты для каждого пользователя. ([Z-004](#z-004))
5. Исправить ссылку T-40 без повторного согласования текста сообщения. ([Z-006](#z-006))
