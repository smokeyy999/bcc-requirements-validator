## Проверка набора в целом

ТЗ задаёт несовместимые результаты для BOM, временной метки в одну минуту и реплики из 81 кодовой точки Unicode. Лёгкость экспорта не имеет измеримого критерия приёмки. В T-5 отсутствует адресат ссылки T-40, а текст сообщения для пустой дорожки задан в T-6.

Открытых предполагаемых пробелов — 0. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-001 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 запрещает BOM в экспортированном файле, а T-2 требует BOM в первых трёх байтах этого файла. Приёмка формата заблокирована.

Затронутые утверждения — [R-M0006-01](#r-m0006-01), [R-M0007-01](#r-m0007-01).

[R-M0006-01](#r-m0006-01) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> T-1. Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> T-2. The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать непустую дорожку с допустимой репликой в новый локальный файл.

**Последствие.** Для одного файла заданы несовместимые требования к первым байтам.

**Общее условие.** Первые три байта файла, полученного при успешном экспорте дорожки. Основания — [R-M0006-01](#r-m0006-01) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат должна требовать приёмка: наличие BOM или его отсутствие?

1. **Вариант 1.** Записывать файл в UTF-8 без BOM.

   **Основание.** [R-M0006-01](#r-m0006-01) «T-1. Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** В начале файла нет UTF-8 BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Записывать UTF-8 BOM в первых трёх байтах файла.

   **Основание.** [R-M0007-01](#r-m0007-01) «T-2. The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла — EF BB BF.

   При выборе этого варианта привести в соответствие [R-M0006-01](#r-m0006-01).

**Черновик приёмочного теста.** Экспортировать дорожку и проверить первые три байта файла по выбранному правилу.

### Z-002 · Масштаб временной метки

**Дефект · Противоречивость · Критичная.** T-3 объявляет миллисекунды для каждого поля метки и сопоставляет 1000 с одной минутой. В том же поле одна минута в миллисекундах равна 60000, поэтому приёмка меток заблокирована.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> T-3. Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать реплику с временной меткой в одну минуту.

**Последствие.** Для одного поля приёмка будет ожидать либо 60000, либо 1000.

**Общее условие.** Одно поле экспортируемой временной метки со значением времени в одну минуту. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое значение должно быть в поле для одной минуты: 60000 по миллисекундной шкале или 1000 по заданному соответствию?

1. **Вариант 1.** Число в каждом поле временной метки выражает время в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «T-3. Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Числовое значение экспортированной метки равно 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Использовать шкалу, в которой числовое значение 1000 обозначает одну минуту, и согласовать с ней объявляемую единицу.

   **Основание.** [R-M0008-02](#r-m0008-02) «Each timestamp field declares milliseconds; the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Числовое значение экспортированной метки равно 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать реплику с меткой в одну минуту и сверить числовое значение и объявленную единицу по выбранной шкале.

### Z-003 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** T-7 требует отклонить реплику, текст которой превышает 80 кодовых точек Unicode. T-8 принимает реплику из 81 кодовой точки Unicode. Расхождение блокирует конкретный приёмочный пример.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> T-7. Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> T-8. In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Экспортировать дорожку с репликой из приёмочного примера, текст которой содержит 81 кодовую точку Unicode.

**Последствие.** Соблюдение предела приводит к провалу приёмочного примера.

**Общее условие.** Экспорт реплики из приёмочного примера с текстом длиной 81 кодовую точку Unicode. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой результат должен ожидать тест для указанной реплики: отклонение или принятие?

1. **Вариант 1.** Отклонять реплику, если её текст превышает 80 кодовых точек Unicode.

   **Основание.** [R-M0014-01](#r-m0014-01) «T-7. Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из приёмочного примера с текстом из 81 кодовой точки Unicode.

   **Основание.** [R-M0015-01](#r-m0015-01) «T-8. In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Экспортировать дорожку с исходной репликой из 81 кодовой точки и сверить, принята ли она.

### Z-004 · Критерий лёгкости экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт воспринимался как лёгкий каждым пользователем, но не задаёт измеримого критерия этого восприятия. Дефект касается приёмки заявленного свойства.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> T-4. The export experience must feel effortless to every user.  

**Сценарий.** Дать каждому участнику выполнить один и тот же экспорт, зафиксировать результат по согласованной мере и проверить порог отдельно для каждого участника.

**Последствие.** По результатам испытания нельзя однозначно принять или отклонить T-4.

**Уже установлено.** Требование относится к восприятию экспорта каждым пользователем. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Определить измеримый критерий успешной оценки лёгкости экспорта пользователем.

**Что различит проверка.** Результат каждого участника удовлетворяет критерию, и испытание пройдено. / Результат хотя бы одного участника выходит за установленный порог, и испытание не пройдено.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** По какому наблюдаемому критерию и порогу определять, что экспорт прошёл легко для каждого участника приёмочного испытания?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Дать каждому участнику выполнить один и тот же экспорт, зафиксировать результат по согласованной мере и проверить порог отдельно для каждого участника.».

**Черновик приёмочного теста.** Дать каждому участнику выполнить один и тот же экспорт, зафиксировать результат по согласованной мере и проверить порог отдельно для каждого участника.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке экспорта. Сначала нужно согласовать формат файла, шкалу меток и результат пограничного примера.

1. Согласовать наличие BOM и соответствие числового значения объявленной единице времени. ([Z-001](#z-001), [Z-002](#z-002))
2. Согласовать предел длины с ожидаемым результатом для реплики из 81 кодовой точки Unicode. ([Z-003](#z-003))
3. Задать измеримый критерий и порог лёгкости экспорта. ([Z-004](#z-004))
4. Исправить ссылку T-40 редакторской правкой. ([Z-005](#z-005))
