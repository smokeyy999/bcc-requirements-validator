## Проверка набора в целом

Требования к BOM и шкале временных меток противоречат приёмке экспорта. Порог длины расходится с обязательным примером. Для смешанной дорожки открыт результат записи, а для удобства экспорта отсутствует критерий приёмки. Сообщение для пустой дорожки задано в T-6, ссылка из T-5 требует исправления.

Открытых предполагаемых пробелов — 1. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-002 · BOM в начале файла

**Дефект · Противоречивость · Критичная.** T-1 исключает BOM, а T-2 требует его в первых трёх байтах того же файла. Формат обязательного экспорта невозможно принять по обоим правилам.

Затронутые утверждения — [R-M0006-02](#r-m0006-02), [R-M0007-01](#r-m0007-01).

[R-M0006-02](#r-m0006-02) · Subtitle track export / Format · [строка 6](../../../../../benchmark/subtitles/requirements.md#L6)

> Write the exported track in UTF-8 without a byte-order mark.  

[R-M0007-01](#r-m0007-01) · Subtitle track export / Format · [строка 7](../../../../../benchmark/subtitles/requirements.md#L7)

> The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.  

**Сценарий.** Экспортировать открытую дорожку с одной допустимой репликой в локальный файл.

**Последствие.** Проверка одного и того же файла требует противоположных результатов.

**Общее условие.** Экспорт открытой дорожки с допустимой репликой и проверка начала полученного файла. Основания — [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.», [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой файл принимать, с BOM или без BOM?

1. **Вариант 1.** Записывать дорожку в UTF-8 без BOM.

   **Основание.** [R-M0006-02](#r-m0006-02) «Write the exported track in UTF-8 without a byte-order mark.».

   **Ожидаемый результат.** Файл начинается без BOM.

   При выборе этого варианта привести в соответствие [R-M0007-01](#r-m0007-01).

2. **Вариант 2.** Первые три байта файла должны составлять BOM UTF-8.

   **Основание.** [R-M0007-01](#r-m0007-01) «The acceptance test requires the first three bytes to be a UTF-8 byte-order mark.».

   **Ожидаемый результат.** Первые три байта файла составляют BOM UTF-8.

   При выборе этого варианта привести в соответствие [R-M0006-02](#r-m0006-02).

**Черновик приёмочного теста.** Экспортировать дорожку и проверить первые три байта файла.

### Z-003 · Шкала временных меток

**Дефект · Противоречивость · Критичная.** T-3 задаёт миллисекунды для каждого поля и одновременно сопоставляет одной минуте число 1000. Для обязательного поля невозможно принять единую шкалу.

Затронутые утверждения — [R-M0008-01](#r-m0008-01), [R-M0008-02](#r-m0008-02).

[R-M0008-01](#r-m0008-01) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> Each timestamp field declares milliseconds  

[R-M0008-02](#r-m0008-02) · Subtitle track export / Format · [строка 8](../../../../../benchmark/subtitles/requirements.md#L8)

> the numeric value 1000 represents one minute.  

**Сценарий.** Экспортировать реплику с временной меткой в одну минуту и прочитать число в соответствующем поле файла.

**Последствие.** Для одной метки проверка ожидает два разных числа.

**Общее условие.** Поле экспортируемой временной метки со значением в одну минуту. Основания — [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds», [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какое число считать правильным для минутной метки, 60000 или 1000?

1. **Вариант 1.** Числовое значение каждого поля временной метки выражено в миллисекундах.

   **Основание.** [R-M0008-01](#r-m0008-01) «Each timestamp field declares milliseconds».

   **Ожидаемый результат.** Минутная метка записана как 60000.

   При выборе этого варианта привести в соответствие [R-M0008-02](#r-m0008-02).

2. **Вариант 2.** Число 1000 в поле временной метки соответствует одной минуте.

   **Основание.** [R-M0008-02](#r-m0008-02) «the numeric value 1000 represents one minute.».

   **Ожидаемый результат.** Минутная метка записана как 1000.

   При выборе этого варианта привести в соответствие [R-M0008-01](#r-m0008-01).

**Черновик приёмочного теста.** Экспортировать одну и ту же минутную метку и сравнить число в файле с выбранным ожидаемым значением.

### Z-004 · Критерий удобства экспорта

**Дефект · Проверяемость · Существенная.** T-4 требует, чтобы экспорт ощущался лёгким для каждого пользователя, но не задаёт наблюдаемый критерий успешности. Это мешает принять заявленное свойство удобства.

Затронутые утверждения — [R-M0009-01](#r-m0009-01).

[R-M0009-01](#r-m0009-01) · Subtitle track export / Format · [строка 9](../../../../../benchmark/subtitles/requirements.md#L9)

> The export experience must feel effortless to every user.  

**Сценарий.** Дать пользователям одну и ту же задачу экспорта и сопоставить их оценки.

**Последствие.** При разных оценках проверяющие могут вынести разные решения о приёмке по одним данным.

**Уже установлено.** T-4 распространяет свойство на каждого пользователя. Основания — [R-M0009-01](#r-m0009-01).

**Открытое решение.** Какой критерий приёмки подтверждает заявленное удобство экспорта?

**Что различит проверка.** Оценка 4 из 5 у каждого участника проходит при пороге 4 из 5 для каждого. / Те же оценки не проходят при пороге 5 из 5 для каждого.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой наблюдаемый результат подтверждает удобство экспорта и какой охват пользователей достаточен для приёмки T-4?

Внести ответ на этот вопрос в [R-M0009-01](#r-m0009-01) для сценария «Дать пользователям одну и ту же задачу экспорта и сопоставить их оценки.».

**Черновик приёмочного теста.** Провести согласованный сценарий экспорта с заданным охватом и оценить результат по утверждённому критерию.

### Z-005 · Реплика из 81 кодовой точки

**Дефект · Противоречивость · Существенная.** T-7 требует отклонить реплику из T-8, а пример требует её принять. Слова «In the acceptance sample» задают вход испытания без исключения из общего порога.

Затронутые утверждения — [R-M0014-01](#r-m0014-01), [R-M0015-01](#r-m0015-01).

[R-M0014-01](#r-m0014-01) · Subtitle track export / Export limits · [строка 14](../../../../../benchmark/subtitles/requirements.md#L14)

> Reject a cue when its text exceeds 80 Unicode code points.  

[R-M0015-01](#r-m0015-01) · Subtitle track export / Export limits · [строка 15](../../../../../benchmark/subtitles/requirements.md#L15)

> In the acceptance sample, a cue of 81 Unicode code points is accepted.  

**Сценарий.** Экспортировать реплику из приёмочного примера с текстом длиной 81 кодовая точка Юникода.

**Последствие.** Реализация порога T-7 провалит приёмочный пример T-8.

**Общее условие.** Экспорт реплики приёмочного примера с текстом длиной 81 кодовая точка Юникода. Основания — [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.», [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** В приёмочном примере реплику из 81 кодовой точки принять или отклонить?

1. **Вариант 1.** Отклонять реплику, если её текст длиннее 80 кодовых точек Юникода.

   **Основание.** [R-M0014-01](#r-m0014-01) «Reject a cue when its text exceeds 80 Unicode code points.».

   **Ожидаемый результат.** Реплика из приёмочного примера отклонена.

   При выборе этого варианта привести в соответствие [R-M0015-01](#r-m0015-01).

2. **Вариант 2.** Принимать реплику из 81 кодовой точки Юникода в приёмочном примере.

   **Основание.** [R-M0015-01](#r-m0015-01) «In the acceptance sample, a cue of 81 Unicode code points is accepted.».

   **Ожидаемый результат.** Реплика из приёмочного примера принята.

   При выборе этого варианта привести в соответствие [R-M0014-01](#r-m0014-01).

**Черновик приёмочного теста.** Выполнить экспорт на данных T-8 и проверить, принята ли реплика.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке по единому набору правил. Ожидаемые результаты для BOM, временных меток и примера с 81 кодовой точкой требуют согласования.

1. Согласовать наличие BOM и шкалу временных меток в требованиях к формату и приёмке. ([Z-002](#z-002), [Z-003](#z-003))
2. Согласовать порог длины с приёмочным примером из 81 кодовой точки. ([Z-005](#z-005))
3. Определить результат записи при экспорте дорожки с отклонённой репликой. ([Z-001](#z-001))
4. Задать наблюдаемый критерий удобства экспорта. ([Z-004](#z-004))
5. Исправить ссылку с T-40 на T-6. ([Z-006](#z-006))
