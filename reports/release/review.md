## Проверка набора в целом

Два подтверждённых конфликта затрагивают сохранение настройки и повторное достижение порога после её изменения. Пограничный пример месяца и пример ERROR требуют уточнения входов. Для интеграционной приёмки остаются открытыми контракт чтения, происхождение значений, состав ответов и измерение получения push.

Открытых предполагаемых пробелов — 13. Неоднозначностей — 2. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-009](#z-009) · После первого push и повышения порога новое достижение подпадает под оба правила. Ф-3 запрещает второй push в том же месяце, а Ф-4 требует его «независимо от истории предыдущей настройки». Число push в обязательном сценарии определить нельзя.
- [Z-012](#z-012) · Метод и пример выбирают GET, а логика требует запрошенной клиентом замены настройки. Это нарушает семантику GET из RFC 9110 § 9.2.1, поэтому обязательное сохранение нельзя принять по данному контракту.

### Z-009 · Второй push после смены порога

**Дефект · Противоречивость · Критичная.** После первого push и повышения порога новое достижение подпадает под оба правила. Ф-3 запрещает второй push в том же месяце, а Ф-4 требует его «независимо от истории предыдущей настройки». Число push в обязательном сценарии определить нельзя.

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

[R-M0126-01](#r-m0126-01) · Уведомление о расходах по карте / Часть B. REST API / Особые правила · [строка 126](../../docs/requirements.md#L126)

> Изменение порога сохраняет накопленные расходы.  

**Сценарий.** Уведомление включено. По карте уже пришёл push на пороге 50 000 ₸. В том же месяце владелец повышает порог до 60 000 ₸ при расходах 50 000 ₸, затем покупка доводит расходы до 60 000 ₸.

**Последствие.** Месячный предел оставляет один push. Следующее достижение после смены порога по другому правилу даёт второй push.

**Общее условие.** На включённой карте уже получен push в текущем месяце. Порог повышают выше сохранённого итога, затем покупка в том же месяце доводит итог до нового порога. Основания — [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-M0040-01](#r-m0040-01) «При изменении порога накопленная сумма сохраняется.», [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход выбрать после достижения нового порога в том же месяце, если по карте уже был push?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, включая смену порога.

   **Основание.** [R-M0039-03](#r-m0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** При достижении нового порога второго push нет.

   При выборе этого варианта привести в соответствие [R-M0040-02](#r-m0040-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-M0040-02](#r-m0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении нового порога приходит второй push за месяц.

   При выборе этого варианта привести в соответствие [R-M0039-03](#r-m0039-03).

**Черновик приёмочного теста.** Получить первый push, поднять порог выше накопленной суммы, достичь нового порога покупкой в том же месяце и подсчитать уведомления.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какую операцию следует вызывать для обязательного сохранения настройки?

### Z-019 · Может ли идентификатор карты из 64 символов, занимающий больше 64 байт после декодирования, входить в допустимый диапазон \`cardId\`?

**Предполагаемый пробел · Полнота · Низкая.** Размер \`cardId\` указан без единицы. Различие исходов имеет значение только для идентификатора карты, у которого число символов и байтов находятся по разные стороны границы.

Затронутые утверждения — [R-M0142-02](#r-m0142-02), [R-M0142-04](#r-m0142-04).

[R-M0142-02](#r-m0142-02) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [строка 142](../../docs/requirements.md#L142)

> \| \`cardId\` \| string \| 1–64 \|  

[R-M0142-04](#r-m0142-04) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [строка 142](../../docs/requirements.md#L142)

> \| \`cardId\` \| string \| 1–64 \| Да \| Карта клиента \| Идентификатор карты \|  

**Сценарий.** Если такой идентификатор может принадлежать карте владельца, отправить его с корректными остальными параметрами и проверить исход валидации длины по согласованной единице.

**Что нужно уточнить.** Неизвестно, может ли карта иметь идентификатор из 64 символов, занимающий больше 64 байт после декодирования.

**Как ответ изменит приёмку.** Для допустимого идентификатора такого вида проверка по символам пропускает его, а проверка по байтам отклоняет. При совпадении числа символов и байтов на допустимом алфавите различие отпадает.

**Уже установлено.** Нужен строковый идентификатор карты клиента размером от 1 до 64. Единица размера и алфавит не указаны. Основания — [R-M0142-02](#r-m0142-02), [R-M0142-04](#r-m0142-04), [R-M0163-01](#r-m0163-01).

**Открытое решение.** Проходит ли проверку длины граничный многобайтовый идентификатор, если он назначен карте?

**Что различит проверка.** Идентификатор проходит проверку длины при подсчёте 64 символов. / Идентификатор отклоняется по длине с 400 при подсчёте более 64 байт.

## Готовность и порядок исправлений

ТЗ требует доработки перед разработкой сохранения настроек и логики уведомлений после смены порога. Остальные сценарии можно прорабатывать по заданным правилам, фиксируя открытые условия интеграционных испытаний.
