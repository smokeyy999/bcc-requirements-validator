## Проверка набора в целом

ТЗ задаёт основное правило учёта и минутный интервал до передачи push. Приёмка смены порога блокируется конфликтом месячного лимита, а контракт записи требует согласования с семантикой HTTP. Для календарного примера вывод зависит от пояса времени совершения покупки. Приёмка срока получения клиентом и событие фиксации признака отправки требуют независимых решений.

Открытых предполагаемых пробелов — 10. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-004 · Месячный лимит после смены порога

**Дефект · Противоречивость · Критичная.** Для второго достижения на той же карте в том же месяце Ф-3 ограничивает итог одним push, а Ф-4 требует отправки независимо от истории предыдущей настройки. Ожидаемое число уведомлений для приёмки смены порога не определено.

> проверка порога → при достижении отправка push  

**Сценарий.** Уведомление включено. Карта уже получила push в этом месяце при расходах 50 000 ₸. Клиент повышает порог до 60 000 ₸, затем проведённая покупка доводит итог до 60 000 ₸ в том же месяце.

**Последствие.** По Ф-3 за месяц остаётся один push, по Ф-4 их становится два.

**Общее условие.** Карта уже получила push в этом месяце. Сохранённые расходы ниже повышенного порога, затем покупка достигает нового порога в том же месяце. Основания — [R-P001L0039-02](#r-p001l0039-02) «На карту приходится максимум один такой push за календарный месяц.», [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При новом достижении в этом сценарии должен прийти второй push или действует лимит по карте?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после смены порога.

   **Основание.** [R-P001L0039-02](#r-p001l0039-02) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет. За месяц один push.

   При выборе этого варианта привести в соответствие [R-P001L0040-02](#r-p001l0040-02).

2. **Вариант 2.** Если сохранённые расходы ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При новом достижении приходит второй push за месяц.

   При выборе этого варианта привести в соответствие [R-P001L0039-02](#r-p001l0039-02).

**Черновик приёмочного теста.** После первого push повысить порог и провести покупку до нового порога в том же месяце. Сверить число push.

**Внешнее основание.** Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. **Сценарий.** С действительной сессией владельца активной карты KZT вызвать объявленный GET с допустимым порогом, отличным от сохранённого.

**Последствие.** По логике метода настройки должны измениться. Это запрошенное клиентом изменение ресурса через безопасный метод.

> Dev: \`/alerts/saveLimit\` . Prod: —  

**Сценарий.** Проверить маршрут Dev по заданному пути. При включении Prod в приёмку выполнить проверку маршрута и по указанному адресу Prod.

**Что нужно уточнить.** Включение Prod в приёмку поставки.

**Как ответ изменит приёмку.** Dev проверяется в обеих ветвях. Включение Prod добавляет проверку маршрута и требует адреса.

**Уже установлено.** Для Dev указан путь. Для Prod в строке адреса стоит прочерк. Основания — [R-P003L0007-01](#r-p003l0007-01), [R-P003L0008-01](#r-p003l0008-01).

**Открытое решение.** Определить, требуется ли проверка маршрута в Prod для приёмки поставки.

**Что различит проверка.** Успешной проверки маршрута Dev достаточно для проверки окружений. / При том же результате Dev требуется также успешная проверка маршрута по адресу Prod.

## Готовность и порядок исправлений

К полной разработке и приёмке ТЗ не готово. Сначала нужны однозначные правила повторного push после смены порога и записи настроек. Затем можно зафиксировать ожидаемые результаты отказов и сквозных проверок.

1. Разрешить случай повторного достижения после смены порога и согласовать HTTP-метод сохранения с заменой настройки. ([Z-004](#z-004), [Z-012](#z-012))
2. Согласовать статусы и примеры отказов, определить чтение текущей настройки и сопоставить коды enabled состояниям переключателя. ([Z-013](#z-013), [Z-014](#z-014), [Z-011](#z-011), [Z-003](#z-003))
3. Указать пояс времени совершения в приёмочном примере и правило расчёта вычета при возврате. ([Z-006](#z-006), [Z-007](#z-007))
4. Задать сумму в вызове push и проследить источники четырёх цифр карты и месячного итога до их потребителей. ([Z-008](#z-008), [Z-010](#z-010), [Z-002](#z-002))
5. Определить участие срока получения в приёмке и отдельно согласовать событие фиксации отправки. ([Z-001](#z-001), [Z-009](#z-009))
6. Определить, входит ли Prod в приёмку, и при необходимости указать адрес метода. ([Z-016](#z-016))
