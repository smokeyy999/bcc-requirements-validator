## Проверка набора в целом

Основные правила учёта заданы. Для испытания первого push нужно подтвердить начальное состояние переключателя. Ф-3 и Ф-4 расходятся при повторном достижении после повышения порога. Сохранение через GET нарушает семантику HTTP. Для интеграционной приёмки нужно уточнить чтение настроек, ответы отказа и данные для экрана и push. Минутный срок передачи задан. Приёмка срока получения клиентом и событие записи признака отправки требуют отдельных решений.

Открытых предполагаемых пробелов — 14. Неоднозначностей — 0. Рекомендаций — 0.

Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. ### Z-010 · Второй push после смены порога

**Дефект · Противоречивость · Критичная.** После первого push повышение порога сохраняет накопленные расходы. При следующем достижении в том же месяце Ф-3 допускает только один push за месяц, а Ф-4 требует второй. Приёмка уведомления после изменения порога заблокирована.

> При изменении порога накопленная сумма сохраняется.

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

**Сценарий.** При включённой настройке карта уже получила push при достижении 50 000 ₸. В том же месяце владелец повышает порог до 60 000 ₸ при накопленных 50 000 ₸ и проводит покупку на 10 000 ₸.

**Последствие.** Ф-3 ограничивает месячный итог одним push. Ф-4 требует push при новом достижении, поэтому итог составит два.

**Общее условие.** Уведомления включены. По карте уже получен push за месяц, накопленная сумма 50 000 ₸ сохраняется после повышения порога до 60 000 ₸, следующая покупка на 10 000 ₸ достигает нового порога в том же месяце. Основания — [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.», [R-D0019-01](#r-d0019-01) «При изменении порога накопленная сумма сохраняется.», [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** После второго достижения в том же месяце должен остаться один push или должен прийти второй?

1. **Вариант 1.** Применять месячный максимум на карту и после смены порога.

   **Основание.** [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** После второй покупки остаётся один push за месяц.

   При выборе этого варианта привести в соответствие [R-D0019-02](#r-d0019-02).

2. **Вариант 2.** Если расходы ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** После второй покупки получено два push за месяц.

   При выборе этого варианта привести в соответствие [R-D0018-03](#r-d0018-03).

**Черновик приёмочного теста.** Зафиксировать первый push, сохранить повышенный порог, проверить сохранение накопленной суммы, достигнуть нового порога и посчитать push по карте за месяц.

> 5. При отклонении суммы вернуть прежнее состояние и результат ERROR.  

**Сценарий.** Сохранить известные порог и состояние переключателя, затем из действующей сессии передать amount=999 для той же карты с допустимым переключателем. Проверить 400 и ERROR, извлечь из ответа оба прежних значения по согласованной структуре и сравнить с сохранёнными.

**Последствие.** При отклонении суммы прежняя настройка возвращается вместе с ERROR. Поле amount описано для успеха, а пример ERROR без входа не определяет структуру ответа на отклонение суммы.

**Уже установлено.** При отклонении суммы возвращаются прежний порог, прежнее состояние переключателя и ERROR. Основания — [R-D0043-01](#r-d0043-01), [R-T007R0003-02](#r-t007r0003-02), [R-T007R0004-02](#r-t007r0004-02), [R-D0065-01](#r-d0065-01).

**Открытое решение.** Как представить оба прежних значения в ответе этой ветви.

**Что различит проверка.** Оба прежних значения извлекаются из предназначенных для отказа полей верхнего уровня. / Оба прежних значения извлекаются из вложенного объекта прежней настройки.

### R-D0076-01 · В примере после отметки 404 \`message\` равен «Карта не найдена».

Уведомление о расходах по карте / Часть B. REST API / Статусы / 403. Unsuccessful — Forbidden · [DOCX, абзац 76](../docx/requirements-copy.docx)

> \{"message":"Карта не найдена"\}  

**Нарушений не выявлено.** Явная отметка 404 перед телом согласуется с фразой «Для чужой карты возвращается 404, как и для отсутствующей карты». Заголовок 403 вызывает навигационное расхождение. Для отсутствующей карты статус определён. При сквозной проверке это утверждение исключено из оснований замечания. Строки явно задают коды 401, 403 и 500, а правило для чужой и отсутствующей карты связывает их ответ с 404. Перенос под соответствующие заголовки упростил бы поиск, но документ не требует такого размещения.

Основания для снятия замечания — [R-D0074-01](#r-d0074-01), [R-D0074-02](#r-d0074-02).

## Готовность и порядок исправлений

ТЗ частично готово к разработке. Приёмка повторного достижения заблокирована до согласования Ф-3 и Ф-4. Для испытания первого push нужно подтвердить состояние переключателя. До фиксации интеграционного контракта нужно согласовать метод сохранения, чтение настроек и представление прежних значений при отказе.

1. Согласовать месячный предел push после изменения порога и закрепить исход повторного достижения. ([Z-010](#z-010))
2. Согласовать HTTP-метод сохранения, контракт чтения и ответы отказа. Привязать оба примера ошибок к их входам. ([Z-013](#z-013), [Z-003](#z-003), [Z-017](#z-017), [Z-015](#z-015), [Z-016](#z-016))
3. Подтвердить дату совершения пограничной покупки по Алматы и область правила для частичного возврата. ([Z-007](#z-007), [Z-008](#z-008))
4. Установить источники месячного итога, состояния включения и цифр карты. Закрепить смысл кодов переключателя, сумму и её единицу в передаче push. ([Z-002](#z-002), [Z-005](#z-005), [Z-006](#z-006), [Z-009](#z-009), [Z-012](#z-012))
5. Определить, входит ли срок получения клиентом в приёмку, и отдельно закрепить событие записи признака отправки. ([Z-001](#z-001), [Z-011](#z-011))
6. Подтвердить начальное состояние переключателя в приёмочном испытании первого push. ([Z-004](#z-004))
