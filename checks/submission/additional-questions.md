# Какие дополнительные вопросы передать автору ТЗ

В отчёте 16 карточек и 16 вопросов. Основная сверка разбирает восемь карточек, включая четыре засчитанных нарушения. Ниже рассмотрены остальные восемь. У каждого из этих вопросов в отчёте стоит отметка «Требует уточнения». Единственный блокирующий вопрос относится к повторному push. [Вопросы из отчёта](../../reports/submission/review.md#questions) · [Сверка основных решений](review-check.md)

| Что проверить | Оценка приоритета | Обоснование и вопрос к автору |
|---|---|---|
| Месячный итог на экране | Запросить для интеграционного теста | Поле `amount` в успешном ответе содержит сохранённый порог. На экране отдельно показывается сумма расходов. По каким данным приложение получает итог выбранной карты за месяц и с чем QA сверяет его после проведённой покупки? [Экран](../../docs/requirements.md#L29) · [Пересчёт](../../docs/requirements.md#L34) · [Поле ответа](../../docs/requirements.md#L156) · [Z-002](../../reports/submission/review.md#z-002) |
| Признак включения при достижении порога | Обсудить вместе с соответствием 0 и 1 | Настройки хранят признак включения. В схеме обработки покупки явно показано получение порога. Стоит уточнить, доступно ли сервису расходов также действующее состояние переключателя. Пользовательский тест может сравнить две карты с одинаковыми порогами при включённых и выключенных уведомлениях. [Значение по умолчанию](../../docs/requirements.md#L37) · [Обмен с настройками](../../docs/requirements.md#L43) · [Параметр](../../docs/requirements.md#L144) · [Z-007](../../reports/submission/review.md#z-007) |
| Значения 0 и 1 для переключателя | Достаточно короткого подтверждения | Контракт принимает числа 0 и 1, возвращает строки и показывает успешный пример со значением «1». Соответствие чисел состояниям экрана в тексте пропущено. Одной таблицы «значение в запросе → сохранённое состояние → переключатель на экране» достаточно для приёмки обоих значений. Вопрос о формате записи значения разобран отдельно. [Запрос](../../docs/requirements.md#L144) · [Ответ](../../docs/requirements.md#L157) · [Пример](../../docs/requirements.md#L167) · [Z-008](../../reports/submission/review.md#z-008) |
| Привязка возврата к исходной покупке | Запросить для интеграционного теста | Месяц уменьшения расходов уже определён. Нужны доступные поля события возврата и способ установить исходную покупку. Тогда QA может оформить возврат в следующем месяце и повторить доставку того же события, проверив, что сумма уменьшилась один раз. [Ф-2](../../docs/requirements.md#L38) · [Хранимые данные](../../docs/requirements.md#L49) · [Повторная доставка](../../docs/requirements.md#L52) · [Z-010](../../reports/submission/review.md#z-010) |
| Последние четыре цифры карты в push | Объединить с обсуждением состава сообщения | Передача четырёх цифр задана. Из контракта `cardId` неизвестно, может ли сервис расходов получить из него нужные цифры. В разговоре о содержимом push достаточно запросить источник этого поля и контрольный пример. [Состав вызова](../../docs/requirements.md#L43) · [Идентификатор карты](../../docs/requirements.md#L142) · [Z-012](../../reports/submission/review.md#z-012) |
| Время получения push на телефоне | Уточнить при согласовании отдельного норматива доставки | Уже можно измерять обязательную минуту между получением события сервисом и передачей push на отправку. Цель о своевременном уведомлении не задаёт предела для доставки на устройство. Если команда принимает и этот этап, стоит согласовать начало измерения, событие получения и допустимое время. [Цель](../../docs/requirements.md#L23) · [Уведомление клиента](../../docs/requirements.md#L39) · [Норматив сервиса](../../docs/requirements.md#L46) · [Z-001](../../reports/submission/review.md#z-001) |
| Применимость 403 | Уточнить у владельца API | Для чужой и отсутствующей карты уже предписан одинаковый ответ 404. Заголовок 403 над этим правилом затрудняет чтение. Нужен отдельный сценарий запрета, если он действительно предусмотрен. Можно уточнить документацию, сохранив установленную проверку 404. [Общее описание 403](../../docs/requirements.md#L175) · [Правило доступа к карте](../../docs/requirements.md#L189) · [Z-017](../../reports/submission/review.md#z-017) |
| Длина идентификатора карты | Низкий приоритет, зависит от допустимого алфавита | Для строки `cardId` указана длина 1–64. Сначала нужен существующий контракт идентификаторов. Если допустимый алфавит включает многобайтовые символы, у автора можно запросить единицу длины и граничный пример. Один пример `demo-42` не определяет алфавит. [Пример запроса](../../docs/requirements.md#L109) · [Параметр](../../docs/requirements.md#L142) · [Z-019](../../reports/submission/review.md#z-019) |
