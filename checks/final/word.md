## Проверка набора в целом

Месячный максимум push конфликтует с правилом смены порога. Запись настройки через GET несовместима с семантикой метода. При отклонении суммы определён ERROR, а HTTP-статус задан противоречиво. Согласованность пограничного примера по месяцу зависит от пояса времени совершения покупки.

Открытых предполагаемых пробелов — 12. Неоднозначностей — 1. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-011 · Повторный push после смены порога

**Дефект · Противоречивость · Критичная.** После первого push в том же месяце Ф-3 запрещает второй, а Ф-4 требует его при достижении повышенного порога. Число push в этом сценарии принять невозможно.

Затронутые утверждения — [R-D0018-03](#r-d0018-03), [R-D0019-01](#r-d0019-01), [R-D0019-02](#r-d0019-02).

> На карту приходится максимум один такой push за календарный месяц.

> При изменении порога накопленная сумма сохраняется.  

[R-D0019-02](#r-d0019-02) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [DOCX, абзац 19](../docx/requirements-copy.docx)

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

**Сценарий.** Уведомление включено. Карта уже получила push в этом месяце. Владелец увеличивает порог выше накопленных расходов, затем покупка доводит расходы до нового порога в том же месяце.

**Последствие.** Ф-3 даёт один push за месяц, Ф-4 даёт два.

**Общее условие.** Уведомление включено. После первого push владелец повышает порог выше накопленной суммы, и расходы достигают нового порога в том же месяце. Основания — [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.», [R-D0019-01](#r-d0019-01) «При изменении порога накопленная сумма сохраняется.», [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** После смены порога в этом сценарии клиент должен получить второй push или месячный максимум сохраняется?

1. **Вариант 1.** На карту приходится максимум один push за календарный месяц, в том числе после смены порога.

   **Основание.** [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет.

   При выборе этого варианта привести в соответствие [R-D0019-02](#r-d0019-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Клиент получает второй push в том же месяце.

   При выборе этого варианта привести в соответствие [R-D0018-03](#r-d0018-03).

**Черновик приёмочного теста.** Получить первый push, увеличить порог, провести покупку до нового порога и посчитать push по карте за месяц.

> 3. Изменение порога сохраняет накопленные расходы.  

**Внешнее основание.** Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. Побочные действия сервера, которых клиент не запрашивал, сами по себе допустимы. [RFC 9110 § 9.2.1 · Safe Methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)

**Сценарий.** Владелец активной карты KZT вызывает GET /alerts/saveLimit с допустимым порогом, отличным от сохранённого.

**Последствие.** Клиент запрашивает замену настройки, а вызов меняет её. Повтор идентичного запроса может оставить ту же настройку, но первый вызов уже нарушает безопасность GET.

### Z-023 · Единица длины cardId

**Неоднозначность · Однозначность · Низкая.** Размер 1–64 задан для строкового параметра без единицы измерения. Подсчёт символов и подсчёт байтов дают разные результаты проверки длины одной строки.

Затронутые утверждения — [R-T006R0002-02](#r-t006r0002-02).

[R-T006R0002-02](#r-t006r0002-02) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [DOCX, таблица 6, строка 2](../docx/requirements-copy.docx)

> cardId	string	1–64  

**Сценарий.** Проверить формат cardId из 64 букв «я», занимающих 128 байт в UTF-8. Проверка длины рассматривается отдельно от поиска карты.

**Последствие.** Строка проходит границу при подсчёте символов и превышает её при подсчёте байтов UTF-8.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Размер cardId задан в символах или байтах, и если в байтах, в какой кодировке?

1. **Вариант 1.** Размер 1–64 измеряется символами строки.

   **Основание.** [R-T006R0002-02](#r-t006r0002-02) «cardId	string	1–64».

   **Ожидаемый результат.** Значение проходит проверку длины.

2. **Вариант 2.** Размер 1–64 измеряется байтами строки.

   **Основание.** [R-T006R0002-02](#r-t006r0002-02) «cardId	string	1–64».

   **Ожидаемый результат.** Значение отклоняется проверкой длины.

**Черновик приёмочного теста.** На строке из 64 букв «я» проверить соблюдение ограничения длины по согласованной единице, отдельно от проверки принадлежности карты.

<a id="decision"></a>

## Готовность и порядок исправлений

ТЗ требует согласования перед разработкой и приёмкой сценариев смены порога и сохранения настройки. Для интеграционной приёмки также нужны критерий получения push и источники данных для конкретных потребителей.

1. Согласовать число push после смены порога и HTTP-операцию записи настройки. ([Z-011](#z-011), [Z-013](#z-013))
2. Определить HTTP-статус отклонённой суммы, форму возврата прежнего состояния и обязательность enabled при успехе. ([Z-005](#z-005), [Z-015](#z-015), [Z-016](#z-016))
3. Уточнить пояс времени совершения в примере, входные данные учёта и предусловия сценария с одним push. ([Z-008](#z-008), [Z-009](#z-009), [Z-017](#z-017))
4. Задать критерий получения push, смысл признака отправки и данные, доступные приложению, сервису расходов и сервису push. ([Z-001](#z-001), [Z-002](#z-002), [Z-003](#z-003), [Z-004](#z-004), [Z-006](#z-006), [Z-010](#z-010), [Z-012](#z-012))
5. Указать единицу измерения длины cardId. ([Z-023](#z-023))
