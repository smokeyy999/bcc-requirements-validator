## Проверка набора в целом

Ф-3 и Ф-4 задают разные числа push при повторном достижении порога в том же месяце. Сохранение через GET противоречит семантике метода, а для обязательного чтения настройки приложением не определены запрос и ответ. Минутный срок проверяет передачу push на отправку. Для своевременности получения клиентом нужен отдельный критерий. Возможные расхождения в примере на стыке месяцев и в примере с ERROR зависят от уточнения входов.

Открытых предполагаемых пробелов — 16. Неоднозначностей — 1. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

### Z-010 · Повторный push после смены порога

**Дефект · Противоречивость · Критичная.** При втором достижении порога в том же месяце Ф-3 запрещает второй push, а Ф-4 требует его независимо от истории предыдущей настройки. Число уведомлений для обязательного сценария определить нельзя.

Затронутые утверждения — [R-P001L0039-03](#r-p001l0039-03), [R-P001L0040-01](#r-p001l0040-01), [R-P001L0040-02](#r-p001l0040-02).

> При изменении порога накопленная сумма сохраняется.  

[R-P001L0040-02](#r-p001l0040-02) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [PDF, стр. 1, строка 40 текстового слоя](../pdf/requirements-copy.pdf#page=1)

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

**Сценарий.** По карте с включённым уведомлением уже был push при достижении 50 000 ₸. В том же календарном месяце при итоге 50 000 ₸ клиент поднимает порог до 60 000 ₸ и проводит покупку на 10 000 ₸.

**Последствие.** Месячный лимит даёт один push за месяц, правило смены порога даёт два. Приоритет правил не задан.

**Общее условие.** По одной карте уже был push в этом календарном месяце. Новый порог выше сохранённых расходов, и следующая покупка доводит расходы до нового порога. Основания — [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-P001L0040-01](#r-p001l0040-01) «При изменении порога накопленная сумма сохраняется.», [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При достижении нового порога выбрать отсутствие второго push или его отправку?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после смены порога.

   **Основание.** [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** На второй покупке нового push нет. За месяц получен один push.

   При выборе этого варианта привести в соответствие [R-P001L0040-02](#r-p001l0040-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, в том числе её отправок в том же месяце.

   **Основание.** [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** На второй покупке приходит push. За месяц получены два push.

   При выборе этого варианта привести в соответствие [R-P001L0039-03](#r-p001l0039-03).

**Черновик приёмочного теста.** Получить первый push, поднять порог выше текущей суммы, достичь нового порога покупкой и посчитать push за месяц.

**Сценарий.** Проверить успешное первое сохранение и замену настройки. Сверить коды по уточнённому условию для 201 либо проверить 200 в обоих сценариях, если 201 не используется.

**Последствие.** 200 описан для успешного выполнения, а 201 лишь отнесён к успешным ответам. Для 201 не указано условие выдачи. Фраза «и далее» сама по себе не обещает дополнительные статусы.

### Z-023 · Какие символы допустимы в cardId и в какой единице проверяется предел 1–64?

**Предполагаемый пробел · Полнота · Низкая.** Для cardId задан предел 1–64 без единицы. Сценарий, различающий символы и байты, зависит от того, допустимы ли многобайтные символы в идентификаторе.

Затронутые утверждения — [R-P003L0042-02](#r-p003l0042-02).

[R-P003L0042-02](#r-p003l0042-02) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [PDF, стр. 3, строка 42 текстового слоя](../pdf/requirements-copy.pdf#page=3)

> \| \`cardId\` \| string \| 1–64 \|  

**Сценарий.** Проверить граничную строку из допустимых символов отдельно от поиска карты. Если разрешены многобайтные символы, проверить строку из 64 символов длиной более 64 байт.

**Что нужно уточнить.** Может ли допустимый по набору символов cardId занимать более 64 байт при длине 64 символа?

**Как ответ изменит приёмку.** Для допустимой многобайтной строки подсчёт символов и байтов даёт разные результаты. При исключённом наборе символов спорная строка не подходит для проверки единицы длины.

<a id="decision"></a>

## Готовность и порядок исправлений

До разработки и приёмки затронутых сценариев нужно согласовать исход повторного достижения порога и контракт чтения и сохранения настроек. Проверки расчёта расходов и минутного срока передачи push можно готовить параллельно. Приёмка своевременности получения push зависит от согласованного критерия.

1. Согласовать месячный лимит с правилом смены порога и зафиксировать число push в сценарии повторного достижения. ([Z-010](#z-010))
2. Согласовать HTTP-метод сохранения с семантикой записи и определить наблюдаемый контракт чтения для приложения. ([Z-014](#z-014), [Z-013](#z-013))
3. Установить дату совершения покупки по Алматы и вход примера с ERROR. Согласовать результаты только там, где подтвердится совпадение условий. ([Z-007](#z-007), [Z-016](#z-016))
4. Задать критерий своевременного получения push, предусловия примера с одним push, источники обоих полей запроса и единицу суммы. ([Z-001](#z-001), [Z-005](#z-005), [Z-009](#z-009), [Z-012](#z-012))
5. Указать источник месячного итога для приложения и данные, по которым тест подтверждает повтор события процессинга. ([Z-002](#z-002), [Z-008](#z-008))
6. Уточнить допуск карт, условие 403, состав тел отказов, представление прежней настройки и применимость 201. ([Z-003](#z-003), [Z-015](#z-015), [Z-017](#z-017), [Z-018](#z-018), [Z-019](#z-019))
7. Уточнить соответствие кодов переключателя его состояниям и правила проверки enabled и cardId. ([Z-006](#z-006), [Z-022](#z-022), [Z-023](#z-023))
