# Независимая вычитка свободной банковской очереди

В первом полном прогоне версии `48f37df` через `gpt-6.2-sol` можно передать владельцу **17 из 18 вопросов** с опубликованными тестами. В той же очереди полностью воспроизведены **12 из 17 прежних тем** версии `5669ac8`. Каждый зачёт требует открытого решения и сценария, который различает его исходы. [Протокол](protocol.md) · [Новый отчёт](../../reports/review8/review.md) · [Прежняя очередь](../finish4/queue-review.md)

Обе целевые формулировки передаются автору дословно. Полный возврат в Z-010 однозначен, а Z-018 проверяет оба прежних значения в ответе с ERROR и их совпадение с сохранёнными. Все 18 вопросов поднимают обоснованное решение с тестом. У одного, Z-014, требуется грамматическое согласование, чтобы буквальная формулировка передавала верное направление вызова.
В Z-009 агент явно спрашивает, как представлены входные сумма и время, допускает преобразование и проверяет запись именно в тиынах. Единица хранения отделена от единицы входа. Сохранились условная приёмка у получателя и событие у отправителя, вопросы об алфавите cardId и точной иллюстративной строке 400 отсутствуют.
Четыре новые относительно прежних 17 темы касаются соответствия 0/1 состояниям переключателя, источников атрибутов проведённой покупки, контракта чтения порога сервисом расходов и применимости 201. Вопрос о чтении порога закрывает иной вход сервиса, чем получение признака включения. Пропуски при свободном обнаружении учитываются отдельно от повторного рецензирования зафиксированной очереди.

## Дословные вопросы и проверка их применимости

### Z-011

**При втором достижении в том же месяце отправить push или подавить его по месячному максимуму?**

Тест из отчёта — Выполнить обе покупки со сменой порога между ними и проверить число push по одной карте за месяц.

Наблюдаемый результат из карточки — Второго push нет. За месяц один push.

Наблюдаемый результат из карточки — При итоге 60 000 ₸ приходит ещё один push. За месяц два push.

**Готов.** Ответ меняет счётчик отправок в одном месяце. В тесте разрешается прямое расхождение двух функциональных правил. [Строка 39](../../docs/requirements.md#L39) · [Строка 40](../../docs/requirements.md#L40) · [Z-011](../../reports/review8/review.md#z-011)

### Z-004

**Передавать 2 000 ₸ покупки или 50 500 ₸ месячного итога и в какой единице представить выбранную сумму?**

Тест из отчёта — Перехватить запрос на push для указанной покупки и сверить значение поля с выбранной суммой в согласованной единице.

Наблюдаемый результат из карточки — Запрос передаёт величину, равную сумме покупки 2 000 ₸. / Запрос передаёт величину, равную новому месячному итогу 50 500 ₸.

**Готов.** Покупка на 2 000 ₸ и месячный итог 50 500 ₸ дают разные значения одного исходящего поля. Его единица для передачи явно не задана. [Строка 43](../../docs/requirements.md#L43) · [Строка 49](../../docs/requirements.md#L49) · [Z-004](../../reports/review8/review.md#z-004)

### Z-014

**Какой HTTP-метод должен вызывать приложение для сохранения?**

Тест из отчёта — Сверить метод в контракте и примере. Сохранить новый порог, повторить тот же запрос и сравнить конечную настройку после каждого вызова.

Наблюдаемый результат из карточки — По ТЗ порог заменяется. По правилу safe клиент не должен запрашивать такую замену через GET.

Редакция вычитки для дословной отправки: «Какой HTTP-метод должно использовать приложение для сохранения настройки?» Тест изменения и повторной записи можно сохранить. ### Z-007

**Как значения enabled=0 и enabled=1 соответствуют выключенному и включённому уведомлению?**

Тест из отчёта — Проверить исходное выключенное состояние. На двух картах без push за текущий месяц сохранить разные допустимые коды, сверить переключатели и провести покупки, впервые доводящие расходы до порога. Проверить push для включённого состояния.
