## Проверка набора в целом

ТЗ задаёт расчёт расходов и базовое достижение порога. Правила расходятся при повторном достижении после смены порога. REST-контракт требует корректировки операции записи и определения чтения настроек. Для части интеграционных проверок и пограничных сценариев нужны уточнения.

Открытых предполагаемых пробелов — 11. Неоднозначностей — 1. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** При включённом уведомлении карта получила push на 50 000 ₸. В том же месяце повысить порог до 60 000 ₸ при итоге 50 000 ₸ и провести покупку на 10 000 ₸.

**Последствие.** Ф-3 оставляет один push за месяц, Ф-4 даёт два.

**Общее условие.** По той же карте в текущем календарном месяце уже был push. После смены порога сохранённый итог ниже нового порога и затем достигает его в том же месяце. Основания — [R-P001L0039-02](#r-p001l0039-02) «На карту приходится максимум один такой push за календарный месяц.», [R-P001L0040-01](#r-p001l0040-01) «При изменении порога накопленная сумма сохраняется.», [R-P001L0040-03](#r-p001l0040-03) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При достижении повышенного порога в этом случае принять один push за месяц или два?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после смены порога.

   **Основание.** [R-P001L0039-02](#r-p001l0039-02) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет. За месяц один push.

   При выборе этого варианта привести в соответствие [R-P001L0040-03](#r-p001l0040-03).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая уже отправленный push.

   **Основание.** [R-P001L0040-03](#r-p001l0040-03) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** На новом пороге приходит второй push за месяц.

   При выборе этого варианта привести в соответствие [R-P001L0039-02](#r-p001l0039-02).

**Черновик приёмочного теста.** После первого push изменить порог, довести сохранённый итог до нового порога и посчитать push за месяц.

### Z-009 · GET меняет настройку

**Дефект · Противоречивость · Существенная.** Описание и пример выбирают GET для сохранения, а логика предписывает заменить настройку по запросу клиента. По семантике GET, указанной в RFC 9110 § 9.2.1, запрос не должен запрашивать такое изменение. Сам результат записи задан.

> 4. Заменить настройку и вернуть результат сохранения.  

**Внешнее основание.** Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. **Сценарий.** Для активной карты владельца сохранён порог 48 000 ₸. Выполнить описанный GET с корректными параметрами и порогом 50 000 ₸.

### R-P004L0027-01 · Пример HTTP 400 содержит сообщение «Некорректный запрос».

## Готовность и порядок исправлений

ТЗ частично готово к разработке. Приёмка уведомления после смены порога заблокирована до согласования Ф-3 и Ф-4. Для завершения приёмки REST нужны согласованный метод записи, контракт чтения и ожидаемые результаты пограничных проверок.

1. Согласовать число push при достижении повышенного порога после уже полученного уведомления в том же месяце. ([Z-007](#z-007))
2. Согласовать HTTP-операцию записи и контракт чтения сохранённых порога и переключателя. ([Z-009](#z-009), [Z-002](#z-002))
3. Уточнить зону времени совершения покупки и применимость примера ERROR к проверке диапазона. ([Z-006](#z-006), [Z-011](#z-011))
4. Определить источники месячного итога для приложения и четырёх цифр для сервиса расходов, а также значение и единицу суммы в передаче push. ([Z-001](#z-001), [Z-004](#z-004), [Z-008](#z-008))
5. Согласовать коды переключателя, разбор enabled, условие 403 и формат cardId. ([Z-003](#z-003), [Z-018](#z-018), [Z-016](#z-016), [Z-015](#z-015))
6. Уточнить критерий своевременности получения push и событие, которое отражает хранимый признак отправки. ([Z-012](#z-012), [Z-013](#z-013))
7. Разместить явно помеченные ответы и примеры в подразделах соответствующих HTTP-кодов. ([Z-019](#z-019))
