## Проверка набора в целом

ТЗ задаёт учёт расходов и проверку порога. Приёмку сохранения блокирует выбор GET для записи, а приёмку уведомления после смены порога блокируют два обязательных исхода. Для REST API, данных push и отдельных приёмочных примеров остаются самостоятельные уточнения.

Открытых предполагаемых пробелов — 12. Неоднозначностей — 2. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

> 3. Изменение порога сохраняет накопленные расходы.

> проверка порога → при достижении отправка push  

**Сценарий.** При включённых уведомлениях карта уже получила push на расходах 50 000 ₸. В том же месяце клиент меняет порог на 60 000 ₸ и проводит покупку на 10 000 ₸.

**Последствие.** Накопленный итог достигает 60 000 ₸. По Ф-3 за месяц остаётся один push, по Ф-4 их становится два.

**Общее условие.** Карта уже получила push в этом месяце. Накопленные 50 000 ₸ сохраняются при повышении порога до 60 000 ₸, затем покупка на 10 000 ₸ достигает нового порога в том же месяце. Основания — [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.», [R-D0019-01](#r-d0019-01) «При изменении порога накопленная сумма сохраняется.», [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** После достижения нового порога в описанном случае за месяц должен остаться один push или стать два?

1. **Вариант 1.** На карту приходится максимум один push за календарный месяц, включая смену порога.

   **Основание.** [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Нового push нет. За месяц остаётся один push.

   При выборе этого варианта привести в соответствие [R-D0019-02](#r-d0019-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая отправку в том же месяце.

   **Основание.** [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Следующее достижение вызывает push. За месяц их становится два.

   При выборе этого варианта привести в соответствие [R-D0018-03](#r-d0018-03).

**Черновик приёмочного теста.** Получить первый push, поднять порог, достичь его новой покупкой и подсчитать push по карте за тот же месяц.

### Z-015 · Какое условие доступа при действующей сессии соответствует HTTP 403 с учётом обязательного 404 для чужой и отсутствующей карты?

**Предполагаемый пробел · Полнота · Низкая.** Слова «Для чужой карты возвращается 404» прямо определяют исход проверки принадлежности. Для отдельной ветви 403 указан запрет доступа без воспроизводимого условия.

Затронутые утверждения — [R-D0067-01](#r-d0067-01), [R-D0074-01](#r-d0074-01).

[R-D0067-01](#r-d0067-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 200. Successful — Created · [DOCX, абзац 67](../docx/requirements-copy.docx)

[R-D0074-01](#r-d0074-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 403. Unsuccessful — Forbidden · [DOCX, абзац 74](../docx/requirements-copy.docx)

**Сценарий.** С действующей сессией проверить 404 для чужой и отсутствующей карты. Для существующей собственной карты с допустимыми параметрами воспроизвести согласованное условие запрета и проверить 403.

**Открытое решение.** Воспроизводимое условие запрета для ветви 403.

**Что различит проверка.** При применимом ограничении запрос владельца своей карты возвращает 403. / При отсутствии применимого ограничения тот же запрос проходит контроль доступа.

## Готовность и порядок исправлений

Спецификация частично готова к разработке. Можно реализовывать описанный учёт покупок и возвратов. Контракт сохранения и поведение push при повторном достижении после смены порога требуют решения до приёмки.

1. Согласовать число push после смены порога и объявить HTTP-операцию, семантика которой допускает сохранение. ([Z-007](#z-007), [Z-012](#z-012))
2. Зафиксировать контракт чтения, коды переключателя, ответы ошибок и правило проверки записи enabled. ([Z-003](#z-003), [Z-004](#z-004), [Z-005](#z-005), [Z-013](#z-013), [Z-014](#z-014), [Z-016](#z-016))
3. Указать источник месячного итога для экрана, значение и единицу суммы в push, источник последних цифр карты. ([Z-002](#z-002), [Z-006](#z-006), [Z-011](#z-011))
4. Дополнить подготовку приёмочных примеров, привязать момент совершения к Алматы и уточнить критерий времени получения и событие установки признака. ([Z-008](#z-008), [Z-009](#z-009), [Z-001](#z-001), [Z-010](#z-010))
5. Уточнить условие 403 и правило длины cardId, разместить правила и примеры под их явными HTTP-кодами. ([Z-015](#z-015), [Z-020](#z-020), [Z-019](#z-019))
