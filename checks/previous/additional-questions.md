# Какие вопросы передать автору ТЗ

В отчёте версии `debbf85` 15 вопросов. Повторный push и HTTP-метод сохранения модель отметила как блокирующие приёмку. Таблица содержит редакционную оценку ещё девяти вопросов после чтения обеих частей ТЗ. У всех девяти в отчёте стоит пометка «Требует уточнения». [Вопросы из отчёта](../../reports/previous/review.md#questions) · [Сверка основных решений](review-check.md)

| Вопрос | Оценка | Что уточнить у автора |
|---|---|---|
| Месячная сумма на экране | Согласен | Экран показывает расходы, а поле `amount` в ответе сохранения содержит порог. Для приёмки нужен источник месячного итога по выбранной карте. [Экран](../../docs/requirements.md#L29) · [Поле ответа](../../docs/requirements.md#L156) · [Z-001](../../reports/previous/review.md#z-001) |
| Сумма, передаваемая в push | Согласен | При превышении порога сумма последней покупки, порог и месячный итог могут различаться. Нужны значение и единица поля в сообщении. ТЗ задаёт единицы хранения покупки и порога по отдельности. [Вызов push](../../docs/requirements.md#L43) · [Единицы](../../docs/requirements.md#L49) · [Z-004](../../reports/previous/review.md#z-004) |
| Включены ли уведомления | Есть оговорка | Источник настройки известен, `enabled` сохраняется и возвращается. Диаграмма указывает получение порога. Стоит спросить, как сервис расходов узнаёт действующее значение переключателя. [Диаграмма](../../docs/requirements.md#L43) · [Признак переключателя](../../docs/requirements.md#L144) · [Ответ](../../docs/requirements.md#L157) · [Z-005](../../reports/previous/review.md#z-005) |
| Данные покупки и возврата | Есть оговорка | Отправитель события покупки указан. Для интеграционного теста стоит запросить контракт события со временем совершения, идентификатором операции и ссылкой возврата на исходную покупку. Это позволит проверить выбор месяца и повторную доставку. [Ф-2](../../docs/requirements.md#L38) · [Процессинг](../../docs/requirements.md#L43) · [Повтор](../../docs/requirements.md#L52) · [Z-008](../../reports/previous/review.md#z-008) |
| Когда израсходован лимит push | Есть оговорка | Лимит уже задан на карту и календарный месяц. Остаётся уточнить момент фиксации отправки. Тест с отсутствием подтверждения доставки нужен, если такой сценарий входит в приёмку. [Лимит](../../docs/requirements.md#L39) · [Передача на отправку](../../docs/requirements.md#L46) · [Хранимый признак](../../docs/requirements.md#L49) · [Z-009](../../reports/previous/review.md#z-009) |
| Последние четыре цифры карты | Лишний как отдельный вопрос | Обязанность передать четыре цифры задана, а способ их получить из `cardId` не описан. При обсуждении контракта по Z-008 можно сразу выяснить, приходят ли цифры с событием или доступны по ссылке на карту. [Состав вызова](../../docs/requirements.md#L43) · [Идентификатор карты](../../docs/requirements.md#L142) · [Z-011](../../reports/previous/review.md#z-011) |
| Срок получения push клиентом | Есть оговорка | Обязательный минутный норматив уже можно проверить от получения события до передачи на отправку. Предельное время доставки на телефон стоит запрашивать, если команда хочет отдельно измерять достижение цели «в момент покупки». [Цель](../../docs/requirements.md#L23) · [Норматив](../../docs/requirements.md#L46) · [Z-014](../../reports/previous/review.md#z-014) |
| Условия ответа 403 | Согласен | Для чужой и отсутствующей карты ожидается 404. Владелец API может назвать отдельный сценарий 403 или уточнить его применимость и исправить заголовок подраздела. [Описание 403](../../docs/requirements.md#L175) · [Правило 404](../../docs/requirements.md#L189) · [Z-017](../../reports/previous/review.md#z-017) |
| Алфавит и длина `cardId` | Есть оговорка | Сначала достаточно получить контракт идентификаторов. При подсчёте в байтах кодировка может изменить результат для строки на границе длины. Пример `demo-42` не определяет весь алфавит. [Пример](../../docs/requirements.md#L109) · [Параметр](../../docs/requirements.md#L142) · [Z-019](../../reports/previous/review.md#z-019) |
