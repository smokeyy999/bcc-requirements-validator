### Z-008 · Второй push после повышения порога

**Дефект · Противоречивость · Критичная.** Ф-3 ограничивает отправку одним push на карту за месяц. Ф-4 требует push при достижении повышенного порога независимо от истории прежней настройки. После первого push принять сценарий по обоим правилам невозможно.

Затронутые утверждения — [R-P001L0039-03](#r-p001l0039-03), [R-P001L0040-02](#r-p001l0040-02).

> На карту приходится максимум один такой push за календарный месяц.  

[R-P001L0040-02](#r-p001l0040-02) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [PDF, стр. 1, строка 40 текстового слоя](../pdf/requirements-copy.pdf#page=1)

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

**Сценарий.** Уведомления включены. По карте уже был push в текущем месяце. Клиент повышает порог выше накопленной суммы, затем покупка доводит итог до нового порога в том же месяце.

**Последствие.** Ф-3 ограничивает число push за месяц одним. Ф-4 требует push при следующем достижении независимо от истории предыдущей настройки.

**Общее условие.** По карте уже был push в этом календарном месяце. Накопленная сумма ниже нового порога, который затем достигается в том же месяце. Основания — [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** После достижения нового порога в этом сценарии клиент должен получить второй push или месячный лимит должен его подавить?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после изменения порога.

   **Основание.** [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** При достижении нового порога второго push нет.

   При выборе этого варианта привести в соответствие [R-P001L0040-02](#r-p001l0040-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая отправку по ней в том же месяце.

   **Основание.** [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении нового порога приходит второй push.

   При выборе этого варианта привести в соответствие [R-P001L0039-03](#r-p001l0039-03).

**Черновик приёмочного теста.** Получить первый push, повысить порог и провести покупку до нового порога в том же месяце. Посчитать push по карте.

### Z-015 · Какие символы допустимы в cardId и в какой единице измеряется предел 64?

**Предполагаемый пробел · Полнота · Низкая.** Для строкового cardId задан диапазон 1–64. Пример demo-42 не устанавливает допустимый алфавит или единицу размера.

Затронутые утверждения — [R-P003L0042-05](#r-p003l0042-05).

[R-P003L0042-05](#r-p003l0042-05) · Уведомление о расходах по карте / Часть B. REST API / Параметры запроса / Query-параметры / Столбцы: Parameter · Format · Size · Mandatory · Logic · Description · DB field · [PDF, стр. 3, строка 42 текстового слоя](../pdf/requirements-copy.pdf#page=3)

> \| \`cardId\` \| string \| 1–64 \| Да \| Карта клиента \| Идентификатор карты \| \`card\_id\` \|  

**Сценарий.** Если допустима строка из 64 символов, занимающая более 64 байт, проверить её на этапе контроля размера отдельно от поиска карты. Иначе проверить границу на согласованном алфавите.

**Что нужно уточнить.** Допускает ли алфавит cardId строку из 64 символов, занимающую более 64 байт?

**Как ответ изменит приёмку.** Если такая строка допустима, она проходит предел в символах и превышает предел в байтах. Если её исключает алфавит, сценарий не различает правила размера.

## Готовность и порядок исправлений

ТЗ не готово к полной приёмке. Сначала нужно определить ожидаемое число push после повышения порога и исправить операцию сохранения. Пограничный пример учёта можно сверить после уточнения часового пояса времени совершения, а проверку переключателя — после определения смысла кодов 0 и 1.

1. Определить, сколько push получает клиент при достижении повышенного порога после первой отправки в том же месяце. (Z-008)
2. Согласовать HTTP-операцию сохранения и контракт чтения сохранённых порога и переключателя. (Z-010, Z-002)
3. Уточнить ответы при отклонении суммы, соответствие кодов переключателю и правила проверки параметров. (Z-003, Z-011, Z-006, Z-015, Z-016)
4. Уточнить источник месячного итога для экрана, значение и единицу суммы в push, источник цифр карты и критерий времени получения push. (Z-001, Z-004, Z-009, Z-012)
5. Указать часовой пояс времени совершения покупки и исходное состояние уведомлений в строках приёмки. (Z-007, Z-005)
