### Z-009 · Второй push после смены порога

**Дефект · Противоречивость · Критичная.** После первого push повышение порога сохраняет накопление. При новом пересечении в том же месяце Ф-3 запрещает второй push, а Ф-4 предписывает его «независимо от истории предыдущей настройки». Принять сценарий одновременно по обоим правилам невозможно.

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** Карта уже получила push при достижении 50 000 ₸. В том же месяце держатель оставляет уведомление включённым и повышает порог до 60 000 ₸. Затем покупки доводят неизменённое накопление до нового порога.

**Последствие.** За месяц по карте ожидается либо один push, либо два.

**Общее условие.** Одна карта и один календарный месяц. После первого push накопление сохранено и ниже нового порога. При включённом уведомлении расходы достигают нового порога. Основания — [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.», [R-D0019-01](#r-d0019-01) «При изменении порога накопленная сумма сохраняется.», [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** После достижения нового порога в этом сценарии клиент должен получить второй push или за месяц должен остаться один?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после смены порога.

   **Основание.** [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет. За месяц остаётся один push.

   При выборе этого варианта привести в соответствие [R-D0019-02](#r-d0019-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, его следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении нового порога приходит второй push за тот же месяц.

   При выборе этого варианта привести в соответствие [R-D0018-03](#r-d0018-03).

**Черновик приёмочного теста.** Получить первый push, повысить порог выше накопленной суммы и в том же месяце довести итог до нового порога. Посчитать push по карте.

> 2. Повторное сохранение заменяет действующую настройку.  

**Внешнее основание.** Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. Побочные действия сервера, которых клиент не запрашивал, сами по себе допустимы. [RFC 9110 § 9.2.1 · Safe Methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)

**Сценарий.** Владелец карты с действующей настройкой передаёт через объявленный GET другой допустимый порог и состояние переключателя.

**Последствие.** По логике ТЗ клиент запрашивает замену настройки, тогда как безопасная операция не должна запрашивать такое изменение.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой HTTP-метод будет выполнять обязательную замену настройки?

Привести контракт и пример [R-D0027-01](#r-d0027-01), [R-D0042-02](#r-d0042-02), [R-D0046-01](#r-d0046-01), [R-T005R0002-01](#r-t005r0002-01), [R-T005R0003-01](#r-t005r0003-01), [R-T005R0008-01](#r-t005r0008-01) в соответствие с правилом «Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. Побочные действия сервера, которых клиент не запрашивал, сами по себе допустимы.». Проверяемое поведение — Владелец карты с действующей настройкой передаёт через объявленный GET другой допустимый порог и состояние переключателя.

**Черновик приёмочного теста.** Вызвать согласованную операцию с новой настройкой и сравнить сохранённые значения до и после вызова. Сверить эффект с семантикой выбранного метода.

### Z-016 · Какой достижимый для этого метода запрет доступа подпадает под правило HTTP 403, если у правила есть отдельный сценарий?

**Предполагаемый пробел · Полнота · Существенная.** Для запрета доступа заявлен HTTP 403. Чужая и отсутствующая карты явно дают HTTP 404, а отсутствие авторизации даёт HTTP 401. Отдельный достижимый запрет пока не описан.

Затронутые утверждения — [R-D0066-01](#r-d0066-01), [R-D0067-01](#r-d0067-01), [R-D0074-01](#r-d0074-01).

[R-D0066-01](#r-d0066-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 200. Successful — Created · [DOCX, абзац 66](../docx/requirements-copy.docx)

> 401. Ответ в случае, если запрос выполнен без необходимой авторизации.  

[R-D0067-01](#r-d0067-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 200. Successful — Created · [DOCX, абзац 67](../docx/requirements-copy.docx)

> 403. Ответ в случае, если на указанный ресурс доступ запрещен.  

[R-D0074-01](#r-d0074-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 403. Unsuccessful — Forbidden · [DOCX, абзац 74](../docx/requirements-copy.docx)

> Для чужой карты возвращается 404, как и для отсутствующей карты.  

**Сценарий.** Проверить HTTP 401 без необходимой авторизации и HTTP 404 для чужой и отсутствующей карты. Если указан отдельный достижимый запрет, воспроизвести его и проверить HTTP 403.

**Что нужно уточнить.** Наличие достижимого запрета доступа, отличного от явно описанных случаев HTTP 401 и HTTP 404.

**Как ответ изменит приёмку.** При наличии отдельного запрета у HTTP 403 появляется воспроизводимая проверка. Иначе описанные входы покрывают HTTP 401 и HTTP 404.

**Уже установлено.** Чужая и отсутствующая карты дают HTTP 404. Отсутствие необходимой авторизации даёт HTTP 401. Основания — [R-D0067-01](#r-d0067-01), [R-D0040-01](#r-d0040-01), [R-D0066-01](#r-d0066-01), [R-D0074-01](#r-d0074-01).

**Открытое решение.** Какой отдельный вход запускает запрет с HTTP 403, если он достижим.

**Что различит проверка.** Обозначенный запрет воспроизводится и возвращает HTTP 403. / Отдельного достижимого входа для HTTP 403 нет, а проверки HTTP 401 и HTTP 404 выполняются по заданным правилам.

## Готовность и порядок исправлений

ТЗ пока не готово к разработке и приёмке в полном объёме. Блокирующие сценарии требуют согласования. Месячный учёт и минутный интервал передачи уже можно проверять по установленным правилам.

1. Согласовать число push после смены порога и HTTP-операцию для обязательной замены настроек. ([Z-009](#z-009), [Z-011](#z-011))
2. Согласовать контракт HTTP 200, восстановить запрос примера ERROR, определить обязательность полей и вход для HTTP 403, если он достижим. ([Z-015](#z-015), [Z-012](#z-012), [Z-013](#z-013), [Z-016](#z-016))
3. Уточнить чтение порога и переключателя, источник месячного итога, состояние уведомления при решении об отправке, его кодирование и оба значения для сервиса push. ([Z-003](#z-003), [Z-002](#z-002), [Z-004](#z-004), [Z-006](#z-006), [Z-008](#z-008), [Z-010](#z-010))
4. Установить дату совершения покупки по Алматы, границу приёмки своевременности у клиента и событие фиксации признака отправки. ([Z-007](#z-007), [Z-001](#z-001), [Z-005](#z-005))
