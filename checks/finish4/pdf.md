## Проверка набора в целом

Два прямых противоречия блокируют приёмку повторного достижения порога после смены настройки и сохранения настройки по HTTP. Срок передачи push измерим. Отдельных решений требуют приёмка времени получения и событие установки хранимого признака отправки. Согласованность пограничной строки с Ф-2 зависит от даты покупки в Алматы.

Открытых предполагаемых пробелов — 11. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-008](#z-008) · Лимит Ф-3 действует на карту за календарный месяц. Ф-4 сохраняет расходы при смене порога и требует push при следующем достижении независимо от истории предыдущей настройки. > 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** Для включённой настройки по карте уже получен push при расходах 50 000 ₸. В том же месяце порог повышают до 60 000 ₸ и проводят покупку на 10 000 ₸.

**Последствие.** При неизменном наборе операций за месяц клиент получит один или два push.

**Общее условие.** Карта уже получила push при 50 000 ₸. В том же месяце порог повышен до 60 000 ₸ при сохранённых расходах 50 000 ₸. Проведённая покупка на 10 000 ₸ приводит к достижению нового порога. Основания — [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-P001L0040-01](#r-p001l0040-01) «При изменении порога накопленная сумма сохраняется.», [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход выбрать при достижении нового порога после уже полученного в этом месяце push?

1. **Вариант 1.** На карту приходится максимум один push за календарный месяц, в том числе после изменения порога.

   **Основание.** [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второго push нет. За месяц получен один push.

   При выборе этого варианта привести в соответствие [R-P001L0040-02](#r-p001l0040-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая уже полученный за месяц push.

   **Основание.** [R-P001L0040-02](#r-p001l0040-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении 60 000 ₸ приходит второй push за месяц.

   При выборе этого варианта привести в соответствие [R-P001L0039-03](#r-p001l0039-03).

**Черновик приёмочного теста.** После первого push повысить порог, убедиться в сохранении расходов, достичь нового порога и проверить общее число push за месяц.

**Сценарий.** У владельца активной карты сохранён порог 40 000 ₸. Он вызывает GET по маршруту из примера с порогом 50 000 ₸ и допустимым значением переключателя.

**Последствие.** Логика ТЗ требует записать 50 000 ₸ вместо 40 000 ₸. Правило safe исключает запрошенную клиентом запись для GET.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Каким HTTP-методом и по какому маршруту приложение должно сохранять новый порог и состояние переключателя?

Привести контракт и пример [R-P001L0052-01](#r-p001l0052-01), [R-P003L0003-01](#r-p003l0003-01), [R-P003L0004-01](#r-p003l0004-01), [R-P003L0009-01](#r-p003l0009-01), [R-P003L0020-02](#r-p003l0020-02), [R-P003L0025-01](#r-p003l0025-01) в соответствие с правилом «Безопасная операция не запрашивает изменение состояния ресурса. В HTTP к безопасным относятся GET, HEAD, OPTIONS и TRACE. Побочные действия сервера, которых клиент не запрашивал, сами по себе допустимы.». Проверяемое поведение — У владельца активной карты сохранён порог 40 000 ₸. Он вызывает GET по маршруту из примера с порогом 50 000 ₸ и допустимым значением переключателя.

[R-P004L0044-01](#r-p004l0044-01) · Уведомление о расходах по карте / Часть B. REST API / Статусы / 500. Unsuccessful — Internal server error · [PDF, стр. 4, строки 44–46 текстового слоя](../pdf/requirements-copy.pdf#page=4)

> \{"message":"Ошибка сервиса"\}  

**Сценарий.** Проверить 401 без необходимой авторизации, 404 для чужой карты и 500 при контролируемом внутреннем сбое. Сверить статус и строковый message, затем проверить допустимость присутствия каждого из полей result и enabled по контракту соответствующего ответа.

**Последствие.** Для result и enabled заданы форматы. Показанные тела 401, 404 и 500 содержат только message. Из примеров следует допустимость показанного состава, а допустимость дополнительных полей для этих исходов не установлена.

**Уже установлено.** Типы полей заданы. Показанные ответы 401, 404 и 500 обходятся без result и enabled. Основания — [R-P004L0003-01](#r-p004l0003-01), [R-P004L0005-01](#r-p004l0005-01), [R-P004L0006-02](#r-p004l0006-02), [R-P004L0032-01](#r-p004l0032-01), [R-P004L0039-01](#r-p004l0039-01), [R-P004L0044-01](#r-p004l0044-01).

**Открытое решение.** Допустимо ли присутствие каждого из двух полей в каждом из трёх ошибочных ответов?

**Что различит проверка.** Ответ с дополнительным полем проходит проверку там, где поле объявлено допустимым. / Тот же ответ не проходит проверку там, где контракт требует отсутствия этого поля.

## Готовность и порядок исправлений

Комплект частично готов к разработке. До реализации и приёмки затронутых сценариев нужно согласовать месячный лимит push и контракт HTTP-сохранения. Для интеграционной приёмки нужно дополнить контракты чтения, передачи данных и ошибочных ответов.

1. Согласовать результат повторного достижения нового порога в том же месяце и HTTP-операцию сохранения настройки. ([Z-008](#z-008), [Z-011](#z-011))
2. Определить чтение текущего порога и переключателя, соответствие кодов состояниям и источник месячного итога для экрана. ([Z-003](#z-003), [Z-006](#z-006), [Z-002](#z-002))
3. Указать источник цифр карты, значение и единицу суммы push, событие установки признака и границу приёмки времени получения. ([Z-009](#z-009), [Z-010](#z-010), [Z-004](#z-004), [Z-001](#z-001))
4. Уточнить зону отметки покупки, привязать оба тела ответа к исходным запросам и определить состав ошибочных ответов. ([Z-007](#z-007), [Z-013](#z-013), [Z-014](#z-014), [Z-015](#z-015))
