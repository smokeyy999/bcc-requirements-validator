## Критичные дефекты

- [Z-009](#z-009) · Ф-3 ограничивает карту одним push за месяц. Ф-4 предписывает push при следующем достижении повышенного порога независимо от истории. При повторном достижении в том же месяце эти нормы не дают принять поведение уведомлений.

### Z-009 · Второй push после смены порога

**Дефект · Противоречивость · Критичная.** Ф-3 ограничивает карту одним push за месяц. Ф-4 предписывает push при следующем достижении повышенного порога независимо от истории. При повторном достижении в том же месяце эти нормы не дают принять поведение уведомлений.

Затронутые утверждения — [R-P001L0039-03](#r-p001l0039-03), [R-P001L0040-02](#r-p001l0040-02), [R-P001L0040-03](#r-p001l0040-03).

[R-P001L0040-02](#r-p001l0040-02) · Уведомление о расходах по карте / Часть A. Новый функционал / Требования к изменениям / Функциональные требования · [PDF, стр. 1, строка 40 текстового слоя](../pdf/requirements-copy.pdf#page=1)

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

**Сценарий.** При включённом уведомлении клиент уже получил push по карте в текущем месяце. Он повышает порог выше накопленных расходов, затем проведённая покупка доводит их до нового порога в том же месяце.

**Последствие.** Ф-3 оставляет один push за месяц. Ф-4 вызывает второй push при достижении нового порога.

**Общее условие.** По включённой настройке уже был push по карте в этом месяце. Порог повышен выше накопленной суммы, новый порог достигнут в том же месяце. Основания — [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.», [R-P001L0040-03](#r-p001l0040-03) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** При повторном достижении после смены порога принять один push за месяц или второй push по новому порогу?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, включая смену порога.

   **Основание.** [R-P001L0039-03](#r-p001l0039-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** Второй push не поступает. За месяц остаётся один push.

   При выборе этого варианта привести в соответствие [R-P001L0040-03](#r-p001l0040-03).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки, включая уже полученный push в том же месяце.

   **Основание.** [R-P001L0040-03](#r-p001l0040-03) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** При достижении нового порога поступает второй push за месяц.

   При выборе этого варианта привести в соответствие [R-P001L0039-03](#r-p001l0039-03).

**Черновик приёмочного теста.** Получить первый push, повысить порог выше текущих расходов, провести покупку до нового порога в том же месяце и посчитать push по карте.

**Последствие.** По логике ТЗ сохранённый порог становится 50 000 ₸. Безопасный GET не допускает такого запрошенного изменения.

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой HTTP-метод закрепить за обязательной операцией сохранения?

### R-P003L0021-01 · При отклонении суммы метод возвращает \`result\` со значением \`ERROR\`.

> 5. При отклонении суммы вернуть прежнее состояние и результат ERROR.  

**Связано с вопросом к автору.** Для неверного параметра установлен 400. Тело с ERROR помещено под 200 и не привязано к запросу. При отклонении суммы требуется вернуть прежнюю настройку вместе с ERROR. Поле amount описано для успеха, а пример ошибки без входа не определяет представление прежних порога и переключателя.

## Готовность и порядок исправлений

ТЗ не готово к разработке затронутых сценариев сохранения и повторного достижения порога. Проверки с однозначно заданными результатами можно подготовить параллельно.

1. Согласовать число push после смены порога и HTTP-метод сохранения. ([Z-009](#z-009), [Z-012](#z-012))
2. Описать чтение порога и переключателя, структуру прежней настройки при отказе и обязательность result по ветвям. ([Z-003](#z-003), [Z-015](#z-015), [Z-014](#z-014))
3. Установить зону совершения пограничной покупки, вход примера 200 с ERROR и правило для частичного возврата. ([Z-007](#z-007), [Z-013](#z-013), [Z-008](#z-008))
4. Указать путь месячного итога до экрана и определить сумму, единицу и источник последних цифр для push. ([Z-002](#z-002), [Z-004](#z-004), [Z-011](#z-011))
5. Определить, входит ли срок получения в приёмку, и выбрать событие записи признака отправки. ([Z-001](#z-001), [Z-010](#z-010))
6. Уточнить применимость 403 и 201 к методу и определить условия для подтверждённых ветвей. ([Z-021](#z-021), [Z-018](#z-018))
