## Проверка набора в целом

ТЗ задаёт расчёт расходов, порог и передачу push. Для обязательных сценариев остаются конфликт месячного лимита со сменой порога, запрошенное изменение настройки через GET и два статуса для чужой карты. Для интеграционной приёмки нужно уточнить контракт чтения, пути данных и наблюдаемые результаты на границах сервисов.

Открытых предполагаемых пробелов — 12. Неоднозначностей — 2. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

## Критичные дефекты

- [Z-011](#z-011) · Месячный максимум Ф-3 включает уже полученный push. Ф-4 требует новый push при достижении повышенного порога независимо от истории. Обязательный сценарий смены порога в том же месяце нельзя принять с единым ожидаемым числом push.

### Z-011 · Повторный push после смены порога

**Дефект · Противоречивость · Критичная.** Месячный максимум Ф-3 включает уже полученный push. Ф-4 требует новый push при достижении повышенного порога независимо от истории. Обязательный сценарий смены порога в том же месяце нельзя принять с единым ожидаемым числом push.

> Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.  

[R-D0047-01](#r-d0047-01) · Уведомление о расходах по карте / Часть B. REST API / Особые правила · [DOCX, абзац 47](../docx/requirements-copy.docx)

> Изменение порога сохраняет накопленные расходы.  

**Сценарий.** При включённых уведомлениях клиент уже получил push в этом месяце. Он повысил порог выше накопленной суммы. Следующая проведённая покупка довела расходы до нового порога в том же месяце.

**Последствие.** Приёмка требует одновременно подавить второй push и отправить его.

**Общее условие.** По той же карте в том же календарном месяце уже получен push. Порог повышен выше сохранённых расходов, и следующая покупка доводит расходы до нового порога. Основания — [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.», [R-D0019-01](#r-d0019-01) «При изменении порога накопленная сумма сохраняется.», [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой исход принять после достижения нового порога в том же месяце: оставить один push или отправить второй?

1. **Вариант 1.** На карту приходится максимум один такой push за календарный месяц, в том числе после изменения порога.

   **Основание.** [R-D0018-03](#r-d0018-03) «На карту приходится максимум один такой push за календарный месяц.».

   **Ожидаемый результат.** После второй покупки новых push нет. За месяц получен один push.

   При выборе этого варианта привести в соответствие [R-D0019-02](#r-d0019-02).

2. **Вариант 2.** Если накопленная сумма ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

   **Основание.** [R-D0019-02](#r-d0019-02) «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.».

   **Ожидаемый результат.** Следующая покупка вызывает push. За месяц получены два push.

   При выборе этого варианта привести в соответствие [R-D0018-03](#r-d0018-03).

**Черновик приёмочного теста.** Получить первый push, повысить порог выше накопленной суммы, провести покупку ровно до нового порога и проверить число push.

**Уже установлено.** Признак хранится. Передача push на отправку должна состояться в течение минуты после получения события сервисом. Момент изменения признака не указан. Основания — [R-D0025-06](#r-d0025-06), [R-D0023-01](#r-d0023-01), [R-D0021-03](#r-d0021-03), [R-D0018-02](#r-d0018-02).

**Открытое решение.** Выбрать наблюдаемое событие передачи на стороне отправителя, при котором меняется признак отправки.

**Что различит проверка.** При начале передачи признак уже меняется. / При начале передачи признак ещё не меняется. Он меняется при её завершении на стороне отправителя.

### Z-012 · Из какого доступного источника сервис расходов получает последние четыре цифры карты для передачи сервису push?

**Предполагаемый пробел · Трассируемость · Существенная.** В push требуются последние четыре цифры карты. Сервис расходов получает порог из настроек, а хранение идентификатора карты само по себе не обеспечивает доступ к этим цифрам.

Затронутые утверждения — [R-D0021-03](#r-d0021-03).

[R-D0021-03](#r-d0021-03) · Уведомление о расходах по карте / Часть A. Новый функционал / Sequence Diagram · [DOCX, абзац 21](../docx/requirements-copy.docx)

> Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога.  

**Сценарий.** Первой покупкой, доводящей включённую настройку до порога, вызвать передачу push. Проследить получение четырёх цифр из согласованного источника и сверить их с фактическими цифрами той же карты в передаче.

**Последствие.** В push требуются последние четыре цифры карты. Сервис расходов получает порог из настроек, а хранение идентификатора карты само по себе не обеспечивает доступ к этим цифрам.

**Уже установлено.** Порог сервис расходов получает из настроек и хранит в тенге. Идентификатор карты хранится, источник последних четырёх цифр не установлен. Основания — [R-D0021-03](#r-d0021-03), [R-D0021-01](#r-d0021-01), [R-D0021-02](#r-d0021-02), [R-D0025-03](#r-d0025-03), [R-T006R0002-05](#r-t006r0002-05).

**Открытое решение.** Связать последние четыре цифры в передаче push с доступным сервису источником данных карты.

**Что различит проверка.** На согласованном пути доступны четыре цифры нужной карты, и передача совпадает с источником. / Согласованный путь не предоставляет сервису четыре цифры нужной карты, и передачу по этому пути принять нельзя.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке в полном объёме. До реализации затронутых сценариев нужно согласовать правила отправки и контракт API. Согласованность примера на границе месяцев и примера ERROR под HTTP 200 зависит от уточнения входов.

1. Согласовать число push после смены порога в том же месяце и HTTP-операцию сохранения. ([Z-011](#z-011), [Z-013](#z-013))
2. Завершить контракт чтения и сохранения, включая статусы, поля ответов, коды переключателя и заголовок запроса. ([Z-014](#z-014), [Z-003](#z-003), [Z-004](#z-004), [Z-017](#z-017), [Z-016](#z-016), [Z-018](#z-018), [Z-019](#z-019))
3. Проследить данные до их потребителей, согласовать сумму в push и событие записи признака. Определить, входит ли срок получения клиентом в приёмку. ([Z-009](#z-009), [Z-002](#z-002), [Z-012](#z-012), [Z-005](#z-005), [Z-010](#z-010), [Z-001](#z-001))
4. Дополнить предусловия первого push, уточнить время совершения покупки по Алматы и установить запрос для примера ERROR под HTTP 200. ([Z-006](#z-006), [Z-008](#z-008), [Z-015](#z-015))
