# Вопросы для согласования на исходном банковском ТЗ

В итоговом отчёте 17 вопросов. Два решения требуют согласования перед приёмкой: приоритет правил повторного push и контракт записи настроек. Вопрос о примере ERROR теперь называет недостающие входные данные. Ниже приведены условия, при которых QA может проверять каждый из четырёх основных сценариев.

Решения по правилам мобильного банка обсуждают указанные в части A представители бизнеса, владелец продукта и аналитик. В части B приведены роли автора и разработчика API. [Роли части A](../../docs/requirements.md#L17) · [Роли части B](../../docs/requirements.md#L113-L114)

1. **Повторный push.** Включить уведомления, на одной карте в одном месяце получить первый push, затем поднять порог выше накопленных расходов. Следующей покупкой довести месячный итог до нового порога. Ф-3 ограничивает число push одним, Ф-4 требует уведомить о достижении нового порога. Владелец продукта выбирает один или два push за месяц и закрепляет приоритет. [Два правила](../../docs/requirements.md#L39-L40) · [Карточка](../../reports/release/review.md#z-009)
2. **Чтение и запись.** Чтение должно вернуть текущие порог и положение переключателя, сохранив оба значения. Для записи требуется заменить настройку. Сейчас описанный GET меняет её. Согласовать два вызова и проверить чтение до и после записи. В отдельном тесте на включённой и выключенной картах проверить, что сервис расходов получает актуальный признак. [Обещанные операции](../../docs/requirements.md#L52) · [Запись](../../reports/release/review.md#z-012) · [Чтение](../../reports/release/review.md#z-013) · [Признак включения](../../reports/release/review.md#z-005)
3. **Ошибка суммы.** На своей карте при действующей сессии отправить 999 ₸ с допустимым переключателем. Для неверного параметра указаны статус 400, ERROR при отклонении суммы и возврат прежнего состояния. Сначала установить вход для примера ERROR под 200. Если он тоже описывает 999 ₸, статусы расходятся. Если другой вход, сохранить отдельные тесты. Согласовать поля для обоих прежних значений. [Обязанность возврата](../../docs/requirements.md#L121) · [Статусы и примеры](../../docs/requirements.md#L162-L171) · [Вход примера](../../reports/release/review.md#z-014) · [Тело ответа](../../reports/release/review.md#z-015)
4. **Покупка на границе месяца.** Для суммы 4 000 ₸ применить дату совершения по Алматы. В примере зона Алматы явно относится к проведению. Уточнить часовую зону 23:58, перевести дату покупки и сверить последовательность с проведением в 00:03. Январская покупка меняет январский счётчик, февральская — февральский. [Правило](../../docs/requirements.md#L38) · [Пример](../../docs/requirements.md#L64) · [Карточка](../../reports/release/review.md#z-007)

## Две формулировки для встречи

- «Входит ли в приёмку получение уведомления на устройстве? Если входит, от какого события измерять предельный срок?» Существующий срок от получения события до передачи push проверяется отдельно. [Z-001](../../reports/release/review.md#z-001)
- «Какое событие в передаче уведомления сервису push устанавливает хранимый признак отправки?» Проверить значение непосредственно до и после согласованного события. [Z-004](../../reports/release/review.md#z-004)

По исходному ТЗ общее число вопросов сохранилось. Исчезли просьбы заново определить источник порога и решить судьбу записи enabled=01. Вопрос о входе образца 200/ERROR стал точнее. В очередь всё ещё попал сценарий многобайтового cardId. Итоговая очередь также вычитана вторым рецензентом по тем же исходным строкам.
