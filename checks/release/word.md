## Проверка набора в целом

Приёмка трёх обязательных веток заблокирована: сохранение через GET, HTTP-статус при отклонении суммы и повторный push после смены порога. Согласованность граничного примера учёта зависит от часовой зоны совершения покупки. Для интеграционных тестов остаются вопросы по чтению настроек, источникам данных и отправке push.

Открытых предполагаемых пробелов — 11. Неоднозначностей — 0. Рекомендаций — 0.

Каждый ID утверждения учитывается один раз. В число нарушений входят подтверждённые дефекты и неоднозначности, для которых показаны две опирающиеся на текст трактовки с разными последствиями. Один и тот же конфликт имеет один ID при любом числе затронутых требований. Критичный дефект блокирует приёмку существенного обязательного сценария. Предполагаемый пробел оставляет открытым ожидаемое поведение или источник данных. Рекомендация предлагает улучшение. Вопросы и рекомендации имеют отдельные счётчики.

**Сценарий.** В сессии владельца отправить запрос с корректными картой и переключателем, в котором отклонена только сумма. Использовать ошибку суммы, представленную ответом «Проверьте сумму».

**Общее условие.** При сохранении с корректной картой и переключателем проверка отклоняет неверную сумму, для которой показан ответ «Проверьте сумму». Ответ в случае, если параметры запроса заполнены неверно.», [R-D0060-01](#r-d0060-01) «200. Ответ в случае успешного выполнения метода.», [R-D0065-01](#r-d0065-01) «\{"result":"ERROR","message":"Проверьте сумму"\}».

**Предложение для автора.** Предложение модели. Выбор формулировки и ожидаемого результата утверждает автор ТЗ.

**Вопрос для решения.** Какой статус должен получить клиент при показанном отклонении суммы, 400 или 200 с ERROR?

1. **Вариант 1.** Отклонённая сумма считается неверно заполненным параметром и даёт HTTP 400.

   **Основание.** [R-D0061-01](#r-d0061-01) «400. Ответ в случае, если параметры запроса заполнены неверно.».

   **Ожидаемый результат.** Приложение получает HTTP 400.

   При выборе этого варианта привести в соответствие [R-D0065-01](#r-d0065-01).

2. **Вариант 2.** Для показанной ошибки суммы применяется альтернативный ответ раздела HTTP 200 с результатом ERROR.

   **Основание.** [R-D0065-01](#r-d0065-01) «\{"result":"ERROR","message":"Проверьте сумму"\}».

   **Ожидаемый результат.** Приложение получает HTTP 200 с result=ERROR.

   При выборе этого варианта привести в соответствие [R-D0061-01](#r-d0061-01).

**Черновик приёмочного теста.** Отправить согласованное отклоняемое значение суммы при остальных корректных данных. Проверить выбранный статус, обязательный ERROR и сообщение под полем в приложении.

> 3. Изменение порога сохраняет накопленные расходы.  

**Сценарий.** При включённых уведомлениях достичь 50 000 ₸ и получить push. В том же месяце поднять порог до 60 000 ₸ и провести покупку на 10 000 ₸.

**Общее условие.** По одной карте с включёнными уведомлениями уже получен push. В том же календарном месяце порог повышают выше накопленной суммы и покупкой достигают нового порога. 1. **Вариант 1.** Максимум один такой push на карту за календарный месяц действует и после смены порога.

   **Ожидаемый результат.** При достижении 60 000 ₸ второго push нет.

**Черновик приёмочного теста.** После первого push повысить порог и пересечь его покупкой. Проверить наличие второго push.

### R-D0074-02 · Запрос для существующей чужой карты даёт HTTP 404.

> Для чужой карты возвращается 404, как и для отсутствующей карты.

### R-D0076-01 · В приведённом после метки 404 примере message равно «Карта не найдена».

Уведомление о расходах по карте / Часть B. REST API / Статусы / 403. Unsuccessful — Forbidden · [DOCX, абзац 76](../docx/requirements-copy.docx)

> \{"message":"Карта не найдена"\}  

**Нарушений не выявлено.** Явное правило для чужой и отсутствующей карты и метка 404 перед примером определяют ветку сообщения. Ошибка внешнего заголовка учтена отдельно. При отклонении суммы сохраняется прежняя настройка и возвращается ERROR. Поле amount задано при успехе, а показанное тело ошибки содержит ERROR и message. Таблица форматов не устанавливает обязательность result и enabled для остальных показанных ошибок. Правило для чужой и отсутствующей карты явно задаёт 404. Записи 401, 403 и 500 также содержат свои коды. Перенос записей упростил бы поиск, а обязательная структура раздела в ТЗ не задана.

## Готовность и порядок исправлений

ТЗ не готово к разработке и приёмке затронутых веток до разрешения трёх блокирующих дефектов.

1. Определить исход повторного достижения в том же месяце, согласовать HTTP-операцию сохранения и единый статус ошибки суммы с обязательным ERROR. ([Z-010](#z-010), [Z-012](#z-012), [Z-003](#z-003))
2. Указать зону совершения покупки в примере и сверить его с Ф-2. Определить период и момент расходования лимита push. ([Z-007](#z-007), [Z-008](#z-008), [Z-005](#z-005))
3. Задать контракт чтения порога и переключателя, источник месячного итога и соответствие кодов состояниям уведомления. ([Z-002](#z-002), [Z-001](#z-001), [Z-006](#z-006))
4. Определить сумму в push, источник последних четырёх цифр и входные данные для учёта возврата. ([Z-004](#z-004), [Z-011](#z-011), [Z-009](#z-009))
5. Задать критерий своевременного получения push и отдельное условие проверки 403. ([Z-014](#z-014), [Z-016](#z-016))
